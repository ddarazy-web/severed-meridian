# Codex 규칙

## 기본 진행 규칙
- 항상 먼저 원인 분석 및 해결 방안을 제시한다.
- 소스 수정은 사용자가 명시적으로 요청했을 때만 적용한다.
- 사용자가 "수정하지 말고", "먼저 보여줘", "소스를 보여줘"라고 요청한 경우 파일을 수정하지 않는다.
- 사용자가 수정 요청을 하기 전에는 분석, 영향 범위, 수정 방향, 예시 코드만 제시한다.
- 커밋은 사용자가 명시적으로 요청했을 때만 진행한다.
- 사용자가 "커밋하지 말고"라고 요청한 경우 절대 커밋하지 않는다.
- 헬퍼 함수의 사용을 지양한다. 3회 이상 재사용을 하는 경우에만 헬퍼 사용을 승인한다.

## 분석 및 답변 규칙
- 크래시/에러 분석 시 원인, 발생 가능 시나리오, 수정 후보, 영향 범위를 함께 설명한다.
- 수정 후에는 어떤 부분을 변경했는지와 기대되는 동작을 설명한다.
- 사용자가 "왜 발생했는지"를 물으면 제공된 스택 정보와 현재 소스 흐름을 기준으로 추정 원인을 제시한다.
- 단순히 가능성만 나열하지 말고, 가장 가능성이 높은 원인을 먼저 제시한다.
- 시뮬레이터와 실제 전투처럼 실행 환경 차이가 있는 경우, 어떤 점이 다른지 함께 확인한다.

## 소스 수정 규칙
- 기존 주석은 기능과 달라지지 않았다면 유지한다.
- 기존 주석이 현재 기능 설명과 맞지 않으면 수정하거나 보강한다.
- 새로 추가하는 주석은 한글로 작성한다.
- 추가/수정된 로직에는 필요한 경우 주석을 꼼꼼하게 추가한다.
- 함수 주석을 추가/수정할 때는, 파라메터 및 리턴값에 대한 주석도 같이 추가한다.
- 불필요한 리팩토링은 하지 않는다.
- 사용자가 요청한 범위 밖의 파일이나 로직은 건드리지 않는다.
- 기존에 직접 수정한 내용이나 커밋된 내용을 임의로 되돌리지 않는다.
- 복원 요청이 있을 경우, 지정된 커밋/범위를 확인한 뒤 해당 변경만 복원한다.

## 빌드/플랫폼 관련 규칙
- Android / iOS / Steam / OneStore / Google 등 플랫폼별 설정 변경 시 다른 플랫폼에 미치는 영향을 함께 확인한다.

## Google Play 내부 테스트 장애 확인 기록
- Google Play 내부 테스트 앱을 다운로드할 수 없거나 스토어에서 `항목을 찾을 수 없습니다`가 표시되면 테스터 등록, 계정, 트랙 상태, 폼팩터뿐 아니라 콘텐츠 등급 상태를 우선 확인한다.
- 실제 QA 앱에서 콘텐츠 등급 분류가 거부되거나 비활성화된 상태 때문에 내부 테스트 트랙을 이용할 수 없었으며, 콘텐츠 등급을 정상 활성화한 뒤 내부 테스트 다운로드 문제가 해결되었다.
- 내부 테스트도 앱 배포에 해당하므로 유효한 콘텐츠 등급이 필요하다. 콘텐츠 등급은 `Play Console > 모니터링 및 개선 > 정책 및 프로그램 > 앱 콘텐츠 > 조치됨 > 콘텐츠 등급`에서 확인한다.
- `Play Console > 모니터링 및 개선 > 정책 및 프로그램 > 앱 콘텐츠`의 `주의 필요` 탭에 미완료 항목이 남아 있는지도 확인한다. 앱에서 사용하지 않는 기능도 단순히 비활성 상태로 방치하지 말고, 해당 설문에서 `해당 없음` 또는 앱에 맞는 답변을 제출하여 필수 선언을 완료해야 한다.
- 앱 콘텐츠의 필수 선언 중 하나라도 미제출·거부·조치 필요 상태이면 내부 테스트를 포함한 게시 및 배포가 제한될 수 있으므로, `주의 필요` 항목이 없고 필요한 선언이 모두 `조치됨` 상태인지 확인한다.
- 확인 대상에는 광고 ID, 건강 앱, 금융 기능, 정부 앱, 데이터 보안, 개인정보처리방침, 광고, 로그인 세부정보(앱 액세스), 콘텐츠 등급, 타겟층 및 콘텐츠 등이 포함된다. Play Console에서 추가되는 신규 필수 선언도 같은 기준으로 확인한다.
- 콘텐츠 등급 분류가 거부된 경우 IARC 설문지를 다시 제출하고 IARC 인증 ID 발급 여부를 확인한다. 대한민국에 게임을 배포하려면 GRAC 등급 적용 여부도 확인한다.
- GRAC 등급이 없는 상태에서 등급 발급 절차를 진행해야 한다면 Google 안내에 따라 프로덕션 및 공개 테스트 출시 국가에서 대한민국을 임시로 제외하고 다른 국가를 선택한 뒤, IARC 인증 ID로 GRAC 등급을 발급받아 대한민국을 다시 포함한다.
- 내부 테스트 장애 점검 순서는 `앱 콘텐츠의 주의 필요·거부 항목 > 콘텐츠 등급/IARC/GRAC 상태 > 내부 테스트 출시 활성 상태 > 테스터 목록과 참여 상태 > 로그인한 Play 계정 > 기기 호환성 > 다른 트랙 및 폼팩터 중복 참여` 순으로 확인한다.

## Firebase SDK 관리 기록
- Firebase Unity SDK 13.10.0에서 `Assets/Firebase/FirebaseApp/Internal/link.xml` 및 `.meta` 파일이 추가되었다.
- 해당 `link.xml`은 Firebase 관련 타입이 Unity의 Managed Stripping 과정에서 제거되지 않도록 보존하는 용도이다. 현재 App/Crashlytics 구성에서는 직접적인 영향이 작을 수 있으나, 추후 Firebase Auth/AppCheck 등을 사용하거나 스트리핑 수준을 높일 경우 필요할 수 있으므로 유지한다.
- 현재 `.gitignore`의 `link.xml*` 규칙에 의해 위 파일들이 Git에서 제외될 수 있다. Firebase SDK 업그레이드나 Jenkins 빌드 점검 시 파일 포함 여부를 확인한다.
- Git에 포함해야 할 경우 `.gitignore`에 다음 예외를 추가하거나 해당 파일만 명시적으로 추적한다.
  - `!Assets/Firebase/FirebaseApp/Internal/link.xml`
  - `!Assets/Firebase/FirebaseApp/Internal/link.xml.meta`


## 문서/보고서 규칙
- 사업팀/비개발자 대상 문서는 프로그래밍 세부사항을 줄이고 이해하기 쉽게 작성한다.
- 비교가 필요한 내용은 표로 정리한다.
- 제출용 문서는 먼저 내용을 정리해서 보여주고, 사용자가 승인하면 문서 파일로 작성한다.



## 로그파일 규칙
- 로그파일을 제안하면, 분석하고 원인을 파악한다.
- 별도로 원인 분석 또는 해결 방안을 묻지 않는다. (생략)
- 원인을 알게 되면, 해결 방안을 제시한다.
- 소스의 수정사항이 있더라도 바로 수정하지 않고 먼저 제안한 후, 수정 요청이 있을 경우 수정을 진행한다.


## 작업 원칙

- 기존 기능을 임의로 변경하지 않는다.
- 작업 전에 관련 코드를 조사한다.
- 중요한 설계 변경은 반드시 기록한다.
- 기존 의사결정과 충돌하는 경우 사용자에게 확인한다.
- 테스트 없이 작업을 완료했다고 판단하지 않는다.
