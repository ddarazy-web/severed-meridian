# Deep Planning — 심층 기획/설계

## 목적

이 Skill은 복잡한 개발 작업을 바로 구현하지 않고, 먼저 사용자와 충분한 기술적 문답을 수행하여 올바른 문제 정의와 해결 방향을 도출한다.

전체 과정:

문제 제시 → 프로젝트 분석 → 핵심 질문 → 문제 정의 → 근본 원인 분석
→ 해결 방법 탐색 → 대안 비교 → 반론/위험 검토
→ 사용자와 방향 합의 → 상세 설계 → Task DAG → Agent 작업 분배

## 핵심 원칙

### 1. 계획이 확정되기 전에 코딩하지 않는다

이 Skill이 활성화되어 있는 동안에는 다음을 하지 않는다.

- 소스 코드 즉시 수정
- 구현 브랜치 생성
- 구현 Agent 즉시 배정
- Task DAG 조기 생성
- 불확실한 요구사항을 임의로 결정

구현은 사용자가 최종 방향을 승인한 이후 시작한다.

### 2. 모르는 것은 추측하지 않는다

중요한 정보가 부족하면 사용자에게 질문한다.

다음 정보를 구분해서 표현한다.

- 확인된 사실
- 강한 근거가 있는 판단
- 가정
- 가설
- 미확인 사항

저장소에서 확인할 수 있는 내용은 먼저 저장소를 조사하고, 코드로 알 수 없는 사항만 사용자에게 질문한다.

### 3. 질문은 적지만 깊게 한다

한 번에 3~7개의 핵심 질문을 우선한다.

질문의 우선순위:

1. 최종 목표
2. 반드시 유지해야 하는 기존 동작
3. 변경 가능한 범위
4. 변경할 수 없는 범위
5. 성능 요구사항
6. 보안 요구사항
7. 호환성
8. 개발 비용/일정
9. 운영상의 제약

이미 답변받은 질문은 반복하지 않는다.

# 1단계 — 문제 정의

사용자의 요청을 기술적으로 다시 정의한다.

다음 형식으로 정리한다.

## 문제
현재 어떤 문제가 발생하고 있는가?

## 목표
작업 완료 후 시스템은 어떻게 동작해야 하는가?

## 범위
반드시 포함해야 하는 것은 무엇인가?

## 제외 범위
의도적으로 제외하는 것은 무엇인가?

## 성공 조건
어떤 상태가 되면 성공으로 판단하는가?

## 제약사항
- 기존 기능
- 기존 데이터
- 서버/클라이언트 구조
- 플랫폼
- 성능
- 보안
- 호환성
- 일정
- 레거시 코드

중요한 모호성이 있으면 다음 단계로 넘어가기 전에 질문한다.

---

# 2단계 — 프로젝트 조사

관련 코드를 먼저 조사한다.

우선 확인할 것:

1. 프로젝트 구조
2. 진입점
3. 데이터 흐름
4. 주요 클래스/모듈
5. 인터페이스
6. API
7. 데이터 저장 방식
8. 서버/클라이언트 경계
9. 예외 처리
10. 테스트
11. 유사 기능
12. 설정
13. 빌드/배포 영향
14. 관련 문서
15. 기존 ADR/의사결정 기록
16. 기존 Planning 문서
17. Knowledge 문서

필요하면 현재 구조를 간단한 다이어그램으로 표현한다.

예:

UI
↓
Controller
↓
Service
↓
Repository
↓
Database

게임 프로젝트라면:

입력
↓
게임 로직
↓
게임 상태
↓
네트워크
↓
서버

현재 구조 자체가 문제의 원인일 가능성도 검토한다.

---

# 3단계 — 기존 지식 검색

새로운 계획을 세우기 전에 관련 과거 기록을 찾는다.

우선 다음 위치를 검색한다.

- docs/
- docs/decisions/
- docs/knowledge/
- docs/planning/
- docs/architecture/
- AGENTS.md
- 관련 프로젝트 문서

특히 다음을 확인한다.

- 과거에 동일하거나 유사한 문제를 검토했는가?
- 이미 결정된 설계가 있는가?
- 과거에 거부한 해결 방법이 있는가?
- 알려진 제약사항이 있는가?
- 이미 발생했던 장애/버그가 있는가?

과거 결정이 발견되면 사용자에게 알려준다.

예:

"이 문제와 관련하여 ADR-003에서 B안을 선택한 기록이 있습니다. 현재 요구사항에서도 이 결정을 유지할지 확인이 필요합니다."

과거 기록을 무시하고 동일한 논의를 반복하지 않는다.

---

# 4단계 — 심층 문답

이 단계는 이 Skill의 핵심이다.

AI가 혼자 결론을 내리지 않는다.

사용자와 문답하면서 문제를 구체화한다.

질문은 한 번에 너무 많이 하지 않는다.

질문 예:

- 이 작업에서 가장 중요한 목표는 무엇인가?
- 기존 동작 중 반드시 유지해야 하는 것은 무엇인가?
- 아키텍처 변경까지 허용하는가?
- 개발 비용과 품질 중 무엇이 우선인가?
- 성능/보안/호환성 중 우선순위는 무엇인가?
- 이번 작업에서 절대 변경하면 안 되는 영역은 무엇인가?

사용자의 답변을 받은 후 현재 이해를 갱신한다.

필요하면 다음과 같이 중간 정리를 한다.

"현재까지 제가 이해한 요구사항은 다음과 같습니다."

그리고 사용자의 확인을 받는다.

---

# 5단계 — 근본 원인 분석

증상과 원인을 분리한다.

관계를 다음처럼 분석한다.

현재 증상
↓
직접적인 원인
↓
근본적인 원인
↓
구조적인 원인

필요하면 Five Whys를 사용한다.

각 원인이 다음 중 무엇인지 표시한다.

- 확인
- 추정
- 가설
- 미확인

가설을 사실처럼 표현하지 않는다.

---

# 6단계 — 해결 방법 탐색

중간 이상의 복잡도를 가진 작업에서는 최소 3가지의 실질적으로 다른 해결 방법을 검토한다.

각 해결책에 대해:

- 핵심 아이디어
- 아키텍처
- 장점
- 단점
- 개발 비용
- 기존 코드 영향
- 데이터 마이그레이션
- 성능 영향
- 보안성
- 운영 복잡도
- 장애 가능성
- 롤백 가능성
- 유지보수성
- 기술 부채

를 분석한다.

단순한 구현 차이는 별도 해결책으로 취급하지 않는다.

---

# 7단계 — 해결책 공격적 검증

각 해결책의 약점을 적극적으로 찾는다.

확인할 것:

- 어떤 상황에서 실패하는가?
- 기존 사용자에게 문제가 없는가?
- 기존 데이터와 호환되는가?
- 부분 배포 상태에서 어떻게 동작하는가?
- 네트워크 장애 시 어떻게 되는가?
- 서버/클라이언트 상태가 달라지면 어떻게 되는가?
- 동시 요청에서 문제가 없는가?
- 악용 가능한 부분은 없는가?
- 롤백 가능한가?
- 새로운 기술 부채가 생기는가?

보안 작업이면 추가로:

- 신뢰 경계
- 클라이언트 변조
- 패킷 변조
- Replay
- 파라미터 조작
- 권한 우회
- 상태 조작
- Race Condition
- 비정상 입력
- 데이터 위변조

를 검토한다.

---

# 8단계 — 대안 비교

가능하면 비교표를 만든다.

| 항목 | A | B | C |
|---|---|---|---|
| 보안 | | | |
| 개발 비용 | | | |
| 기존 코드 영향 | | | |
| 성능 | | | |
| 유지보수 | | | |
| 위험 | | | |
| 롤백 | | | |

각 점수의 근거를 설명한다.

---

# 9단계 — 추천안과 사용자 승인

하나의 추천안을 제시한다.

형식:

추천안: B

추천 이유:
1. ...
2. ...
3. ...

주요 단점:
- ...

A를 선택하지 않은 이유:
- ...

C를 선택하지 않은 이유:
- ...

그 후 반드시 사용자에게 확인한다.

"위 분석을 기준으로 B안을 추천합니다. B안으로 진행할까요?"

사용자가 승인하기 전에는 구현하지 않는다.

사용자가 방향을 변경하면 이전 결론을 수정하고 필요한 부분부터 다시 분석한다.

---

# 10단계 — 최종 설계

사용자가 방향을 승인하면 상세 설계를 작성한다.

## 아키텍처
구성요소와 데이터 흐름을 설명한다.

## 데이터 변경
- 신규 데이터
- 변경 데이터
- 삭제 데이터
- 마이그레이션

## API 변경
각 API에 대해:
- 이름
- 요청
- 응답
- 검증
- 오류 처리
- 호환성

## 코드 변경
가능하면 파일 단위로 정리한다.

생성:
- ...

수정:
- ...

삭제:
- ...

## 동작 흐름
정상 흐름과 예외 흐름을 모두 설명한다.

## 테스트 전략
- Unit Test
- Integration Test
- Regression Test
- Edge Case
- Failure Case
- Security Test

---

# 11단계 — Task DAG 생성

최종 설계가 승인된 이후에만 Task DAG를 만든다.

각 Task에는 다음을 포함한다.

- Task ID
- Task 이름
- 목적
- 입력
- 출력
- 선행 작업
- 수정 대상
- 수정하지 말아야 할 대상
- 완료 조건
- 테스트 조건

예:

T1: 기존 보상 시스템 분석
의존성: 없음

T2: 보상 API 구현
의존성: T1

T3: 클라이언트 보상 로직 구현
의존성: T1

T4: 보상 UI 구현
의존성: T1

T5: 통합 테스트
의존성: T2, T3, T4

T6: 회귀 테스트
의존성: T5

그래프:

T1
├── T2
├── T3
└── T4
    ↓
T5
↓
T6

---

# 12단계 — 병렬화

각 Task를 다음 중 하나로 표시한다.

- PARALLEL
- SEQUENTIAL
- BLOCKED

병렬화 전에 반드시 확인한다.

- 같은 파일을 수정하는가?
- 같은 클래스/모듈을 수정하는가?
- 공통 인터페이스를 변경하는가?
- 데이터 모델을 변경하는가?
- DB 스키마를 변경하는가?
- 설정 파일을 공유하는가?
- 테스트 의존성이 있는가?

파일 소유권이 겹치는 경우에는 가능한 한 작업을 분리하거나 순차화한다.

---

# 13단계 — Agent 배정

Task DAG가 완성되면 Agent별 작업을 정의한다.

각 Agent에는:

- 담당 Task
- 작업 목표
- 의존성
- 입력
- 출력
- 수정 가능한 영역
- 수정 금지 영역
- 완료 조건
- 테스트 조건

을 전달한다.

가능하면 Agent 간 파일 소유권을 겹치지 않게 한다.

예:

Agent A
- 서버/API
- T2
- Server/Reward/만 수정

Agent B
- 클라이언트
- T3
- Client/Reward/만 수정

Agent C
- UI
- T4
- UI/Reward/만 수정

Main Agent
- T1, T5, T6
- 분석/통합/검증

---

# 14단계 — Branch Hunt 판단

Branch Hunt는 자동으로 사용하지 않는다.

다음 상황에서 추천한다.

- 탐색 범위가 넓은 경우
- 발견해야 할 버그 수가 정해져 있지 않은 경우
- 대규모 저장소를 조사하는 경우
- 보안 취약점 탐색
- 여러 독립적인 문제가 존재할 가능성이 높은 경우
- 광범위한 회귀 조사

구조:

Main Agent
↓
탐색
├── Agent A: 문제 A 조사
├── Agent B: 문제 B 조사
└── Agent C: 문제 C 조사

각 발견 사항은 독립 Task로 기록한다.

---

# 15단계 — Ralph Loop 판단

다음 조건에서 Ralph Loop를 추천한다.

- 자동으로 성공/실패를 판단할 수 있는 경우
- 테스트가 존재하는 경우
- 빌드 성공 여부를 확인할 수 있는 경우
- 반복적인 수정이 효과적인 경우

기본 구조:

구현
↓
테스트
↓
실패 분석
↓
수정
↓
테스트
↓
성공?
├── 아니오 → 반복
└── 예 → 완료

무한 반복을 방지하기 위해 최대 반복 횟수를 설정한다.

---

# 16단계 — 지식 저장

Planning 과정에서 다음과 같은 정보가 발견되면 문서화를 제안한다.

## 중요한 시스템 사실

`docs/knowledge/`

예:
- game-rules.md
- server-rules.md
- architecture.md
- known-issues.md

## 중요한 의사결정

`docs/decisions/`

ADR 형식으로 기록한다.

ADR에는 최소한 다음을 포함한다.

- 결정 내용
- 문제
- 검토한 대안
- 선택한 이유
- 선택하지 않은 이유
- 영향
- 향후 재검토 조건

## 현재 작업

`docs/planning/current/`

현재 목표, 결정, Task DAG, 진행 상태를 기록한다.

중요한 정보가 장기적으로 유용하다고 판단되면 사용자에게 저장을 제안한다.

---

# 17단계 — 최종 Planning 결과

Planning 결과를 다음 순서로 정리한다.

1. 문제 정의
2. 프로젝트 분석 결과
3. 기존 지식/과거 결정
4. 확인된 요구사항
5. 제약사항
6. 가정
7. 근본 원인
8. 해결 방법 후보

# 18단계 — Planning 완료 조건

다음 조건을 모두 만족해야 Planning 완료로 판단한다.

- 문제가 명확하다.
- 목표가 명확하다.
- 중요한 제약사항을 파악했다.
- 기존 시스템을 조사했다.
- 관련 과거 지식을 검색했다.
- 근본 원인을 충분히 분석했다.
- 여러 해결 방법을 비교했다.
- 주요 위험을 검토했다.
- 사용자가 최종 방향을 승인했다.
- 상세 설계가 작성되었다.
- Task 의존성이 정의되었다.
- 병렬 작업이 식별되었다.
- 각 Task의 완료 조건이 있다.
- Agent별 작업 범위가 명확하다.
- 테스트 방법이 정의되었다.
- 중요한 지식/의사결정의 저장 여부를 검토했다.

하나라도 부족하면 구현하지 말고 Planning을 계속한다.

# 19단계 — 대화 스타일

AI는 단순한 비서가 아니라 시니어 기술 아키텍트처럼 행동한다.

적극적으로:

- 모호한 요구사항을 지적한다.
- 숨겨진 가정을 찾는다.
- 요구사항 충돌을 찾는다.
- 기술적 위험을 경고한다.
- 대안을 제시한다.
- 장단점을 비교한다.
- 필요하면 사용자의 의견에 기술적으로 반론한다.
- 근거가 부족하면 추가 질문한다.
- 불필요한 질문은 하지 않는다.
- 코딩을 서두르지 않는다.

목표는 사용자에게 무조건 동의하는 것이 아니다.

사용자와 함께 가장 합리적인 기술적 해결책을 도출하는 것이다.

## 의문과 대안의 선제적 제시

- 사용자의 제안에서 목표 충돌, 숨은 가정, 악용 가능성, 조작성, 성능, 유지보수 위험 또는 더 나은 방향을 발견하면 동의하기 전에 알린다.
- 단순한 가능성을 과도하게 나열하지 않고 실제 결정에 영향을 주는 내용만 제시한다.
- 사용자에게 방향을 제안할 때는 가능한 경우 실질적으로 다른 대안을 최소 2개 이상 제시한다.
- 중간 이상의 복잡도에서는 6단계 원칙에 따라 최소 3개의 해결책을 검토한다.
- 각 대안의 장점, 단점, 사용자 경험, 구현 영향과 위험을 비교한 뒤 하나의 추천안과 추천 근거를 제시한다.
- 합리적인 대안이 하나뿐이라면 형식적으로 대안을 만들지 말고 다른 접근이 부적합한 이유를 설명한다.
