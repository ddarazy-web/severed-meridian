# 관리 가능한 구조 기준

새 하위 시스템, 여러 책임이 얽힌 기능, 폴더 재구성 또는 장기 확장을 고려하는 작업에서 사용한다. 작은 수정에 이 문서의 모든 구조를 기계적으로 적용하지 않는다.

## 기본 방향

이 프로젝트의 신규 독립 기능에는 **기능 중심 모듈형 모놀리스**를 기본 방향으로 사용한다.

- 기능 중심: 사용자가 경험하는 기능과 업무 영역을 최상위 탐색 기준으로 삼는다.
- 모듈형: 각 기능의 상태 소유권, 공개 진입점과 의존 방향을 구분한다.
- 모놀리스: 실제 배포·빌드 단위를 불필요하게 분산하지 않고 현재 Unity 프로젝트 안에서 관리한다.

Clean Architecture의 모든 계층, 인터페이스와 DTO를 형식적으로 복제하지 않는다. 구조가 해결해야 할 실제 복잡도와 테스트·교체 요구가 있을 때만 경계를 추가한다.

## 판단 우선순위

1. 변경할 위치와 영향 범위를 쉽게 찾을 수 있는가
2. 상태와 수명주기의 소유자가 명확한가
3. 의존 방향과 외부 계약을 설명할 수 있는가
4. 사용자가 설정·상태·실패 원인을 확인할 수 있는가
5. 기능 추가 또는 교체가 기존 코드를 광범위하게 수정하지 않고 가능한가
6. 위 목적에 비해 구조와 추상화가 과도하지 않은가

기능 동작만 만족하는 구조보다 이후 수정과 장애 분석이 쉬운 구조를 우선한다. 그러나 아직 존재하지 않는 요구사항을 예상해 인터페이스와 계층을 미리 늘리지 않는다.

## 책임과 의존 방향

- 각 타입의 책임을 한 문장으로 설명할 수 있게 한다.
- 상태를 실제로 변경할 수 있는 주체를 제한하고 읽기와 쓰기 경계를 구분한다.
- 상위 정책이 구체적인 Unity 표현이나 외부 SDK 세부사항에 직접 얽히지 않도록 한다.
- 순환 의존성을 만들지 않는다. 이벤트와 콜백을 사용해도 구독·해제 주체와 수명주기를 명확히 한다.
- 전역 상태가 필요하면 생성, 초기화, 갱신, 해제 시점을 드러내고 숨은 실행 순서에 의존하지 않는다.

기본 흐름은 가능한 한 한 방향으로 읽혀야 한다.

```text
입력·UI
  ↓
Application: 진행과 유스케이스 조정
  ↓
Domain: 규칙과 상태 판정
  ↓
결과
  ↓
Presentation·저장·로그
```

- Presentation이 Domain 상태를 임의로 직접 변경하지 않게 한다.
- Domain이 팝업, Addressables, 플랫폼 SDK 같은 표현·인프라 세부사항을 직접 호출하지 않게 한다.
- 기능 외부에는 작은 공개 진입점만 제공하고 내부 타입을 불필요하게 노출하지 않는다.

## 객체지향과 다른 방식의 선택

| 상황 | 우선 검토할 방식 |
|---|---|
| 상태와 수명주기를 함께 소유 | 캡슐화된 클래스 |
| 런타임 구현 교체가 실제로 존재 | 좁은 인터페이스와 다형성 |
| Unity 기능의 조립과 선택적 동작 | 상속보다 컴포넌트 조합 |
| 입력에 따른 계산·변환·검증 | 순수 함수 또는 불변 데이터 |
| 대량 개체의 반복 시뮬레이션 | 데이터 중심 처리와 명시적 단계 |
| 구현이 하나이고 교체 요구가 없음 | 구체 타입과 단순한 직접 호출 |

객체 수를 늘리는 것이 객체지향 설계의 목표가 아니다. 책임, 상태와 계약이 더 명확해지는지를 기준으로 선택한다.

## 함수 분리와 헬퍼 기준

- 동일 로직이 실제 세 곳 이상에서 반복될 때 재사용 헬퍼를 만든다.
- 한두 줄의 단위 작업마다 이름을 붙여 헬퍼로 분해하지 않는다. 호출을 따라다녀야 전체 흐름을 이해하게 되면 오히려 관리성이 낮아진다.
- 한 함수가 지나치게 길어 서로 다른 책임이나 단계가 섞이면, 재사용되지 않더라도 책임 단위의 private 메서드로 분리할 수 있다.
- 긴 함수의 분리 여부는 줄 수만으로 판단하지 않는다. 입력·출력, 상태 변경, 실패 처리와 단계 경계가 독립적으로 설명되는지를 본다.
- 분리된 메서드는 호출 순서만 감추는 모호한 이름 대신 수행 책임과 결과가 드러나는 이름을 사용한다.

## 폴더 구조

프로젝트 최상위에서는 기능, 공통 시스템과 플랫폼 경계가 먼저 보이게 한다.

```text
Scripts/
├─ Features/
│  ├─ Survivor/
│  ├─ Battle/
│  ├─ Gacha/
│  └─ Story/
├─ Systems/
│  ├─ Save/
│  ├─ Audio/
│  ├─ Addressables/
│  └─ Network/
├─ UI/
├─ Platform/
│  ├─ Android/
│  ├─ IOS/
│  └─ Steam/
└─ Shared/
```

- `Features`에는 사용자가 직접 경험하는 독립 기능을 둔다.
- `Systems`에는 여러 기능이 사용하는 기반 시스템을 둔다.
- `Platform`에는 플랫폼별 구현과 어댑터를 둔다.
- `Shared`는 실제로 여러 모듈에서 공유되고 명확한 소유자가 없는 안정적인 요소로 제한한다.
- 기존 저장소가 다른 최상위 명칭을 사용하면 이름을 억지로 바꾸지 않고 같은 의미의 경계를 기존 구조 안에 적용한다.

기능 관련 파일은 가능한 한 가까이 둔다. 기능이 작을 때는 평평하게 유지한다.

```text
Survivor/
├─ SurvivorMinigame.cs
├─ SurvivorGameplayController.cs
├─ SurvivorGameplayConfig.cs
├─ SurvivorInputController.cs
└─ SurvivorResult.cs
```

실제 책임 경계와 파일 수가 커질 때만 다음 구조를 선택적으로 사용한다.

```text
FeatureName/
├─ Runtime/
│  ├─ Domain/
│  ├─ Application/
│  ├─ Presentation/
│  └─ Configuration/
├─ Editor/
└─ Tests/
```

- 모든 기능에 위 폴더를 강제하지 않는다.
- 파일이 적으면 기능 루트를 평평하게 유지한다.
- Runtime과 Editor 경계는 Unity 컴파일 규칙에 맞게 명확히 한다.
- 타입 하나 때문에 폴더 하나를 만들지 않는다.
- 기술 종류별 전역 폴더보다 함께 변경되는 기능 파일의 응집을 우선하되, 기존 하위 시스템 구조와 충돌하면 기존 방식을 유지한다.

다음과 같이 기술 종류만으로 신규 기능을 흩어 놓는 최상위 구조는 피한다.

```text
Scripts/
├─ Managers/
├─ Controllers/
├─ Models/
├─ Interfaces/
├─ Helpers/
└─ Utils/
```

이 구조는 기능 하나를 변경할 때 여러 폴더를 오가게 만들고 소유권과 영향 범위를 숨긴다. 단, 기존 레거시 구조를 요청 없이 일괄 이동하지 않는다.

## 사용자 확인 가능성

기능을 사용하는 개발자와 콘텐츠 작업자가 다음을 확인할 수 있게 한다.

- 핵심 설정값과 적용 대상
- 현재 동작 상태와 상태 전환 이유
- 자동 선택 또는 계산된 결과의 근거
- 실패한 단계, 대상과 복구 방법
- 런타임에서만 확인 가능한 상태를 위한 제한된 디버그 표시 또는 읽기 전용 진단 정보

상시 로그를 과도하게 늘리거나 내부 구현 전체를 공개하지 않는다. 정상 운영 비용과 정보 민감도를 고려해 필요한 진단 지점만 제공한다.

확인 수단은 책임에 맞게 선택한다.

| 확인 대상 | 권장 수단 |
|---|---|
| 정적 설정과 참조 | Inspector, ScriptableObject, 검증 메뉴 |
| 런타임 상태와 전환 이유 | 읽기 전용 디버그 뷰, 제한된 상태 API |
| 실패 단계와 대상 | 구조화된 로그, 검증 보고서 |
| 자동 선택·계산 결과 | 입력값과 결정 근거를 포함한 진단 정보 |

확인 기능이 런타임 성능, 정보 보안 또는 릴리스 화면에 영향을 주면 Editor·Development 조건으로 제한한다.

## 대규모 조직의 관리 원칙

규모가 커질수록 특정 디자인 패턴보다 다음 운영 장치를 중요하게 본다.

1. 소유권: 기능과 상태를 책임지는 모듈 또는 팀이 명확하다.
2. 경계: 모듈이 공개하는 계약과 직접 접근하면 안 되는 내부 구현이 구분된다.
3. 단방향 의존성: 순환 참조와 숨은 호출 흐름을 피한다.
4. 작은 공개 API: 필요한 진입점만 공개하고 변경 파급을 제한한다.
5. 자동 검증: 테스트뿐 아니라 설정, 에셋, 의존 규칙과 빌드 결과를 반복 검증한다.
6. 관찰 가능성: 실패한 상태와 단계를 재현·추적할 수 있다.
7. 결정 기록: 장기 영향이 있는 선택은 ADR로 이유와 폐기한 대안을 남긴다.
8. 점진적 구조화: 실제 복잡도가 생길 때 경계를 추가하고 예상만으로 확장 구조를 만들지 않는다.

새 구조를 평가할 때 클래스와 폴더 수보다 이 원칙을 실제로 지키는지 확인한다.

## 구현 후 설명과 검토

구조를 새로 만들거나 크게 바꿨다면 사용자에게 다음을 보여준다.

- 관련 폴더 트리
- 핵심 타입별 한 줄 책임
- 입력부터 결과까지의 데이터·제어 흐름
- 외부 의존성과 직렬화 경계
- 모듈 간 허용된 의존 방향과 공개 진입점
- 현재 제공하는 확장 지점
- 단순성을 위해 의도적으로 일반화하지 않은 부분
- 자동 검증과 남은 수동 확인 항목

검토 시에는 기능 성공뿐 아니라 새로운 변경이 어느 파일에서 시작되는지, 실패 원인을 어디서 확인하는지, 타입을 제거하거나 교체할 때 영향 범위를 예측할 수 있는지도 확인한다.
