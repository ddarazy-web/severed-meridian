# Unity 프로젝트 규칙

기존 프로젝트 동작을 보존하면서 요청을 충족하는 가장 작고 완결된 변경을 수행한다. 저장소의 기존 지침과 사용자의 현재 요청은 이 스킬보다 우선한다.

## 작업 맥락 확인

코드를 제안하거나 수정하기 전에 다음을 수행한다.

- 적용되는 저장소 지침을 읽고 영향받는 코드, 호출부, 직렬화된 에셋 및 플랫폼 조건부 코드를 조사한다.
- 확인된 엔진, 패키지, 경로 및 로컬 규칙은 [프로젝트 프로필](references/project-profile.md)을 읽는다. 변경될 수 있는 값은 원본 파일에서 다시 확인하며 저장소 내용을 최종 기준으로 삼는다.
- 새 하위 시스템, 여러 책임이 얽힌 기능, 폴더 재구성 또는 확장 지점 설계가 포함되면 [관리 가능한 구조 기준](references/maintainable-structure.md)을 읽는다.
- 프로젝트가 직접 관리하는 코드와 외부 라이브러리, 생성 코드, 패키지 및 로컬 라이브러리 코드를 구분한다. 작업이 외부 코드를 직접 대상으로 하지 않는 한 외부 소스 수정 대신 어댑터나 프로젝트 코드 수정을 우선한다.
- 관련된 경우 씬, 프리팹, ScriptableObject, Addressables, 저장 데이터 및 Android·iOS·Steam·스토어별 변형에 미치는 영향을 확인한다.

## 안전한 구현

- 규칙은 점진적으로 적용한다. 새 코드는 현재 프로젝트 규칙을 따르고, 기존 코드는 요청으로 직접 수정하는 부분만 주변 코드 스타일에 맞춘다.
- `.editorconfig`와 수정 대상 파일 주변의 스타일을 따른다. 별도 요청 없이 수정 파일 전체를 정리하거나 요청 범위 밖의 레거시 명명법, namespace, 서식 또는 아키텍처를 일괄 변경하지 않는다.
- namespace는 해당 하위 시스템의 기존 방식을 따른다. 주변 코드가 전역 namespace를 사용하면 신규 코드도 이를 유지하고, 이미 namespace 체계가 있는 영역에서는 그 체계를 이어간다.
- 기존 assembly definition 구조를 유지한다. 일반 기능 추가에는 새 asmdef를 만들지 않는다. 컴파일 격리, 테스트 어셈블리 또는 Editor/runtime 분리처럼 실익이 명확한 경우에만 의존성과 마이그레이션 영향을 분석하여 먼저 제안한다.
- 의존성 접근은 해당 하위 시스템의 기존 방식을 따른다. 기존 singleton 또는 service 접근을 새 기능 때문에 VContainer로 전환하지 않는다. 이미 VContainer를 사용하는 영역에서는 그 영역의 등록 방식과 수명주기 규칙을 이어간다.
- 에셋 로딩은 해당 하위 시스템의 기존 방식을 따른다. Addressables, Resources 또는 Inspector 직접 참조 중 하나를 프로젝트 전체에 새로 강제하지 않는다. 기존 영역의 로딩, 해제, 캐싱 및 수명주기 규칙을 이어간다.
- 런타임 UI 프레임워크를 새로 선정하거나 화면 프리팹을 기본적으로 생성하지 않는다. 런타임 UI는 UI 팀이 전달한 프리팹과 해당 하위 시스템의 기존 연결 방식을 사용한다. UI Toolkit 등 UI 프레임워크의 신규 선택은 Editor 전용 도구에 한해 작업 요구사항에 맞춰 판단한다.
- UI 팀이 전달한 프리팹은 사용자가 프리팹 수정까지 명시적으로 요청한 경우에 구조와 컴포넌트 연결을 변경할 수 있다. 시각 디자인 변경이 필요한 경우에는 프리팹 수정 요청에 포함되어 있더라도 적용 전에 범위와 기대 결과를 별도로 확인한다.
- Unity 직렬화 호환성을 보존한다. 직렬화 필드, 타입, 어셈블리 이름, 에셋 또는 경로를 가볍게 변경하지 않는다. 이름 변경이 필요하면 마이그레이션을 계획하고 상황에 맞는 Unity 호환성 수단을 사용한다.
- 런타임 코드에서 Editor 전용 API를 사용하지 않는다. 새 Editor 코드는 `Editor` 폴더 또는 Editor 전용 어셈블리 경계 안에 둔다.
- 모든 Unity 에셋과 짝을 이루는 `.meta` 파일을 보존한다. 확인된 마이그레이션 사유 없이 GUID가 포함된 메타데이터를 재생성, 교체 또는 삭제하지 않는다.
- Unity Editor를 통한 변경이 더 안전한 경우 씬, 프리팹 또는 기타 Unity YAML 직렬화 파일을 직접 수정하지 않는다. 직접 수정은 범위가 작고 구조를 이해하며 결과를 검증할 수 있을 때만 허용한다.
- 새 의존성이나 중복 추상화를 도입하기 전에 설치된 라이브러리와 기존 하위 시스템 패턴을 재사용한다. 비동기 처리에는 UniTask가 사용되고 있으므로 비동기 작업을 추가할 때 취소 처리와 Unity 오브젝트 수명주기를 보존한다.
- 빈번하게 실행되거나 수명주기에 민감한 경로에서 프레임 단위 할당, 반복적인 오브젝트 탐색, 메인 스레드의 블로킹 I/O 및 해제되지 않는 이벤트 구독을 새로 만들지 않는다. 이 항목은 검토 기준이며 요청과 무관한 최적화를 허용하지 않는다.
- 모든 단위 작업을 헬퍼 함수로 분리하지 않는다. 동일 로직이 실제로 3회 이상 반복 사용될 때에만 재사용 헬퍼로 추출한다. 다만 한 함수가 지나치게 길어 서로 다른 책임이나 처리 단계를 파악하기 어려운 경우에는 재사용 횟수와 무관하게 책임 단위 메서드로 분리할 수 있다.
- 새 주석은 한글로 작성한다. 의도, 수명주기 제약, 플랫폼 차이 또는 명확하지 않은 우회 처리를 설명하며 코드 문법을 그대로 서술하지 않는다.

## 관리 가능한 구조

- 단기 기능 완성보다 변경 위치, 상태 소유자, 의존 방향과 영향 범위를 쉽게 파악할 수 있는 구조를 우선한다. 다만 예상만으로 계층, 인터페이스 또는 확장 지점을 만들지 않는다.
- 신규 독립 기능은 기능 중심 모듈형 모놀리스를 기본 방향으로 삼는다. 최상위에서 기능과 공통 시스템이 먼저 보이고, 기능 내부에서 Runtime, Domain, Application, Presentation, Configuration, Editor, Tests 같은 실제 책임 경계가 드러나게 한다.
- 폴더와 namespace, 핵심 타입의 책임 및 의존 방향이 같은 구조를 표현하게 한다. 폴더 트리만 보아도 기능 소유권과 변경 시작점을 추정할 수 있어야 한다.
- 객체지향을 목적처럼 강제하지 않는다. 상태와 수명주기의 캡슐화, 실제 구현 교체 또는 컴포넌트 조합에 유리할 때 사용하고, 단순 계산·변환·검증에는 순수 함수나 데이터 중심 구조가 더 명확하면 이를 사용한다.
- 코드와 폴더는 관련 기능이 함께 보이도록 구성한다. 파일 수가 적은 기능에 형식적인 하위 폴더를 만들지 않고, 책임 경계가 생길 때만 Runtime, Editor, Tests, Configuration 등의 하위 구조를 도입한다.
- `Managers`, `Controllers`, `Models`, `Interfaces`, `Helpers`, `Utils`처럼 기술 종류만으로 신규 기능의 최상위 폴더를 나누지 않는다. 함께 변경되는 기능 파일의 응집을 우선한다.
- 중요한 설정, 현재 상태, 자동 결정 결과와 실패 이유는 Inspector, 명확한 로그, 검증 결과 또는 필요한 범위의 읽기 전용 디버그 수단으로 사용자가 확인할 수 있게 한다. 숨은 전역 상태와 암묵적인 초기화 순서를 피한다.
- 신규 구조를 제안하거나 구현한 뒤에는 폴더 트리와 핵심 타입의 책임, 데이터 흐름, 확장 지점과 의도적으로 확장하지 않은 부분을 사용자가 검토할 수 있게 설명한다.

## 변경 위험에 비례한 검증

- 최종 diff에서 의도하지 않은 에셋, 패키지 잠금 파일, 생성된 프로젝트 파일 및 줄바꿈 변경이 발생하지 않았는지 확인한다.
- 기존 테스트가 있는 영역에서는 관련 테스트를 변경 내용에 맞춰 유지하고 가장 좁은 범위로 실행한다. 테스트 기반이 없는 영역에는 사용자의 요청 없이 새로운 테스트 구조를 만들지 않는다.
- 가능한 범위에서 컴파일을 확인하고, 자동 테스트로 다루지 않는 동작은 필요한 수동 검증 절차를 제시한다. 실제로 수행하지 않은 Unity 검증을 완료했다고 보고하지 않는다.
- 씬, 프리팹, Addressables, 렌더링, 애니메이션, 입력 또는 플랫폼 관련 작업에서는 현재 환경에서 수행할 수 없는 Unity Editor 또는 실제 기기 검증 항목을 명시한다.
- Android, iOS, Steam, OneStore, Google Play 또는 기타 플랫폼 설정 변경 시 다른 플랫폼에 미치는 영향을 명시적으로 확인하거나 보고한다.
- 변경된 동작, 수행한 검증, 남은 수동 확인 사항 및 프로젝트 문서와 구현 사이의 불일치를 보고한다.

## 결정 기록

- 여러 시스템에 영향을 주거나 저장 형식, 플랫폼, 아키텍처, 외부 계약 또는 장기 호환성을 변경하는 중요한 결정은 ADR 기록 대상으로 본다.
- 나중에 선택 이유와 폐기한 대안을 다시 확인할 필요가 있는 결정에는 ADR 작성을 제안한다.
- 단순 구현 세부사항, 작은 기능 변경 및 기존 패턴을 그대로 따르는 작업에는 별도 요청 없이 ADR이나 기능 문서를 만들지 않는다.
- ADR이 필요한 경우 저장소에 정의된 결정 문서 경로와 기존 형식을 따른다.

## 확인이 필요한 결정

다음 항목을 한 번의 작업만으로 프로젝트 전체 규칙으로 확정하지 않는다. 적용하기 전에 사용자에게 확인하거나 이미 기록된 결정을 근거로 삼는다.

- 레거시 코드 전반의 namespace 도입 또는 namespace와 폴더의 매핑
- 새로운 assembly definition 경계
- 의존성 주입 패턴의 의무화 또는 기존 singleton·service 접근 방식의 교체
- UI 팀이 전달한 런타임 프리팹의 시각 디자인 변경
- 기존 Addressables 및 Resources 사용 범위를 넘어서는 새로운 에셋 로딩 정책
- 명명법 마이그레이션, 광범위한 서식 변경, analyzer, warning-as-error 정책 또는 자동 리팩터링
- 저장 형식, 네트워크 프로토콜, 최소 지원 플랫폼, 목표 프레임 또는 성능 예산 변경
