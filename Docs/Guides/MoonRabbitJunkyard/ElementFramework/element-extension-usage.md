# 퍼즐 요소 콘텐츠·행동·드론 정책 추가 안내

현재18종의 실제 제작 SO, 기획 출처 및 배포 MemoryPack 사용법은 [요소 제작 원본과 MemoryPack 안내](element-content-authoring.md)를 따른다. 아래 단계별 사례의 임시 입력과 현재 출시 제작 원본은 구분한다.

2026-10-07. Unity 6000.3.10f1의 현재 제작·실행 경계를 기준으로 한다. [통합 가이드](../../../Planning/MoonRabbitJunkyard/ElementFramework/integration-guideline.md)와 [5단계 검증 기록](../../../Verification/MoonRabbitJunkyard/ElementFramework/phase-05-progress.md)을 함께 확인한다. 최종85종692682 PASS/FAIL0·각 실제 종료0과 전량 논리/원본 보존 감사를 완료했다. 미검증 플랫폼과 새 행동의 공식 출시 경계는 아래에 구분한다.

## 같은 행동의 새 콘텐츠

1. Create → MATCH → 요소 정의에서 `ElementDefinitionAsset`을 만든다. 기존 ID를 변경하거나 재사용하지 않고 영구 ID와 표시 이름을 지정한다. 필요한 프로필만 활성화한다. 같은 행동의 수치·크기·표현 차이는 데이터로 추가한다.
2. Create → MATCH → 요소 카탈로그의 `ElementCatalogAsset`에 정의를 연결한다. `CreateCatalog()` 검증에서 중복·누락 ID, 잘못된 프로필과 생성 참조가 거절되는지 확인한다. 콘텐츠마다 종류 enum이나 실행기 분기를 추가하지 않는다.
3. Create → MATCH → 요소 시각 카탈로그의 `ElementVisualCatalogAsset`을 카탈로그에 연결한다. 새 ID의 시각 정의 또는 기존 이미지로 향하는 명시적 공유 별칭을 등록한다. 내구도·색·방향·프레임·효과와 생성되는 표현까지 지원해야 한다. 이미지 누락을 임의의 기본 종류로 숨기지 않는다.
4. 레벨의 `ElementCatalog`를 연결하고 검색·필터·선택 후 배치한다. `ElementPlacementEditing.ForDefinition`과 기존 SerializedObject/Undo 경로를 사용한다. 층·겹침·2×2 경계를 검증한다. RandomPower 공급 정의는 직접 배치하는 파워와 다르며 직접 배치 불가 정의는 선택만으로 배치되지 않는다.
5. 저장·재로드·Undo/Redo와 Asset/팩2 실행을 확인한다. 편집 보드·플레이 테스트·월드 보드의 동일 표현 조회, 실제 피해·제거·미션·공급까지 확인한다.

공급 본체 참조는 현재 지원 계약에 맞는1칸 Durability 정의를, RandomPower 참조는 파워 정의를 가리킨다. 공급용 래퍼는 결과 정의의 표현을 따라간다. 새 행동을 공급하려면 참조 검증과 공급 실행의 지원 여부를 별도로 확인한다.

5단계 사례는2×2 금속기둥 상자·거미줄 층·가로 로켓의 신규 ID3개다. 기존 행동/공유 이미지 별칭의 실제 확장에 생산 코드 변경은 필요하지 않았다. 이는 임시 제작 입력 검증이며 출시용 신규 에셋3개를 저장했다는 뜻은 아니다.

## 저장·호환·복구

- 스키마5는 ID 배치/정의를, 팩2는 해당 규칙을 저장한다. 구형 스키마4/팩1 읽기는 호환 어댑터에 유지한다. 기존 enum 숫자와 영구 ID를 바꾸지 않는다.
- `LevelElementMigration.Preview`와 `PreviewSupply`는 원본을 저장하지 않는 미리보기다. 선택 적용은 구형 스키마4와 Undo 경계에서 수행한다. 스키마5를 다시 구형 변환하지 않는다.
- 선택 적용 전에 `LevelPackSnapshot` 등으로 규칙 값을 보관하고 원본 에셋/.meta의 위치·GUID·연결을 별도로 기록한다. 값 복구와 GUID 복구는 다르다. 원본 전체 변환이나 HEAD 복원으로 기존 WIP를 덮어쓰지 않는다.
- 신형 팩은 카탈로그를 포함하는 Snapshot/Encode 경로를 사용한다. 레벨 목록만 받는 기존 Encode는 구형 팩1 계약을 유지한다. 50레벨 번호 구간과50→51 경계를 유지한다.
- 아트는 규칙 팩/지문과 분리한다. 팩2 단독 호출부는 대응하는 시각 카탈로그를 별도로 전달해야 한다. 에디터 게임 실행은 이를 연결하지만 임의의 독립 호출부까지 이미지가 자동 포함되지는 않는다.
- 실패 시 소유한 임시 검사 경로만 정리하고 원본 해시/GUID/팩과 과거 증거의 복원을 확인한다. 제작 값은 Undo/변경 전 백업으로 복구한다. 임의 씬 저장·디스크 배포 팩 재생성·과거 원문 삭제·전체 WIP 원복을 복구 수단으로 사용하지 않는다.

## 새 고유 행동

기존 프로필로 표현할 수 없는 규칙에만 구현을 추가한다. 먼저 변경 의미와 실패 사례를 정하고 기존 게임 정의에 적용하는 공식 규칙 변경은 별도로 합의한다.

1. `ElementReactionBehavior`에 영구 키를 추가하고 `PackedElementDefinition`의 검증 계약을 갱신한다. 기존 키 숫자는 유지한다.
2. `ElementBehaviorRegistry`에 읽기 전용 조회/적용 함수를 명시적으로 등록한다. 적용이 같으면 기존 공통 함수를 재사용한다. 미등록 행동을 기본 행동으로 대체하지 않는다.
3. `ElementLevelLayout`의 화면/미션 호환 경계와 제작·직렬화·공급·시각·봇 공개 관찰을 확인한다. 교환·매칭·낙하·연쇄 실행기를 복제하지 않는다.
4. 실제 정의로 Asset/팩2 왕복, 조회의 비변경성, 공통 피해·제거·미션 실행과 규칙 난수 보존을 확인한다. enum/등록 개수를 고정한 검사 계약 보정과 런타임 결과 변화를 분리한다.

5단계 `EvenTurnDurability`는 짝수 턴에 기존 내구도 피해를 허용하고 홀수 턴에 보호하는 최소 사례다. 기존 피해 적용을 재사용하며 검사 정의에만 연결했다. 정식 콘텐츠로 사용하려면 플레이어에게 보이는 규칙, 봇 공개 판단, 공급·시각 상태 지원 의미를 별도로 검토해야 한다. 기존 출시 정의에는 적용하지 않았다.

## 필요한 드론 정책

정의500개를 위해 정책500개를 등록하지 않는다. 기존 미션/대상 기여 의미에 맞으면 정책을 재사용하고 맞지 않을 때만 `PowerBlocks/Runtime/DroneTargetPolicyRegistry` 등록을 확장한다.

활성 미션의 남은 수와 대상 반응으로 필요한 정책만 조회하고 후보 검색 캐시를 공유한다. 병합·예약·착탄 재검증·동률 선택은 `DroneTargetManager` 공통 경로를 유지한다. 읽기 전용 조회에서 규칙 난수를 소비하거나 숨은 공급·내부 ID·예약을 봇 공개 관찰에 전달하지 않는다.

제거·공급·생성 뒤 기존 `Invalidate` 계약과 Request/Refresh/Land 예약 수명을 확인한다. 검사에서 직접 Invalidate한 결과와 게임 실행 중 자동 호출된 결과를 구분한다. 5단계 호출 수 검사는 전자이며 최종 드론 회귀는 통합 경계를 확인한다.

필수 관찰은 정책별 호출 수·공유 검색 수·반복 재사용·비활성 호출0·뒤늦은 공급 목표·완료 미션 제외·착탄 전 무효화/재선정·예약 반환이다. 새 짝수 턴 행동의 Damage 반응은 기존 Durability 정책에 맞아 별도 정책을 추가하지 않았다.

## 리소스와 풀

`ElementResourcePlan`은 배치·공급 참조·행동/효과 생성 관계를 따라 준비 집합을 만든다. 기본 블록과 생성 가능한 파워도 포함한다. 전체500개 이미지/풀을 선로딩하지 않는다. 공유 아틀라스 동반 이미지와 미사용 별도 주소 요청은 구분한다.

준비 완료 뒤 실행하며 반환·취소·전환에서 소유자가 핸들과 Sprite 복제본을 해제한다. 월드 보드/효과 슬롯은 준비 용량 안에서 재사용한다. 반복 Transform 수는 native 자식까지 포함하며 논리 칸 수가 아니다. 준비 중 취소/전환은 단순 Dispose로 대신하지 않는다.

## 필수 검사와 측정 한계

`Elements/Editor/Tests/ElementScaleVerification`의 RunContent/RunBoards/RunCatalog/RunBehavior/RunPolicies/RunResources가 확장 사례다. 전용 배치 Editor와 임시 제작 에셋을 소유하는 검사이므로 사용자 작업 Editor에서 직접 실행하지 않는다. `Logs/ElementFramework/Phase05` 실행/원문 보존 스크립트와 실제 종료 기록을 사용한다.

500개는 저장/재로드 가능한 제작 정의와 참조로 구성했다. 가상화 표시 행12개와 실제 검색·선택·배치·Undo/Redo·구독 해제를 확인했다. 측정 환경은 같은 Windows Editor, 워밍업1회/표본5회다. 실제 min/max와 입력 범위는5단계 기록/원문 JSON에 남긴다.

`GC.GetAllocatedBytesForCurrentThread`는 알려진 할당에도0을 반환해 이 환경에서 사용할 수 없었다. `GC Allocated In Frame` 바이트는 전체 Editor 프레임을 포함하며 함수 단독 할당이 아니다. GC.Alloc 나노초를 바이트로 해석하지 않는다. native 객체 검증은 화면 픽셀, Android/iOS IL2CPP·번들 빌드·실기기 FPS를 증명하지 않는다.

## 중복 후보의 유지 이유

`LegacyElementLevelAdapter`는 스키마4 미리보기/읽기, `LegacyElementDefinitions`와 구형 시각 연결은 구형 입력/선택, `ElementLevelLayout.ViewKind`는 현재 보드/미션 표현을 연결한다. 공급 `ResolveBody`는 리소스 계획/공급 레이아웃에서 사용한다. 세 보드 바인딩·소유권은 다르고 표현 조회는 공유 `ElementVisualLookup`으로 모였다.

이 경계는 이름이나 유사 코드만으로 삭제하지 않는다. 현재/구형 호출부·전후 동등성·취소/소유권까지 입증하지 못한 후보는 유지한다. 삭제 실적을 위해 호환 경계를 제거하지 않는다.
