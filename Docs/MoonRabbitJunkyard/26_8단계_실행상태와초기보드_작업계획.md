## 목적과 완료 의미

에디터에서 만든 레벨 정의를 원본과 분리된 실행용 상태로 구성하고, 같은 레벨 내용과 시드로 같은 초기 구성을 재현한다. 제작자가 이를 실제 Editor에서 읽기 전용으로 확인할 수 있게 한다.

이번 단계의 초기 보드는 **시작 조건 검사 전의 초기 배치 후보**다. 완성 매칭 없음·유효한 교환 최소 하나라는 게임 시작 조건은 그대로 유지하며, 그 조건을 확인하는 매칭/교환 조회와 후보 재생성은 다음 단계에서 연결한다. 따라서 이번 결과를 플레이 가능·시작 가능·클리어 가능 판정으로 표시하지 않는다.

목표는 다음 구현이 에셋이나 편집 창 상태를 직접 수정하지 않고 사용할 수 있는 기반을 만드는 것이다. 실제 한 수 진행과 낙하·효과·보충·봇을 한꺼번에 넣지 않는다.

## 확인된 현재 상태

- `LevelDefinition.CurrentSchemaVersion`은 4다. 일반/파워 블록, 장애물, 덮개, 먼지, 흐름, 연결, 공급, 회수 부품, 미션 정의가 있다.
- `BoardDefinition`은 10×10 활성 칸을 표현한다. 일반 블록은 다섯 종류 중 레벨에 선택된 3~5종을 사용한다.
- `InitialBlockDefinition`은 무작위 일반/고정 일반/청소로켓/달폭탄/수거드론/무지개 자석을 구분하며 로켓 방향을 저장한다.
- `LevelPlacementRules`는 점유와 2×2 본체 크기를 제공한다. 폐가전과 발전기는 네 칸을 점유하지만 본체는 하나다.
- 정의의 읽기 전용 목록도 내부 불변성을 보장하지 않는다. 합류 우선순위, 전선 꼭짓점, 생성구 공급 목록에는 중첩된 `List`가 있다. 얕은 복사만으로 실행 상태를 격리할 수 없다.
- 공급 목록의 저장 인덱스 0이 먼저 공급된다. 화면 아래쪽이 먼저 공급되는 표현과 혼동하지 않는다.
- 기존 구조 검사는 제작 데이터 오류를 검사하며 매칭·시작 가능성을 판정하지 않는다. 오류 데이터도 에디터 저장은 허용한다.
- 7단계에서 실제 Editor·네이티브 메뉴·저장 재시작을 검증했다. 이번 단계의 새 동작은 별도 증거가 필요하다.

## 포함 범위

1. 원본 정의를 검증하고 독립된 실행 설정/상태로 옮기는 진입점.
2. 명시적 시드를 사용하는 상태별 난수와 초기 배치 후보 구성.
3. 블록·본체·덮개·먼지·바닥/연결·공급·미션의 초기 상태 보존.
4. 같은 입력의 재현, 서로 다른 실행 상태의 독립성 및 원본 불변 검증.
5. `Match` 메뉴 아래 읽기 전용 초기 보드 확인 화면과 실패 안내.
6. 실제 Unity 검증, 원본/기존 편집 기능 보존 확인 및 사용법 기록.

## 데이터와 동작 계약

### 입력과 실패

- 입력은 현재 메모리의 `LevelDefinition` 내용과 명시적인 시드다. 에셋 경로에서 몰래 다시 읽어 미저장 편집을 버리지 않는다.
- 기존 구조 검사와 실행부의 지원 버전 경계를 먼저 확인한다. null, 불명확한 점유/ID, 범위 밖 좌표 등 오류가 있으면 좌표·필드 경로가 있는 진단을 반환하며 후보를 성공으로 내놓지 않는다.
- 첫 실행 구성은 v4를 대상으로 한다. 구버전/미래 형식을 임의로 변환하지 않고 실행 구성 미지원 사유를 표시한다. 기존 에디터의 읽기·저장 지원 범위는 바꾸지 않는다.
- 에셋 집합의 레벨 번호 중복 검사는 Editor 책임으로 유지한다. 실행 코어는 `AssetDatabase`를 참조하지 않는다.
- 오류를 자동 삭제·보정하거나 원본을 저장하지 않는다. 구성 실패 후 이전 성공 후보가 최신 결과처럼 보이면 안 된다.

### 원본과 실행 상태 분리

- 실행 상태는 에셋의 가변 목록·중첩 목록을 공유하지 않는다. 기존 좌표/열거형/참조 없는 값 형식은 재사용할 수 있다.
- 보드 구성, 사용 색, 이동 횟수, 미션, 흐름과 연결, 공급 설정을 유실 없이 옮긴다. 동작 미구현이라는 이유로 정의를 버리지 않는다.
- 현재 이동 횟수는 정의 값, 미션의 진행 수는 0으로 시작한다. 목표/남은 수는 정의와 모순되지 않게 표현한다. 곰팡이 확산에 따른 목표 증가 등 진행 규칙은 아직 실행하지 않는다.
- 본체별 내구도·색·충전 목표를 보존하고 발전기 현재 충전은 0으로 시작한다. 폐가전/발전기의 네 점유 칸은 한 본체를 가리킨다. 칸별로 본체 네 개를 복제하지 않는다.
- 바닥의 먼지·중력·경로·합류·벽·통로·도착 정보와 위쪽 점유물을 분리한다. 설정 없는 중력은 아래 방향으로 해석한다.
- 공급 목록/순서/수량/종료 방식·유지 목표·생성 한도를 보존한다. 초기 구성만으로 공급 목록을 소비하거나 유지형 추가 공급을 실행하지 않는다.
- 실행 중 변화가 없는 설정은 읽기 전용으로 노출하고, 실제 상태의 변경 책임은 실행 코드 안에 둔다. 화면에서 원본 또는 실행 목록을 직접 편집하는 기능은 넣지 않는다.
- 에디터에서 원본을 바꾸어도 이미 구성된 후보는 바뀌지 않는다. 다시 구성할 때 새 내용을 반영한다. 다른 시드의 두 상태도 서로 영향을 주지 않는다.

### 초기 배치 후보 구성

아래는 이번 단계의 **후보 구성 절차 제안**이며, 낙하·공급으로 시작 보드를 안정화하는 최종 실행 절차를 대신하지 않는다.

1. 구조가 유효한 정의를 독립적으로 복사한다.
2. 비활성 칸과 장애물 본체 점유, 회수 부품, 명시한 일반/파워 블록을 반영한다.
3. `FixedNormal`의 색과 파워 종류/로켓 방향은 그대로 둔다. `RandomNormal`의 과거 고정 색 값은 무시한다.
4. 명시된 무작위 일반 칸과 아직 점유자가 없는 활성 칸에는 선택된 3~5색 중 하나를 균등 추출해 배치한다. 고정 장애물의 다른 점유 칸, 회수 부품/파워 칸, 비활성 칸을 덮어쓰지 않는다.
5. 덮개와 먼지를 별도 층으로 적용하고 아래 블록을 보존한다. 곰팡이 아래 블록을 빈칸으로 취급하거나 파워 블록에 일반 색을 부여하지 않는다.
6. 초기 상태와 시드·진단을 반환한다. 구성 도중 매칭 제거·파워 생성·피해·이동 수 소비·목표 완료를 실행하지 않는다.

4번은 초기 배치 후보를 확인하기 위한 직접 구성이다. 플레이 중 도달할 수 없는 빈칸을 직접 채우지 않는 낙하 규칙과 구분한다. 공급 경로 도달성·고정 공급 소비·초기 안정화의 실제 순서는 후속 실행 단계에서 정한다. 이 후보를 곧바로 게임 시작 상태로 쓰지 않는다.

초기 고정은 최초 위치/색 지정이며 이동 잠금이 아니다. 장애물/덮개가 주는 이동 제한과 같은 플래그로 합치지 않는다. 시작 후보에 완성 매칭이 있거나 유효 교환이 없더라도 이번 단계에서 고정 배치를 바꾸거나 재추첨하여 숨기지 않는다. 화면에는 시작 조건 미검사임을 표시한다.

### 시드와 재현

- 시드는 실행 상태별로 소유한다. `UnityEngine.Random` 같은 전역 난수 상태를 바꾸지 않는다.
- 무작위 칸의 방문 순서는 행→열 오름차순 등 고정된 순서로 정의한다. 해시 컬렉션 순회 순서나 화면 렌더링 횟수가 난수 소비를 바꾸면 안 된다.
- 같은 정의 내용·같은 시드·같은 난수 구현 버전에서 같은 초기 결과를 만든다. 서로 다른 시드가 반드시 다른 보드를 만든다는 보장은 하지 않는다.
- 기존 표준 난수 구현을 먼저 검토하고, 재현 보장 범위와 선택한 구현/버전을 기록한다. 이번에 검증하지 않은 Unity 버전·플랫폼 사이의 동일성을 주장하지 않는다.
- 같은 시드 재구성과 새 시드 생성을 구분한다. 새 시드는 화면의 실행 요청 때만 생성하고 실제 사용 값을 표시한다. repaint/선택만으로 다시 생성하지 않는다.
- 재현 자료는 레벨 내용과 시드를 함께 식별한다. 레벨이 바뀌었는데 번호와 시드만 같다는 이유로 동일 조건이라고 표시하지 않는다.
- 이번 화면은 제작자용 진단이다. 향후 플레이 봇에는 시드·숨겨진 공급/덮개 내부 상태를 공개하지 않는다. 봇 API와 저장/리플레이 시스템은 지금 만들지 않는다.

## 구조와 파일 책임 제안

```text
Assets/Scripts/
  Board/                 기존 좌표·보드 정의 유지
  Levels/                기존 v4 저장 정의·구조 검사 유지
  Simulation/            초기 구성과 독립 실행 상태
  Editor/Levels/         초기 보드 확인 창·검증 코드
```

| 역할 | 제안 타입/파일 | 책임 |
| --- | --- | --- |
| 실행 상태 | `Simulation/LevelRuntimeState.cs` | 설정 복사본과 현재 점유/내구도/진행/난수의 소유권 |
| 초기 구성 | `Simulation/LevelStateBuilder.cs` | 구조 진단, 복사, 점유 구성, 시드 적용과 결과 반환 |
| 보드/개체 상태 | 같은 폴더의 필요한 작은 타입 | 본체와 칸 참조, 일반/파워·덮개·바닥의 표현 |
| 난수 | 필요할 때 `Simulation/SimulationRandom.cs` | 상태별 난수 접근과 시드의 단일 소유 |
| Editor 확인 | `Editor/Levels/LevelInitialStateWindow.cs` | 입력/재구성/읽기 전용 표시·실패 안내 |
| 검증 | 기존 방식의 `Editor/Levels` 검증 파일 | 초기 구성·독립성·재현·실제 화면 검사 |

파일명은 책임을 설명하는 제안이며 파일 수를 완료 기준으로 삼지 않는다. 작으면 결과/값 형식을 관련 파일에 함께 둔다. `Simulation`은 이 기능의 소유 폴더이며 별도 게임명 폴더를 추가하지 않는다.

의존 흐름은 `Editor 진단 화면 → 초기 구성 → 실행 상태`, 입력 방향은 `Levels/Board 정의 → 초기 구성`이다. 실행 코어에 `UnityEditor`, `EditorWindow`, `SerializedObject`, 에셋 저장, 화면 콜백을 넣지 않는다. 게임 실행 UI·봇이 Editor 창을 거쳐야 하는 구조도 만들지 않는다.

## 초기 보드 확인 화면

- 메뉴는 `Match/초기 보드 확인`을 제안한다. 기존 레벨 에디터 메뉴·컨텍스트 메뉴·편집 버튼을 유지한다.
- 필수 입력은 레벨과 시드다. 한 줄에 관련 입력을 모으고 `같은 시드로 구성`, `새 시드로 구성`을 구분한다. 고급 옵션을 늘리지 않는다.
- 표시 내용은 레벨 번호, 사용한 시드, 구성 상태, 보드, 선택 칸의 내용과 필요한 초기 수량이다. 입력이 바뀌면 기존 후보를 지우거나 이전 입력 결과라고 명확히 표시한다.
- 라벨·색·간단한 도형으로 구분한다. 새 캐릭터 이미지가 필요하지 않으며 색만으로 종류를 구분하지 않는다. 2×2 본체, 파워 방향, 덮개 아래 내용, 바닥 정보는 읽기 전용 속성으로 확인할 수 있게 한다.
- 기존 USS의 색/간격/선택 표현을 참고하되 기존 편집 창을 대규모 리팩터링하지 않는다. 필요하지 않은 렌더링 프레임워크를 만들지 않는다.
- `초기 배치 후보 · 시작 조건 미검사 · 플레이 미지원`을 지속 표시한다. 실행/봇/난이도 버튼을 미리 만들지 않는다.
- 1000×780과 680×480에서 입력·진단·속성 접근을 확인한다. 기존 수준의 스크롤을 사용한다.

## 검증과 인수 기준

| 검사 | 확인할 결과 |
| --- | --- |
| 전체 무작위/전체 고정/부분 고정 | 선택 색만 사용하고 고정 색·파워 종류·방향 보존, 초기 고정과 잠금 구분 |
| 점유와 층 | 비활성 칸 비점유, 2×2 한 본체, 회수 부품 보존, 덮개/먼지/바닥 동시 보존 |
| 정의 복사 | 합류 목록·전선·공급 목록 등 중첩 데이터를 두 실행 상태/원본이 공유하지 않음 |
| 초기 카운터 | 이동 수·미션 목표·진행 0·충전 0·공급 순서/수량/한도 미소비 |
| 같은 입력 재현 | 반복 구성 및 별도 Unity 프로세스에서 같은 입력/시드의 의미 있는 전체 상태 비교 |
| 새 시드 | 표시 값과 사용 값 일치, 다른 상태를 만들 때 이전 상태나 전역 Unity 난수 변경 없음 |
| 실패 | null·범위/점유/ID 오류·지원 밖 버전 진단, 원본 보존, 성공한 후보로 오표시하지 않음 |
| 미검사 경계 | 시작 매칭/교환 조건 위반 후보를 성공적인 게임 시작으로 표시하지 않음 |
| 실제 화면 | 메모리의 미저장 정의 구성, 원본 수정 후 재구성, 시드 재현, 좁은 창·레벨 전환·실패 표시 |
| 보존/회귀 | 원본 JSON·dirty·파일·GUID/meta 유지, 기존 편집/저장/복제/Undo 영향 범위 회귀 |

고정 시드의 기준 예시 결과와 다른 프로세스 결과를 비교해 같은 버그를 가진 두 코드 호출만 비교하는 검사를 피한다. 성능 임계값을 임의로 만들기보다 기본 10×10에서 실제 구성 시간과 멈춤 여부를 기록한다. 실행하지 못한 검사와 플랫폼은 미검증으로 남긴다.

## 구현 순서 제안과 위험

아래는 문서 단계의 순서안이다. Goal 실행 요청 후 당시 코드와 대조해 작업 의존성·수정 책임을 목표 문서에 확정한다. 지금 구현용 에이전트나 새 Goal을 실행하지 않는다.

1. 정의→실행 상태 필드 대응표와 실패/시드 계약을 확정하고 원본 보존 기준을 기록한다.
2. 독립 상태 복사와 점유 구성을 만들고 중첩 참조·2×2·초기 카운터 검사를 수행한다.
3. 난수와 초기 후보 구성을 연결하고 고정/무작위·재현·실패 경계를 검증한다.
4. 읽기 전용 Editor 확인 화면을 연결해 실제 조작과 크기별 접근을 확인한다.
5. 별도 프로세스 재현·원본 보존·영향 범위 회귀를 마치고 증거/사용법을 기록한다.

주요 위험은 얕은 복사, 공급의 성급한 소비, 고정 배치를 이동 불가로 취급하는 것, 2×2를 여러 본체로 만드는 것, 초기 후보를 게임 시작 성공으로 오해하는 것이다. 각각 위의 직접 검사로 막는다. 기존 편집 창 공용 코드를 수정할수록 회귀 범위가 늘어나므로 첫 확인 화면은 작은 독립 창을 권장한다.

## 후속 단계

9단계 후보는 읽기 전용 매칭/교환 가능 조회와 시작 조건 검사다. 직선·ㄱ/ㄴ/T·2×2, 덮개·벽·이동 가능한 고철/회수 부품·파워 교환 예외를 함께 다룬다. 고정 배치를 유지하면서 무작위 부분만 재생성하고, 제한 내 실패와 확정 불가능을 구분하는 정책도 그때 정한다.

이후 교환과 매칭 처리 → 파워/장애물 반응 → 낙하/통로/공급 → 미션/종료 → 수동 테스트 플레이 → 관측자 봇/분석으로 나눈다. 이 순서는 후속 제안이며 각 단계의 세부 목표는 별도 문서로 확정한다.
