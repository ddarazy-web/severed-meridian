# 9단계 개발 목표 — 매칭·행동 조회와 시작 보드 조건

- 작성일: 2026-09-27.
- 상태: 2026-09-27 구현·검증 및 완료 조건별 증거 감사 완료.
- 상세 계획: [9단계 작업 계획](28_9단계_매칭조회와시작조건_작업계획.md).
- 선행: [8단계 완료 결과](27_8단계_개발목표.md).

## Goal 목표

현재 Unity 프로젝트에서 읽기 전용 매칭/가능 행동 조회, 시작 조건 검사와 고정 배치를 보존하는 제한 탐색을 구현한다. 기존 Match 초기 보드 확인 화면에 결과·근거·진단을 연결한다. 원본·v4·기존 후보 동작을 보존하고 실제 Unity 조작·독립 프로세스 재현·필요한 회귀를 검증한다.

시작 성공은 완성 매칭이 없고 유효한 **교환**이 최소 하나 있는 상태다. 제자리 파워 발동만으로 시작 성공 처리하지 않는다. 성공해도 실제 플레이·클리어 가능 판정은 아니다.

## 실행 지침

1. 상세 계획, 확정 게임 규칙, 현재 코드를 대조하고 프로젝트 지침·ponytail·관련 Unity/UI Toolkit 규칙을 따른다. 이 문서를 참조한 Goal 실행은 계획의 추천 구현·검증을 포함한다.
2. 스크립트는 Assets/Scripts/Simulation 및 Editor/Levels 아래 책임별로 유지한다. 새 게임명 폴더·패키지·asmdef·범용 프레임워크를 추가하지 않는다.
3. 기존 v4 정의/직렬화·GUID/meta·오류 데이터 저장 정책과 8단계 원시 후보 API를 보존한다. 현재 메모리의 미저장 내용을 입력으로 사용한다.
4. 매칭/행동 조회는 상태·미션·내구도·공급·난수를 변경하지 않는다. 가상 교환에서 입력을 직접 바꿨다가 복구하는 방식은 피한다.
5. 직선/ㄱ·ㄴ·T/2×2와 벽·거미줄·곰팡이·이동 가능한 고철/회수·파워 예외를 계획 표대로 다룬다. 일반 블록만 검사한 것을 전체 행동 검사로 표시하지 않는다.
6. 겹친 패턴은 구성 좌표와 분류를 보존하며 조회에서 합집합 제거 또는 동률 난수 선택을 수행하지 않는다.
7. 생성은 무작위 일반 칸만 변경한다. 초기 고정을 이동 잠금으로 바꾸거나 플레이 중 섞기 규칙과 혼동하지 않는다.
8. 시작 조건 미충족·증명된 고정 위반·전체 고정 실패·탐색 한도 도달을 구분한다. 상한 실패를 불가능한 레벨이라고 단정하지 않는다.
9. 탐색 상한의 최초 제안은 색 할당 100,000회다. 실제 비용과 최종 값을 기록하고, 시간 제한 때문에 같은 시드 결과가 달라지지 않게 한다. 진행 중 입력 변경/창 종료 후 오래된 결과를 적용하지 않는다.
10. 화면은 기존 Match 도구 안에서 원시 후보/시작 조건 구성을 구분하고 조건 통과와 플레이 미지원을 함께 표시한다. 미검사/실패를 통과처럼 보이지 않게 한다.
11. 검증은 소유한 임시 에셋으로 진행한다. Unity 실행 중 소스 변경을 피하고 실제 실행한 결과만 완료로 기록한다. 과거 검사 수를 새 검증에 합산하지 않는다.
12. 실행 전에 아래에 작업 의존성·수정 책임·검증 기준을 작성한다. 문서 작성만으로 Goal이나 구현을 시작하지 않는다.

## 착수 기록

- 2026-09-27: 현재 v4/8단계 상태와 9단계 규칙 표를 대조했다.
- 작업 순서: T1 보존 기준/조회 계약 → T2 MatchQuery → T3 ActionQuery → T4 제한 탐색 → T5 기존 UI 연결 → T6 실제 Unity/재시작/8단계 회귀 → T7 보존 감사·문서.
- 파일 책임: Simulation의 새 조회/탐색 파일, 기존 초기 확인 창 및 전용 partial/USS, Editor 검증 파일. v4 모델과 일반 레벨 편집기는 수정하지 않는다.
- 조회는 가상 교환 뷰를 사용해 원본과 난수를 유지한다. 탐색만 독립 작업 상태의 색과 난수를 변경한다.
- 기본 상한은 색 할당 100,000회. 정해진 좌표/색 셔플 순서와 작업량 제한을 사용하고 Editor에서는 작은 단위로 진행한다.
- 보존 기준: Logs/StartingBoardVerification/baseline.json. 임시 데이터는 Assets/__StartingBoardVerification_<guid> 아래만 사용한다.

## 구현 및 사용법

1. **Match → 초기 보드 확인**에서 레벨과 시드를 지정한다. 미저장 Inspector 내용도 사용한다.
2. `구성 목적`을 `원시 후보`로 두면 8단계와 동일한 후보를 구성하고 매칭·행동을 조회한다. 완성 매칭이 있어도 후보 자체는 보여준다.
3. `시작 조건 구성`은 무작위 일반 칸의 색만 탐색한다. `같은 시드로 구성`은 같은 입력을 재현하며 `새 시드로 구성`은 화면에 표시된 새 시드를 사용한다.
4. 상단에 시작 조건 결과와 매칭/유효 교환/제자리 발동 수를 표시한다. 파워 제자리 발동만 있어도 시작 조건을 통과시키지 않는다.
5. 오른쪽 매칭·행동 목록을 선택하면 관련 칸을 강조한다. 실제 교환·제거는 실행하지 않으며 클릭/재표시로 난수를 소비하지 않는다. 목록은 제한 높이 안에서 스크롤한다.
6. 레벨·시드·구성 목적·원본 내용 변경 시 이전 결과를 지우며 진행 중 검색도 취소한다. 창 종료 후 결과를 적용하지 않는다.

### 알고리즘과 경계

- `MatchQuery`/`ActionQuery`: 각각 `match-query-v1`/`action-query-v1`. 정렬된 좌표/패턴을 반환하며 가상 교환 뷰로 조회한다. 실제 상태를 바꿨다가 복원하지 않는다.
- `StartingBoardSearch`: `starting-board-dfs-v1`. 최초 원시 후보가 통과하면 그대로 반환한다. 고정 일반 칸을 제외한 일반 칸을 행/열 순서로 방문하며 색 후보를 Fisher–Yates 방식으로 섞고, 완성 매칭 분기를 버리는 깊이 우선 탐색이다.
- 색 할당 **100,000회**를 최종 상한으로 유지한다. UI는 `Advance(64)`로 나누며 벽시계 시간으로 성공/실패를 결정하지 않는다. 프레임 분할 1/64/100000에서 같은 결과·시도 수·난수 진행을 확인한다.
- 정의 오류, 고정 매칭 위반, 전체 고정 미충족, 탐색 한도 도달을 구분한다. 추가로 모든 변수 할당을 실제 소진한 경우 `Exhausted`로 표시한다. 한도 도달은 불가능 증명이 아니다.
- 실패 작업의 부분 보드는 성공 상태로 공개하지 않는다. 고정 파워·장애물·덮개·먼지·회수·흐름·연결·공급은 보존한다.
- 동일 입력 지문/시드/알고리즘/Unity·Mono 환경에서 재현한다. System.Random의 다른 런타임/플랫폼 간 동일열을 보장하지 않는다. 최종 유효 보드의 균등분포도 주장하지 않는다.

### 변경 파일 책임

- `Assets/Scripts/Features/Matching/Runtime/MatchQuery.cs`: 패턴 종류·색·좌표와 벽/덮개 판정.
- `Assets/Scripts/Features/PuzzlePlay/Runtime/Actions/ActionQuery.cs`: 교환 및 제자리 발동 허용·이유, 가능한 행동 조회.
- `Assets/Scripts/Features/PuzzlePlay/Runtime/Setup/StartingBoardBuilder.cs`: 시작 조건 보고, 단계별 제한 탐색과 실패 구분.
- 기존 `LevelInitialStateWindow.cs`, 새 `LevelInitialStateWindow.Query.cs`, `LevelInitialState.uss`: 기존 Match 화면 연결과 취소/결과/강조.
- `StartingBoardVerification.cs`, `.Edges.cs`, `.UI.cs`: 정답 예제·보존·실제 UI·독립 재시작 검증.
- 기존 `LevelInitialStateVerification.UI.cs`: 9단계부터 실제 검사를 수행하므로 고정된 ‘미검사’ 문구 대신 실제 보고와 안내의 일치를 검사한다. 기존 원시 후보 검사 의미는 유지한다.

### 비용 측정과 변경 이유

- 시드 12345, 10×10 무작위: 3색은 113회/264ms, 4색은 105회/166ms, 5색은 108회/111ms였다. 이는 해당 실행의 측정값이며 기기별 성능 보장은 아니다.
- 의도적으로 서로 인접하지 않은 변수 9칸을 두어 유효 교환이 없는 경우, 최종 상한 100000회에서 **40480ms**에 종료했다. 64회 단위 최대 처리 시간은 **55.16ms**였다. UI는 각 단위 사이에 갱신/취소를 처리한다.
- 매칭 조회는 처음에 매 칸마다 형태 회전 배열을 생성했다. 고정된 형태 목록을 재사용하고 색 불일치를 배열 생성 전에 거절하도록 바꿨으며 모든 방향 정답 예제로 재검증했다.
- 시작 조건 모드가 원시 빌더를 중복 실행하던 호출을 제거했다. 조회 목록이 속성 전체를 밀어내지 않도록 목록 높이를 제한했다.
- 상한 도달 화면 검증은 내부 테스트 한도 0을 주입했다. [limit.png](../../Logs/StartingBoardVerification/limit.png)의 0/0은 그 검사 값이며 사용자 설정이나 제품 기본값이 아니다.

검증 재실행 진입점은 `Levels.Editor.StartingBoardVerification.Data`(배치 데이터 검사), `Start`(실제 UI 포함), `Restart`(Start 후 독립 프로세스)다. Start는 GUI가 있는 Unity에서 실행하며 완료 후 종료한다. Restart가 보존 검증과 임시 에셋 정리를 수행하므로 Start 뒤에는 반드시 실행한다. 8단계 회귀는 기존 `LevelInitialStateVerification.Start`와 `Restart`를 사용한다.

로그는 `Logs/StartingBoardVerification`의 `ui-unity.log`, `restart-unity.log`, `stage8-regression-unity.log`, `stage8-restart-unity.log`에 있다. 사용자 프로젝트를 열고 있는 Unity와 동일 프로젝트의 검증 프로세스를 동시에 실행하지 않는다.

### 최종 보존과 남은 한계

- [보존 변경 목록](../../Logs/StartingBoardVerification/preservation-changes.txt)은 허용한 기존 창/USS/회귀 안내 검사와 이번 문서 변경만 포함한다. 레벨 데이터·기존 meta/GUID·Packages·ProjectSettings는 baseline과 동일하다.
- 별도 사용자 요청으로 작성한 10단계 문서와 목차 링크는 유지했다. 10단계 구현은 수행하지 않았다.
- 소유한 검증 에셋 폴더와 대기 state.json, 검증 Unity 프로세스가 남아 있지 않음을 확인했다.
- 실제 교환·제거·파워 효과·낙하·공급·미션·봇·난이도 분석은 미지원이다. 시작 조건 통과는 클리어 가능성 판정이 아니다.
- Android/iOS/다른 런타임의 성능·동일 난수열은 검증하지 않았다. 실제 플레이의 파워 생성 위치·동률 선택·피해 규칙도 이번 읽기 전용 조회의 완료 범위에 포함하지 않는다.
