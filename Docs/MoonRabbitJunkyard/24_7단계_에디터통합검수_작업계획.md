## 목표와 단계 선정 이유

현재 에디터로 레벨을 만들고 수정·검사·복제·저장하는 제작 동선을 끝까지 검증한다. 개별 기능이 동작하는 것에 더해, 서로 다른 도구를 연속 사용해도 선택·오류 안내·Undo·미저장 데이터가 일관되게 유지되는지 확인한다. 재현된 결함만 수정하고 실제 작업에 필요한 사용 안내를 남긴다.

최초 계획의 6~7단계는 공통 편집·복제·연결 수정·통합 검수다. 연결 수정은 4단계, 공통 편집과 복제는 6단계에서 구현했다. 이번 단계는 남은 통합 검수로 에디터 제작 기능의 인수 기준을 닫는다. 이미 통과한 단위 검사를 무조건 반복하거나 기능을 다시 구현하지 않는다.

**완료 의미는 레벨 제작 도구의 통합 검수 완료다.** 구조 검사 통과를 실제 플레이 가능·클리어 가능·적정 난이도 판정으로 바꾸지 않는다.

## 확인된 현재 상태

- `LevelDefinition` 저장 형식은 v4다. 초기 배치·장애물·덮개·먼지·흐름·연결·공급·회수·미션을 저장한다.
- `LevelEditorWindow.Validate()`는 기존 규칙 검사와 레벨 번호 중복 검사를 함께 호출한다. 좌표/공급 항목/흐름·연결/미션 오류로 이동하는 동선과 오래된 결과 거절이 있다.
- `LevelBoardView`, 선택 패널, 흐름 오버레이, 공급 목록이 한 창에서 상태를 공유한다. 개별 도구보다 도구 전환 경계가 이번 검수의 중심이다.
- `LevelEditorContextMenu`는 복사·붙여넣기와 기존 버튼 작업을 제공한다. 공급 행 우클릭 선택, 선택 변경 후 메뉴 거절, 드래그와 우클릭 구분이 구현되어 있다.
- 단계별 데이터·실제 UI·별도 재시작 검증 코드가 있다. 최근 메뉴 확장 관련 220개 통과 기록은 선행 증거이며 이번 단계 완료 증거로 자동 승계하지 않는다.
- 실제 낙하·공급 소진·매칭·효과·미션 진행·플레이 봇은 구현 범위 밖이다.

통합 경계에 결함이 있다는 것은 아직 확인되지 않았다. 아래 항목은 검수 대상이며 구현된 버그로 단정하지 않는다.

## 범위와 대안

| 대안 | 장점 | 비용/위험 | 판단 |
| --- | --- | --- | --- |
| 기존 결과만 모아 바로 종료 | 가장 적은 작업 | 여러 도구를 연속 사용하는 과정과 네이티브 메뉴 표시 증거가 부족할 수 있음 | 기존 결과는 참고 자료로 사용 |
| 대표 제작 동선 검수 후 발견된 결함만 수정 | 기존 구현을 활용하고 수정 범위를 제한 | 실제 Editor 조작·별도 재시작 필요 | 추천 |
| 런타임 실행부와 테스트 플레이를 동시에 개발 | 다음 기능을 빨리 시작할 수 있음 | 매칭·공급·중력 실행 규칙까지 범위가 크게 늘어남 | 후속 별도 계획 |

포함 범위는 대표 통합 시나리오, 오류 안내와 수정 동선, 버튼/컨텍스트 메뉴의 동작 일치, 선택 수명, Undo/Redo, 저장·복제·재시작, 실제 창 사용성 및 사용 안내다. 새 기능은 인수 조건을 충족하지 못하는 기존 동선을 고치는 데 필요한 최소 변경만 허용한다.

제외 범위는 새 장애물·새 게임 규칙, 다중 삭제/이동·영역 복사, 대규모 UI 재설계, 자동 레벨 추천, 초기 보드 생성/첫 교환 판정, 실제 플레이·부스터·봇·난이도 분석, 서버·결제·광고·아트다. 자동 검사 프레임워크·명령 버스·새 패키지를 만들지 않는다.

## 대표 통합 시나리오

### A. 신규 제작 → 검사 → 저장 → 재열기

1. 기존 Match 레벨 에디터에서 새 레벨을 만들고 번호·색·이동 횟수·활성 영역을 설정한다.
2. 일반/파워 블록, 장애물/덮개/먼지, 중력·경로·통로·연결, 생성구/고정 공급 목록, 회수·미션을 기존 허용 조합으로 구성한다.
3. 하나의 레벨에 충돌하는 모든 기능을 억지로 넣지 않는다. 고정 공급과 유지 공급처럼 함께 사용할 수 없는 경우는 별도 임시 레벨로 분리한다.
4. 카테고리·층·탭을 전환하고, 사용 중 목록에서 대상으로 이동하여 수정한다. 오류가 없는 구조 검사 결과와 미지원 검사 안내를 확인한다.
5. 명시적으로 저장하고 창을 다시 연다. 별도 Unity 프로세스에서 전체 직렬화 값·GUID·공급 순서·내부 연결을 비교한다.

완료 증거: 실제 UI 조작, 저장 직전 전체 값, 재시작 후 비교, 대표 화면. 검수용 데이터는 임시 픽스처이며 플레이용 밸런스 데이터로 배포하지 않는다.

### B. 오류 발견 → 해당 대상 이동 → 수정 → 재검사

기존 검사기로 검출되는 오류 중 다음 대표 경로를 다룬다.

| 오류 대상 | 확인할 동선 |
| --- | --- |
| 미사용 색/배치 충돌/내구도 | 올바른 편집 층·칸·본체로 이동하고 수정 |
| 고정 공급 항목 | 정확한 생성구·목록 항목 선택과 해당 속성 표시 |
| 미완료 통로/발전기 연결 | 해당 칸·경로·연결 강조 및 기존 편집 도구로 수정 |
| 미션 수량/회수 공급 부족 | 레벨 설정의 관련 미션·공급 설정 확인 |
| 중복 레벨 번호 | 충돌 이유와 상대 에셋 식별, 번호 수정 후 재검사 |
| 보드 밖 좌표/유일하지 않은 배치 | 임의 대상을 고치지 않고 이유·원본 필드 경로 안내 |

수정 후 오래된 검사 결과가 최신 결과인 것처럼 남지 않는지 확인한다. 이전 결과를 클릭했을 때 다른 대상을 수정/선택하지 않아야 한다. 읽기·검사·오류 이동으로 자동 정규화하거나 원본을 저장하지 않는다.

현재 UI에서 안전하게 수정할 수 없는 손상 데이터는 원본 Inspector의 해당 필드로 안내하는 기존 경계를 유지한다. 모든 손상 데이터 전용 복구 도구를 추가하지 않는다.

### C. 연속 편집 → 취소/Undo → 복제 → 원본 보존

- 여러 층/종류 선택, 혼합 속성, 설정 붙여넣기와 생성구 공급 붙여넣기의 서로 다른 적용 정책을 확인한다.
- 기존 버튼과 컨텍스트 메뉴에서 대표 작업 결과와 Undo 단위를 비교한다. 삭제는 현재 제공하는 범위만 사용한다.
- 공급 행 우클릭·복제·순서 변경·삭제, 2×2 이동, 흐름/연결 편집 뒤 층·도구·레벨 전환을 연속 수행한다.
- 메뉴 열림 이후 원본/선택 변경, 외부 Inspector 변경, Undo/Redo, Esc·포커스 이탈·창 닫기 뒤 오래된 콜백과 미완료 드래그가 적용되지 않는지 확인한다.
- 미저장 원본을 복제한다. 새 번호/GUID 외 모든 값과 내부 연결 보존, 원본 JSON/GUID/dirty 보존, 사본 변경의 독립성을 확인한다.
- 불완전/오류 데이터도 명시적으로 저장할 수 있어야 한다. 취소·충돌·실패로 원본 파일을 덮어쓰지 않는다. 구버전/미래 형식의 기존 지원·거절 경계를 유지한다.

## 실제 UI 인수 기준

- Match 메뉴, 왼쪽 카테고리/탭, 한 줄 제목·드롭다운, 오른쪽 탭, 기존 USS 스타일을 유지한다.
- 기준 창 1000×780과 좁은 창 680×480에서 중요한 버튼·속성이 잘리거나 접근 불가능하지 않아야 한다. 기존 스크롤을 사용한다.
- 네이티브 우클릭 메뉴를 실제로 열어 항목·하위 메뉴·비활성 상태·행 대상 선택을 확인한다. 메뉴 이벤트/액션 자동 검사와 네이티브 표시 검사를 구분해 기록한다.
- 현재 대상에 해당하는 기능만 노출한다. 새 메뉴를 늘리는 것이 이번 단계의 목표가 아니다.
- 대상을 선택하지 않거나 잘못된 데이터를 열어도 예외 없이 안내한다. 사용법에는 구조 검사 범위와 현재 테스트 플레이 미지원 상태를 명확히 적는다.

## 실행 순서 제안

1. 최신 구현/선행 증거와 위 인수 기준을 대조하고 중복 검사와 미검증 경계를 구분한다. 변경 전 원본·사용자 파일 기준을 기록한다.
2. 임시 레벨로 A/B/C를 실제 조작해 재현 가능한 실패를 수집한다. 발견 사항마다 영향·기대 결과·최소 수정 범위를 기록한다.
3. 실패를 먼저 재현하는 검사나 조작 절차를 확보한 뒤 수정하고 같은 경로를 재검증한다. 실패가 없으면 임의의 리팩터링을 하지 않는다.
4. 넓은/좁은 창과 실제 메뉴 표시를 확인하고, 명시적 저장 후 별도 프로세스에서 데이터/GUID 보존을 검사한다.
5. 변경된 경계의 기존 회귀만 실행한다. 공유 창/선택 코드를 바꾸면 관련 배치·흐름·공급·공통 편집을 포함한다. 새 증거가 없으면 같은 검사를 계속 반복하지 않는다.
6. 실제 사용 순서와 완료 조건별 증거·제한을 기록하고 소유한 임시 에셋·대기 상태만 정리한다.

이 문서를 참조한 실행 요청 후 목표 문서에 실제 작업 의존성과 수정 파일을 확정한다. 공유 Editor 상태를 다루므로 기본은 순차 작업이며 문서 작성만으로 구현·Goal·에이전트를 시작하지 않는다.

## 완료 후 다음 방향

7단계 인수 기준을 충족하면 공통 게임 실행부를 별도 설계한다. 우선 후보는 원본과 분리한 실행 상태·재현 가능한 시드·초기 보드 구성이다. 이후 매칭/효과/낙하·공급/미션 실행을 필요한 의존성에 맞춰 나누고 수동 테스트 플레이를 연결한다. 봇은 사용자와 같은 관측·입력 계약을 사용하는 별도 구조로 유지한다. 이 순서는 후속 제안이며 이번 문서로 런타임 설계를 확정하지 않는다.
