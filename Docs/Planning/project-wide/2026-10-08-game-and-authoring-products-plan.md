# 게임·Windows 제작 도구 분리 — 6단계 통합 계획

> 2026-10-08 · 통합 계획 / 1~5단계 구현·검증 완료, 6단계 진행 중
> 2026-10-08 추가 요청으로 네 제품의 Build Profile 및 제품 심볼을 먼저 생성했다. 공통 실행 진입과 시험 상태 격리(1단계)를 구현·검증했으며, JSON 기반(2단계) 구현·검증을 완료했고 공통 편집과 기존 창의 JSON 작업 모드(3단계)도 구현·검증했다. 2026-10-09 공통 레벨툴 기본판과 실제 게임 시험(4단계)을 Unity Play Mode에서 검증했다. 2026-10-09 고급 기능과 기본 편집 화면 전환(5단계)을 검증 완료했으며 제품 연결/전체 이관(6단계)의 구조·데이터·프로필 검증까지 완료했다. 실제 배포 빌드·실기 실행은 별도 승인 후 검증할 게이트로 남는다. 실제 빌드는 수행하지 않았다.
> 실행 담당은 각 단계 상세 계획 확정 후 superpowers:executing-plans로 순차 진행한다. 필요하면 하위 에이전트를 사용할 수 있다. Player/Addressables 빌드·커밋·푸시는 하지 않는다. HTML 매뉴얼은 별도 요청 전까지 갱신하지 않고, 질문은 제한시간 없는 일반 채팅 문답으로 진행한다.

**Goal:** 하나의 Unity 프로젝트에서 Android 게임, iOS 게임, Windows Steam 게임, Windows 레벨 제작 도구를 분리 구성하고, 동일한 데이터·퍼즐 로직을 사용하여 제작과 플레이 시험을 수행한다.

**Architecture:** 콘텐츠 문서·검증·편집 기능·퍼즐 실행을 공유하고 제품별 시작 과정·화면·저장·서비스 연결을 분리한다. 제작 원본은 JSON, 게임 배포 입력은 기존 MemoryPack을 유지한다. Unity 안의 기존 레벨 에디터는 전환 검증 전까지 유지한다. 레벨툴 씬이 완성되면 Unity에서도 같은 씬을 기본 편집 화면으로 사용하고, 기존 창은 공통 씬을 여는 진입 역할로 축소한다.

**Tech Stack:** 현재 Unity/C#, MemoryPack, Addressables, Unity Build Profiles. 독립 도구도 Unity 실행 앱이다. 공통 데이터·편집 기능에 UnityEditor 의존성을 허용하지 않는다. 도구 UI 방식과 필요한 asmdef 경계는 첫 단계의 기술 확인으로 결정하며, 실제 사용 없이 빈 계층을 만들지 않는다.

**Spec:** 사용자 확정 방향 — 단일 프로젝트, Android 게임·iOS 게임·Steam 게임·Windows 편집 도구 분리, 게임 로직 공유, JSON 제작 원본. 기존 [JSON 전환 계획](2026-10-08-json-authoring-transition-plan.md)의 데이터 계약을 포함한다.

## 1. 계획의 크기와 기존 계획 관계

전체는 **6단계**로 진행한다. 기존 JSON 5단계를 추가로 수행하는 11단계 계획이 아니다.

| 이번 단계 | 큰 결과 | 기존 JSON 계획과 관계 |
|---|---|---|
| 1 | 제품 경계·공유 실행 진입 정리 | 데이터와 실행 의존 경계 확정 |
| 2 | JSON 읽기·쓰기·이관 기반 | 기존 1단계 및 정의·카탈로그 저장 기반 |
| 3 | 공통 편집 기능 + 기존 에디터 JSON 전환 | 기존 2·3단계 |
| 4 | Windows 도구 기본 제작·플레이 시험 | 신규 독립 앱의 첫 사용 가능 구간 |
| 5 | 튜토리얼·공급·고급 검사 등 기능 완성 | 기존 에디터 기능 대조 및 이식 |
| 6 | 네 제품 프로필·콘텐츠 파이프라인·전체 이관 검수 | 기존 4·5단계 + 제품별 분리 검증 |

단계마다 2~3개의 내부 작업 묶음으로 구현/검증한다. 내부 작업 하나마다 새 번호의 계획서를 생성하지 않는다. 반대로 한 단계가 끝나기 전까지 결과를 전혀 확인할 수 없는 대규모 일괄 수정도 피한다.

## 2. 확인한 현재 상태

- 전역 빌드 씬 목록에는 PuzzleGame 씬이 활성화되어 있다. Assets/Settings/BuildProfiles에 네 제품의 프로필과 전용 심볼을 생성했다. 게임 프로필은 현재 PuzzleGame 씬을 사용하며, 레벨툴 프로필은 4단계에서 LevelTool 씬을 연결했다. 제품별 실행 기능과 콘텐츠가 이미 분리된 상태로 간주하지 않는다.
- PuzzleGameSession은 번호 기반 로딩 외에 LevelDefinition 사본·시드·취소 토큰을 받는 InitializeAsync 진입점이 있다. 사본 소유권과 해제 책임도 정의되어 있다.
- 현재 실제 게임 진입 도구인 PuzzleEditorLauncher는 EditorApplication, SessionState, EditorSceneManager에 의존한다. 독립 앱에서 그대로 사용할 수 없다.
- 레벨 편집 화면과 저장은 EditorWindow, SerializedObject/Property, AssetDatabase 및 Unity Undo에 연결되어 있다.
- 매칭·낙하·피해 등 실행은 Features/PuzzlePlay의 실행 코드와 게임 세션을 통해 수행한다. 공유 가능 범위는 실제 호출 관계를 더 확인하여 정하며 순수 .NET이라고 단정하지 않는다.
- 현재 제작 SO·JSON 이관 위험과 팩 생성 경로는 기존 JSON 계획에 기록되어 있다.
- Steam SDK·광고·결제·저장 시스템의 제품별 완성 상태는 이번 조사로 확인하지 않았다. 1단계 목록화 대상이다.

## 3. 목표 구조

    공통 콘텐츠 문서·JSON 저장·ID 참조 검사
                        │
                공통 편집 기능
                        │
                공통 레벨툴 씬
                 ┌──────┴──────┐
          Unity 내 레벨 편집   Windows 제작 도구
                 └──────┬──────┘
                     플레이 시험
                        │
             공통 퍼즐 실행·보드·게임 연출
                        │
             Android / iOS / Steam 게임

최종 전환 뒤 기존 '레벨 편집' 메뉴는 공통 레벨툴 씬을 연다. 기존 EditorWindow와 레벨툴 씬에 편집 기능을 각각 추가·유지하지 않는다. 전환 전 기존 창은 기능 대조와 안정적인 제작을 위한 임시 경로로 유지한다.

### 책임과 의존 방향

| 영역 | 책임 | 허용하지 않는 의존 |
|---|---|---|
| 콘텐츠 문서·저장 | JSON 모델, 버전, 안정 ID, 파일 읽기/쓰기, 참조 검사 | UnityEditor·에셋 객체 참조 |
| 공통 편집 기능 | 배치·교체·영역 편집·변경 이력·조건 조립 | EditorWindow, Unity Undo, 특정 UI |
| 공통 퍼즐 실행 | 매칭·낙하·피해·파워·미션·튜토리얼 | 도구 UI, Steam/모바일 서비스 |
| 공통 표현 | 보드·애니메이션·입력 결과·게임 HUD | 제작 파일의 직접 수정 |
| 제품 시작 구성 | 필요한 서비스/입력/데이터 공급자 연결 | 제품 선택을 곳곳에서 암묵적으로 추측 |
| Unity 편집 어댑터 | AssetDatabase, 기존 UI/Undo, 구형 가져오기 | Windows 앱으로의 역방향 의존 |
| Windows 도구 화면 | 문서 목록·파일 선택·속성 편집·시험 제어 | UnityEditor API |

공통 퍼즐 실행·표현에서 합리적인 UnityEngine 의존은 허용한다. 이번 목표는 Unity 실행 앱 네 종류의 분리이며 게임 전체를 순수 .NET으로 재작성하는 것이 아니다.

기능 중심 폴더는 유지한다. 신규 도구는 Features/LevelAuthoring 같은 담당 영역에 묶고, 제품 시작/선택은 작은 별도 영역으로 둔다. 실제 분리할 기능에만 필요한 어셈블리 경계를 추가하며 기존 스크립트를 일괄 이동하지 않는다.

### 상태 소유와 플레이 시험

- 편집 원본 문서와 플레이 시험 상태를 분리한다.
- 시험 시작 때 문서·정의·표현 설정의 일관된 사본과 시드를 전달한다.
- 시험은 기존 실행 로직을 사용한다. 시험 종료 시 사본/리소스를 정리하고 편집 선택·카메라·미저장 상태로 돌아간다.
- 시험 결과가 원본 레벨 배치나 일반 게임의 진행·아이템·학습 완료 기록에 쓰이지 않게 한다.
- 도구의 시험 저장소는 도구 전용이다. 제품명만 다르게 설정하는 데 의존하지 않고 저장 경로와 서비스 연결도 명시한다.
- 도구 플레이는 배포용 팩 재생성 없이 현재 문서로 실행할 수 있어야 한다. 배포용 팩 확인은 별도 모드다.

### 화면 재사용 범위

최종 편집 화면은 Unity와 Windows 독립 앱이 함께 사용하는 레벨툴 씬 하나로 통합한다. 기존 Unity EditorWindow의 화면을 그대로 exe에 넣지는 않는다. 데이터·편집 동작·검증·게임 표현을 공유하고 파일 선택/입력/창 관리 등의 환경 연결만 대체한다.

도구 UI는 1단계에서 런타임 UI Toolkit의 기존 편집 UI 재사용 가능성과 현재 게임 UI 연결 비용을 비교해 결정한다. 보드/입력/긴 속성 목록의 대표 구간을 먼저 확인하고 전 화면을 한 번에 새로 만들지 않는다. 기존 게임 프리팹의 시각 디자인 변경은 이 계획에 포함하지 않는다.

## 4. 제품 분리 규칙

프로필 이름과 전용 심볼은 생성 완료했다. 아래 GameBootstrap/AuthoringBootstrap 시작 구성은 후속 단계의 목표이며 아직 생성하지 않았다. 현재 설정과 제한은 [빌드 프로필 준비 기록](../../Verification/project-wide/2026-10-08-product-build-profiles.md)을 참조한다.

| 제품 | 플랫폼 | 시작 구성 | 전용 코드/서비스 | 데이터 |
|---|---|---|---|---|
| Android Game | Android | GameBootstrap → 게임 | 모바일 입력·해당 플랫폼 서비스 | MemoryPack·게임 리소스 |
| iOS Game | iOS | GameBootstrap → 게임 | 모바일 입력·해당 플랫폼 서비스 | MemoryPack·게임 리소스 |
| Windows Steam Game | Windows | GameBootstrap → 게임 | PC 입력·Steam 어댑터 | MemoryPack·게임 리소스 |
| Windows Level Editor | Windows | AuthoringBootstrap → 제작 화면 → 시험 | 파일 작업·편집·검사 | JSON 작업 폴더·표현 리소스 |

- 플랫폼 조건과 제품 조건을 구분한다. Windows라는 이유로 Steam 초기화를 실행하지 않는다.
- 프로필별 제품 심볼은 정확히 하나를 선택하도록 검사한다. 예: PRODUCT_ANDROID_GAME / PRODUCT_IOS_GAME / PRODUCT_STEAM_GAME / PRODUCT_LEVEL_EDITOR.
- 제품 선택은 시작 구성과 빌드 포함 경계에서 처리한다. 핵심 매칭/피해 코드에 제품별 분기를 흩뿌리지 않는다.
- 프로필 씬 목록만 믿지 않는다. asmdef 조건, 플러그인 호환 설정, Resources/StreamingAssets, Addressables와 직접 참조도 검사한다.
- Unity Build Profile과 Addressables Profile은 별개다. 하나의 제품 선택 명령이 적절한 콘텐츠 설정/출력 경로를 명시적으로 선택하고 검증하도록 연결한다.
- Addressables Profile이 자동으로 불필요한 그룹을 제외한다고 가정하지 않는다. 그룹 포함 규칙과 카탈로그/출력 경로를 별도로 정한다.
- Android 번들을 Windows 도구에 재사용하지 않는다. 동일한 리소스 원본에서 대상 플랫폼에 맞는 산출물을 만든다.
- 두 Windows 제품의 캐시·콘텐츠 카탈로그·로그·저장·출력 경로를 구분하여 서로 덮어쓰지 않게 한다.

## 5. 단계별 작업과 완료 기준

### 1단계 — 제품 경계와 공통 플레이 진입 확보

**결과:** 제품별 시작 구성과 공유할 기능이 정리되고, 기존 게임 동작을 유지하면서 시험 입력/저장 경계를 검증할 수 있다.

- [x] 현재 에디터 기능·실행 코드·저장·서비스·리소스 의존을 목록화한다. 필수 기능/후속 기능과 실제 신규 작업량을 확정한다.
- [x] 공통 레벨 입력, 시드, 튜토리얼 모드, 취소·종료 결과, 사본 소유권을 명시한 플레이 진입 계약을 마련한다. 기존 게임 세션의 초기화 경로를 재사용한다.
- [x] 정식 게임/시험 세션 저장과 서비스 구성을 분리하고 기존 Unity 에디터 시험을 같은 계약에 연결한다.
- [x] 도구 UI 기술과 필요한 최소 어셈블리 경계를 대표 화면으로 확인한다. 이 결과는 이후 구현의 기준으로 기록한다.

**검증:** 같은 입력·시드·행동의 기존/새 진입 결과 비교, 실패·취소·반복 진입의 리소스 정리, 시험 전후 일반 게임 저장 불변.
**하지 않음:** 전 화면 이식, 전체 JSON 이관, Steam 서비스 신규 구현.

완료 근거: [1단계 기록](../../Verification/project-wide/game-authoring-stage-01-progress.md). 다음 작업: [2단계 계획](game-authoring-stage-02-plan.md).

### 2단계 — JSON 콘텐츠 기반과 안전한 변환

**결과:** Unity 밖에서 다룰 수 있는 문서 형식으로 실제 콘텐츠를 손실 없이 저장·읽기 가능.

- [x] 기존 JSON 계획의 문서 종류·ID·버전·상대경로·기획 출처·공유 구성 계약을 확정한다.
- [x] 레벨·요소·표현·카탈로그·공통 튜토리얼·샘플·모양의 JSON 저장과 기존 입력 변환을 구현한다.
- [x] 구형 SO 원본을 변경하지 않는 내보내기, 안정 ID 대응표, 저장 중단 복구·외부 수정 충돌 검사를 구현한다.
- [x] 대표 자료로 JSON→공유 실행 입력까지 연결한다. 자동 양방향 동기화는 도입하지 않는다.

**검증:** 문서 종류별 왕복, 미지원 버전/없는 참조/중복 ID/잘못된 경로, Unicode 경로, 저장 실패, Unity 없는 문서 파싱·참조 검사.
**하지 않음:** 제작 원본 전체 교체, 영구 SO 자동 재생성, Windows UI 완성.

완료 근거: [2단계 검증 기록](../../Verification/project-wide/game-authoring-stage-02-progress.md). 다음은 [3단계 계획](game-authoring-stage-03-plan.md)이며 자동 착수하지 않는다.

### 3단계 — 공통 편집 기능과 기존 에디터 JSON 연결

**결과:** 현재 Unity 안의 에디터에서 JSON을 실제로 편집하고 게임 테스트할 수 있음.

- [x] 파일 작업·배치·교체·이동·복제·영역 선택·미션/공급 편집에서 UI와 데이터 변경을 분리한다.
- [x] 공통 편집 세션이 문서·선택·미저장·취소/되돌리기 상태를 소유하게 한다. 기존 Undo와 새 변경 이력을 동시에 중복 적용하지 않는다.
- [x] 기존 화면을 공통 편집 기능에 연결하고 레벨 선택·새 파일·저장·복제·재열기 기능을 JSON에 연결한다.
- [x] 튜토리얼 공통 흐름·레벨별 값·내 샘플·모양 저장을 동일 저장소로 연결한다. 세부 UI는 기존 화면을 유지한다.

**검증:** 대표 편집 작업 전후 결과 비교, Undo/Redo·재시작·미저장·공유 영향·외부 수정 충돌, 편집 자료로 실제 게임 진입.
**경계:** 임시 SO 어댑터가 남을 수 있으나 외부 도구의 공통 편집 API에 노출하지 않는다. 순수 저장 계약과 Unity 실행 입력 어댑터는 구분한다.

### 4단계 — Windows 도구의 기본 제작·플레이 시험

**결과:** Unity Play Mode에서 독립 앱용 화면으로 “열기 → 편집 → 시험 → 복귀 → 저장”을 수행하는 첫 사용 가능 버전.

- [x] 실행용 제작 시작 씬과 UI를 만들고 공통 편집 세션에 연결한다. 같은 씬을 Unity에서도 열어 편집·시험할 수 있게 하고 기존 레벨 편집 메뉴/창에서 해당 씬으로 진입하는 경로를 제공한다. 기본판 단계에서는 기존 창을 유지한다.
- [x] JSON 작업 폴더/레벨 목록/새로 만들기/열기/저장/기본 보드 편집/요소 속성/기본 미션/Undo를 제공한다.
- [x] 공통 게임 세션·보드 연출로 실제 플레이 시험하고 원래 편집 상태로 돌아오게 한다.
- [x] 기본 표현 리소스 카탈로그를 앱에서 읽게 한다. Unity AssetDatabase가 없어도 동작하도록 연결한다.

**검증:** Editor 전용 API 참조 없는 런타임 코드 경계, 제작→시험 반복, 원본/게임 저장 불변, 실패·취소·누락 리소스 처리.
**주의:** 빌드 금지 유지 중에는 “배포 가능한 exe 검증 완료”라고 보고하지 않는다. 실행용 코드와 씬을 Editor Play Mode에서 검증한 상태로 구분한다.

### 5단계 — 고급 제작과 검사 기능 완성

**결과:** 합의한 기존 레벨 에디터의 제작·시험 기능을 Windows 도구에서도 사용할 수 있음.

- [ ] 튜토리얼 단계 조립·대상 선택·공통 구성·레벨별 값·샘플·논리 재생을 연결한다.
- [ ] 고정 공급·생성구·연결/흐름·2×2 요소·맵 모양·여러 레벨 작업 등 기본판에서 빠진 제작 기능을 연결한다.
- [ ] 자동 플레이·반복 시험·결과/난이도 확인은 기존 실행 로직을 사용하여 연결한다. UnityEditor에 묶인 검사 실행기·기록 경로는 환경 어댑터로 분리한다.
- [ ] 1단계 기능 목록과 대조하여 누락을 기록하고, 필요한 기존 기능을 말없이 후속으로 미루지 않는다. 필수 기능 동등성과 파일 저장·미저장 상태 보호·시험 복귀를 검증한 뒤 Unity의 기본 레벨 편집도 레벨툴 씬으로 전환한다. 기존 창의 중복 편집 UI는 제거/비활성화하고 필요한 씬 실행·구형 가져오기 어댑터만 남긴다.

**검증:** 같은 문서·시드·행동에서 기존 Unity 제작창과 공통 레벨툴 씬의 배치/조건/논리 결과 동등성. Unity Play Mode에서 편집한 내용은 명시 저장한 JSON에 유지되고, 미저장 상태에서 종료/씬 이동할 때 경고·취소·저장 선택으로 유실을 막는다. 봇·통계는 동일 설정으로 비교하고, 사람이 클리어 가능하다는 보증과 구분한다.
**진행 단위:** 제작 기능 완성 / 검사 기능 연결 두 묶음으로 진행한다. 테스트 스크립트 자체를 앱에 넣는 것이 아니라 필요한 제품용 검사 기능을 분리한다.

### 6단계 — 제품 프로필·팩 파이프라인·최종 이관

**결과:** 네 제품을 명시적으로 선택하는 구성과 일관된 콘텐츠 생성 경로를 갖추고, JSON을 기본 제작 원본으로 채택할 준비를 마침.

- [ ] 네 Build Profile의 플랫폼·씬·제품 심볼·지원되는 Player Settings·출력 폴더를 구성한다.
- [ ] 게임/도구 모듈·플랫폼 서비스·네이티브 플러그인·리소스 포함을 제품별로 검사한다.
- [ ] JSON→검증→공통 튜토리얼 해석→MemoryPack→Addressables 입력을 연결한다. 기존 50레벨 구간과 호환 로더를 유지한다.
- [ ] 전체 데이터 이관을 임시 경로에서 먼저 검증하고 정상 스냅샷만 기본 원본으로 전환한다. 기존 SO는 복구 자료로 보존한 뒤 활성 원본에서 제외한다.
- [ ] 씬 직접 참조·Resources·StreamingAssets·Addressables·사전 로드 객체에 제작 원본/불필요한 도구 리소스가 섞이지 않는지 확인한다.
- [ ] 승인된 시점에만 실제 제품 빌드·별도 PC/Android/iOS 실행을 검증한다. 출시/업로드는 별도 업무로 남긴다.

**검증:** 50/51·100/101 경계, 팩/정의 일관성, 교체 중 실패 복구, 제품 심볼 충돌, 잘못된 플랫폼 플러그인, 게임/도구 저장 격리, 깨끗한 환경에서 재생성.
**완료 상태 구분:** 빌드 금지 중에는 “구조·프로필·데이터 검증 완료 / 실제 배포 빌드 검증 대기”로 보고한다. 네 제품 산출물의 실제 실행을 확인하기 전까지 전체 출시 준비 완료로 표현하지 않는다.

## 6. 단계 사이의 원본·배포 정책

- 1~2단계: 기존 SO가 기존 제작의 기준이다. JSON 변환은 별도 시험 자료다.
- 3~5단계: 명시적으로 선택한 JSON 작업 폴더는 JSON만 원본이다. SO와 자동 병합하지 않는다.
- JSON 시범 모드에서 옛 SO를 읽어 배포 팩을 생성하지 않도록 차단한다. 팩 변환이 연결되기 전에는 현재 편집 자료로 시험한다.
- 6단계: 전체 참조/동작 동등성이 확인된 자료만 기본 JSON 원본으로 전환한다.
- 런타임 게임은 MemoryPack 사용을 유지한다. 도구의 시험은 문서 사본을 사용하며, 필요 시 팩 입력 시험을 별도로 제공한다.

## 8. 이번 범위에서 확장하지 않는 것

- 프로젝트를 Android/iOS/Steam/도구용으로 복사하여 각각 유지하지 않는다.
- 매칭·피해·드론·튜토리얼 실행을 도구용으로 다시 구현하지 않는다.
- Steam 상점 등록·결제·업적·클라우드 저장 전체 구현, 모바일 신규 서비스 구축은 이 구조 계획의 완료 조건이 아니다. 존재하는 연동은 분리하고 미구현 서비스는 명시한다.
- JSON 파일로 임의 신규 이미지/프리팹까지 실행 중 가져오는 기능은 포함하지 않는다. 새 시각 리소스 배포는 기존 Unity 콘텐츠 경로를 사용한다.
- 외부 앱에서 Unity AssetBundle이나 Addressables 빌드를 실행하는 기능은 포함하지 않는다. 제작은 도구, 검증·팩/콘텐츠 변환은 Unity 파이프라인이 담당한다.
- 협업 서버·실시간 공동 편집·웹 편집기·자동 업데이트·설치 프로그램·매뉴얼 HTML 갱신은 별도 요청 범위다.

## 9. 운영과 다음 착수

- 6단계 큰 틀을 유지하고 후속 상세 계획은 해당 단계 직전에 만든다.
- 각 단계는 결과를 확인할 수 있는 내부 작업 2~3묶음으로 진행한다.
- 단계 완료 보고에는 변경·검증·남은 제약과 다음 단계 계획/목표/복사 가능한 실행문을 포함한다. 마지막에 실제 변경을 요약한 커밋 메시지를 복사 가능한 코드 블록으로 제공하되 커밋·푸시는 실행하지 않는다.
- 1단계 [계획서](game-authoring-stage-01-plan.md)·[목표](../../Goals/project-wide/game-authoring-stage-01-goal.md)·[실행문](../../Commands/project-wide/game-authoring-stage-01-command.md)을 작성했다. 1~6단계의 승인된 구조·데이터·Unity 검사 범위를 완료했다. 최종 근거는 [6단계 검증 기록](../../Verification/project-wide/game-authoring-stage-06-progress.md)을 따른다. 배포 빌드는 자동 실행하지 않는다.
- 계획이 바뀌면 영향받는 단계와 계약만 수정하며 아직 실행하지 않을 모든 세부 문서를 미리 작성하지 않는다.
