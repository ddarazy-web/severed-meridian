# 제품 빌드 도구 — 3단계 통합 계획

> 2026-10-15 최초 계획 · 2026-10-16 3단계 공통 옵션 구조·모의/재로드/조회 회귀 검사 완료
> 구현 담당: 단계별 상세 계획에 따라 `superpowers:executing-plans`로 순차 진행한다. 실제 제품 빌드는 별도 승인 전까지 실행하지 않는다. 현재 작업 폴더의 기존 구현과 검증 기록은 보존한다.

**Goal:** Unity Build Profile을 선택하고 제품 정보·사전 검사·옵션·실행 결과를 한 화면에서 다루는 Unity 에디터용 빌드 도구를 제공한다.

**Architecture:** 기존 제품 정의를 원본으로 사용하고, 공통 빌드 흐름·플랫폼별 처리기·제품 프로필·옵션 처리기를 분리한다. 플랫폼과 옵션은 등록 후 조회하며 중앙 실행기의 플랫폼별 switch를 늘리지 않는다.

**Tech Stack:** Unity 6000.3.10f1, C#, Editor UI Toolkit, Unity Build Profiles, 기존 Products.Editor 및 콘텐츠 빌드 파이프라인.

**Spec:** 이번 대화에서 확정한 요구사항을 이 문서의 ‘확정 계약’에 통합했다. [1단계 계획](build-tool-stage-01-plan.md) · [1단계 목표](../../Goals/project-wide/build-tool-stage-01-goal.md) · [실행 명령문](../../Commands/project-wide/build-tool-stage-01-command.md)

## 1. 확정 계약과 작업 제한

- 메뉴는 **`Match → Build → 빌드 도구`**다. 앞으로 추가하는 빌드 관련 메뉴도 `Match/Build` 아래에 둔다.
- 기존 프로필을 조회·선택해 빌드한다. 제품 이름·식별자·씬·제품 심볼을 새 설정 파일에 중복 정의하지 않는다.
- 목록에서 선택하는 행과 Unity의 활성 Build Profile은 구별한다. 단순 조회·선택으로 플랫폼을 전환하거나 프로젝트 설정을 저장하지 않는다.
- GPG ON/OFF, 특정 플러그인 ON/OFF 등 제품·플랫폼별 옵션을 추후 추가할 수 있다. 이번 계획에서 실제 SDK 옵션의 기본값이나 지원 제품을 임의로 확정하지 않는다.
- 옵션 하나는 컴파일 준비·빌드 전처리·빌드 후처리·종료 정리 중 필요한 여러 단계에 참여할 수 있다.
- 공통 코드와 플랫폼별 코드를 분리한다. Android 게임과 Android 레벨툴은 같은 Android 처리기를, 두 Windows 제품은 같은 Windows 처리기를 사용한다.
- 제품 심볼·시작 씬·필수 데이터 등 제품 실행에 필요한 계약은 해제 가능한 일반 옵션으로 만들지 않는다.
- 이번 문서 작업 및 1단계는 Player/APK/AAB/iOS 출력·Addressables 번들 빌드·배포·커밋·푸시를 하지 않는다. 향후 단계에서도 실행 가능한 코드 작성과 실제 산출물 생성 승인은 구분한다.
- HTML 매뉴얼은 별도 요청 전까지 갱신하지 않는다. 씬·프리팹을 에디터 스크립트로 재작성하지 않는다. 질문은 제한시간 없는 일반 채팅으로 한다.

## 2. 현재 소스에서 확인한 사항

| 영역 | 확인한 상태와 계획에 미치는 영향 |
|---|---|
| `ProductProfiles.cs` | 다섯 제품 정의, 심볼+플랫폼 식별, 프로필 검사·활성화와 출력 경로 설정이 있다. 제품 정보의 원본으로 재사용한다. |
| `ProductProfiles.Audit.cs` | 제품 경계·테스트 포함 금지·씬·식별자·콘텐츠 검사가 있다. `ProductBuildGuard`가 플랫폼과 **고정 출력 경로**를 검사한다. 임의 출력 경로 옵션은 이 계약을 먼저 정리해야 한다. |
| `ProductProfiles.ContentPaths.cs` | 제품별 Addressables 경로·포함 설정을 변경하고 저장하는 경로가 있다. 읽기 전용 사전 검사에서 호출하지 않는다. |
| 콘텐츠 처리 | MemoryPack, 아틀라스, 매뉴얼 동봉 등 기존 빌드 콜백이 있다. 2단계에서 순서를 조사해 연결하고 동일 처리를 두 번 실행하지 않는다. |
| 기존 검사 | `ProductBoundaryVerification.Run`은 내부에서 `Configure`를 호출한다. `ProductSelectionVerification`도 활성 선택을 변경한다. 1단계의 ‘조회 무변경’ 근거로 무조건 실행하지 않는다. |

현재 제품은 Android Game, iOS Game, Windows Steam Game, Windows Level Editor, Android Level Editor다. 이 목록을 화면 코드에 다시 상수로 복제하지 않는다.

## 3. 화면과 사용자 흐름

```text
프로필 목록                 선택한 프로필 정보
Android Game                플랫폼 / 앱 식별자 / 시작 씬
iOS Game                    제품 심볼 / 출력 위치 / 현재 활성 여부
Windows Steam Game
Windows Level Editor        사전 검사 / 문제와 해결 위치
Android Level Editor        적용 가능한 옵션 / 이번 실행 요약

새로고침  사전 검사         빌드  진행 상태  결과·로그·출력 폴더
```

- 프로필은 프로젝트 Build Profile 에셋에서 발견하고 기존 제품 정의와 대조한다. 등록되지 않음·설정 오류·플랫폼 미지원도 목록에서 이유를 확인할 수 있게 한다.
- 선택한 제품의 예상 출력과 현재 활성 프로필을 나란히 표시한다. 서로 다르다는 이유만으로 자료를 잘못된 것으로 판정하지 않는다.
- 1단계에는 새로고침과 읽기 전용 검사가 제공된다. 빌드 버튼은 실행 불가 상태이며 2단계 예정이라는 설명을 표시한다.
- 추가 옵션이 없으면 ‘등록된 추가 옵션 없음’을 표시한다. 동작하지 않는 GPG·플러그인 체크박스를 미리 제공하지 않는다.
- 기존 `Tools/Products` 진입은 이번 신규 메뉴 추가만으로 삭제·이동하지 않는다. 향후 빌드 관련 메뉴를 옮겨야 하면 호출부·단축키·문서 영향을 확인해 해당 단계에 포함한다.

## 4. 책임과 의존 구조

```text
빌드 도구 UI
    ↓
프로필 조회·공통 검사 / 공통 빌드 실행기
    ├─ 기존 ProductProfiles의 제품 계약
    ├─ 등록된 플랫폼 처리기 → Android / iOS / Windows
    └─ 등록된 옵션 처리기 → 제품·플랫폼에 해당하는 옵션만 조회
                  ↓
          기존 Unity 빌드·콘텐츠 처리
```

| 구성 | 책임 |
|---|---|
| 프로필 조회 | 에셋 GUID로 프로필을 식별하고 기존 제품 정의와 연결한다. 같은 제품의 복제 프로필과 미등록 프로필도 구별한다. |
| 공통 검사 | 제품 계약, 상태 표시, 검사 결과를 관리한다. 플랫폼별 차이를 중앙 switch에 모으지 않는다. |
| 공통 실행기 | 요청 확정, 전환·재컴파일 대기, 단계 실행, 중복 방지, 오류·결과·복원을 소유한다. |
| 플랫폼 처리기 | 플랫폼 고유 준비 상태·설정·빌드 방식과 전후처리를 담당한다. 공통 흐름 전체를 복제하지 않는다. |
| 제품 프로필 | 게임·레벨툴의 씬·식별자·제품 심볼·출력 계약을 제공한다. 별도의 Windows 레벨툴 플랫폼 클래스를 만들지 않는다. |
| 옵션 정의·처리기 | 안정 ID, 설명, 적용 대상, 기본값, 의존·충돌, 단계별 적용·복원을 담당한다. |

구체 처리기는 명시적 등록표로 시작한다. 리플렉션 기반 자동 발견, 플러그인 프레임워크, 새 DI/asmdef는 필요 없이 도입하지 않는다. 실제 공통 부분은 조합·공통 클래스로 공유하고, 모든 기능을 강제로 거대한 부모 클래스에 넣지 않는다. Unity API 경계의 불가피한 플랫폼 판정과 기존 코드의 모든 분기를 없애는 작업은 구별한다.

## 5. 옵션 적용·전후처리 계약 — 3단계 구현 기준

| 단계 | 담당 내용 |
|---|---|
| 실행 전 검증 | 해당 제품·플랫폼에 적용 가능한 옵션만 수집하고 의존성·상충 조합을 검사한다. 선택하지 않은 옵션도 OFF 처리가 필요한지 판정한다. |
| 컴파일 준비 | 관련 심볼·어셈블리·플러그인 포함 설정 등 컴파일에 선행해야 하는 변경을 적용한다. 변경 시 스크립트 재로드 이후 이어갈 요청을 보존한다. |
| 빌드 전처리 | 패키징 전에 필요한 Manifest·Gradle·콘텐츠 설정 등을 준비한다. 기존 콜백과 중복되지 않게 실행 위치를 정한다. |
| 빌드 후처리 | 실제 성공 결과와 산출물 경로를 받아 생성 프로젝트·파일을 수정한다. 없는 산출물을 가정해 처리하지 않는다. |
| 종료 정리 | 성공·실패·취소와 후처리 오류에서도 원본 프로젝트의 임시 변경을 복원한다. 적용한 변경의 역순으로 정리하며 복원 실패도 따로 보고한다. |

- GPG OFF는 호출만 중지하는 것과 SDK 바이너리·의존성까지 제외하는 것이 다르다. 옵션 구현 때 실제 플러그인을 조사해 제외 범위를 명시한다. 공유 의존성을 사용하는 다른 기능을 함께 제거하지 않는다.
- 각 옵션은 ON/OFF 양쪽 처리와 단계별 효과를 정의한다. 같은 옵션으로 반복 빌드하거나 ON 다음 OFF로 빌드해도 이전 설정이 남지 않아야 한다.
- 실행 순서는 공통 단계 → 플랫폼 단계 → 의존성을 반영한 옵션 단계처럼 명시한다. 구현 시 실제 콜백 시점에 맞춰 확정하며 타입 발견 순서에 의존하지 않는다. 순환 의존·충돌은 실행 전에 차단한다.
- 옵션이 바꾸는 설정의 소유권을 명시한다. 같은 값을 여러 옵션이 다른 값으로 변경하려 하면 실행 전에 거절한다. 심볼처럼 합칠 수 있는 값은 공통 소유자가 한 번에 적용한다.
- 프로필 자체의 선택값과 이번 실행에서 계산한 최종 적용값을 구별해 표시하고 기록한다. `PRODUCT_` 심볼을 일반 기능 옵션용으로 추가하지 않는다.
- SDK 제거·재설치나 `manifest.json` 변경을 매 빌드의 기본 방식으로 삼지 않는다. 플러그인별 지원 수단을 확인한 뒤 전용 처리기를 연결한다.
- 임시 원본 변경은 복원하지만 최종 산출물에 적용한 후처리는 유지한다. 후처리 실패는 전체 작업의 실패로 표시하고 이미 생성된 결과의 위치를 함께 남긴다.

## 6. 상태·저장·재시작

- 개인별 마지막 선택과 향후 옵션 값은 프로필 GUID 기준으로 `UserSettings/MatchBuildTool.json` 같은 Git 제외 로컬 설정에 보관한다. 실제 저장 위치와 제외 여부는 1단계에서 확인한다. 인증정보는 저장하지 않는다.
- 팀 공통 기본값은 옵션 정의에서 제공한다. 공유 프리셋이 필요해지기 전에는 별도 제작 SO나 프리셋 시스템을 만들지 않는다.
- 2단계의 실행 요청은 확정 당시 프로필·옵션을 보존하고 실행 중 화면 변경으로 바뀌지 않게 한다.
- 스크립트 재로드 후에는 진행 중인 요청과 설정 적용 상태를 확인하고 이어간다. 에디터 재실행은 별도로 구분해 **빌드 자동 재개를 하지 않는다.** 원복이 필요한 미완료 작업은 먼저 알리고 정리한다.
- 빌드한 프로필은 활성 상태로 유지하는 것을 권장 기본값으로 둔다. 원래 플랫폼으로 자동 복귀하며 재컴파일을 반복하지 않는다. 원본 임시 설정 복원과 활성 프로필 복귀는 별개다.

## 7. 단계별 결과

| 단계 | 작업 묶음 | 완료 결과 / 검증 |
|---|---|---|
| 1. 조회·사전 검사 | 프로필 발견·제품 정보, 공통/플랫폼 검사, UI·선택 기억 | 다섯 제품과 미등록·손상 프로필을 표시하고, 선택·검사로 활성 프로필·플랫폼·콘텐츠·에셋이 바뀌지 않음을 검사한다. 실제 빌드 없음. |
| 2. 실행·결과 | 요청 저장·프로필 활성화·전환 대기, 기존 콘텐츠/빌드 연결, 결과·중단 복구 | 중복·재로드·실패를 모의 실행 경로로 검사한다. 실제 빌드 검증은 별도 승인된 경우에만 수행하고, 미수행 시 명시한다. |
| 3. 제품별 옵션 | 옵션 등록·대상·의존·충돌, 단계별 적용·복원, 선택값 저장 | 임시 검사 옵션으로 ON→OFF·제품 전환·실패/취소·복원 오류를 검사한다. 실제 GPG·SDK를 임의 설치하지 않는다. |

각 단계는 2~3개의 내부 작업 묶음으로 진행한다. 내부 작업마다 새 단계 계획서를 만들지 않는다. 상세 계획은 앞 단계 완료 시 현 소스에 맞춰 작성한다. 현재 3단계 공통 구조까지 구현·모의 검증했다. 실제 SDK 어댑터와 제품 빌드는 별도 후속 범위다.

## 8. 이번 범위 밖

스토어 업로드·서명정보 관리·배포, 여러 제품 연속 빌드, 원격 빌드 서버, 자동 SDK 설치, 플러그인 범용 제거기, 제품별 사용자 정의 씬·출력 경로 편집은 포함하지 않는다. iOS 프로젝트 생성과 Xcode 서명·아카이브는 다른 성공 조건이며 호스트 환경별 지원 범위를 구현 시 확인한다.

## 9. 검토 초점과 보고

1. 동일 `PRODUCT_LEVEL_EDITOR` 심볼을 사용하는 Android·Windows를 혼동하지 않는가.
2. 잘못된 프로필 하나가 목록 전체를 깨뜨리거나 원본 자동 수정을 유발하지 않는가.
3. 선택만으로 `Select`·`Configure`·콘텐츠 동기화를 호출하지 않는가.
4. 컴파일 전 변경을 늦은 빌드 콜백에만 넣거나, 재로드 때 빌드를 두 번 실행하지 않는가.
5. OFF·부분 실패·에디터 중단 후 원복 누락으로 다음 제품에 설정이 새지 않는가.

단계 마무리에는 변경 사항·실제 검증·미검증·제약을 보고하고, 다음 단계 계획·목표·복사용 실행문을 작성한다. 다음 단계를 자동 구현하지 않는다. 커밋 메시지는 실제 구현을 마친 단계에만 제시하며 커밋·푸시는 하지 않는다.

## 11. 이번 확정 사항을 적용하는 기준

- 전체 작업은 위의 **3단계**로 유지한다. 각 단계 안의 구현·검증 묶음 때문에 별도 단계 문서를 계속 늘리지 않는다.
- 1단계의 기존 완료 기록은 당시 소스에 대한 기록이다. 후속 단계가 추가한 실행 UI를 1단계의 비활성 버튼 기준에 맞추려고 제거하지 않는다. 이미 충족한 요구는 재사용하고 실제 누락만 다음 구현 요청의 범위로 삼는다.
- 공통 실행기는 진행·중복 방지·결과·정리를 소유하고, 플랫폼 처리기는 플랫폼 차이만 제공한다. 공통 동작은 조합으로 공유하며 필요한 경우에만 공통 기반 클래스를 둔다. 상속 계층 자체를 목표로 만들지 않는다.
- 옵션은 제품과 플랫폼에 맞는 등록 항목만 조회한다. 하나의 옵션에 컴파일 준비·전처리·후처리·정리를 함께 등록할 수 있다. 실제 SDK 연동 전에는 GPG/플러그인 토글이 완성된 것처럼 제공하지 않는다.
- 후속 실행·복구 검증에는 요청의 부분 저장 실패, 로그 기록 실패 중 정리 수행, 완료 결과가 없는 호출을 포함한다. 결과 근거가 없으면 성공·실패를 단정하거나 빌드를 자동 재호출하지 않는다.
- 단계별 실행 요청 시 기존 문서와 현 소스를 대조한다. 3단계 [계획](build-tool-stage-03-plan.md)·[목표](../../Goals/project-wide/build-tool-stage-03-goal.md)·[실행문](../../Commands/project-wide/build-tool-stage-03-command.md)은 2단계 완료 후 작성했으며 자동 구현하지 않는다.
- 문서만 정리하는 요청은 문서 검증만 수행한다. 구현 요청의 컴파일·관련 검사는 별도로 기록하고 실제 Player/Addressables 빌드는 승인 없이 실행하지 않는다.

## 12. 3단계 완료 상태

옵션 정의·대상·기본값·의존/충돌·개인 선택 저장과 확정 실행값, 컴파일 준비·전후처리·역순 정리를 연결했다. 최종 옵션/옵션 재로드 및 기존 네 회귀 검사를 통과했다. [3단계 진행 기록](../../Verification/project-wide/build-tool-stage-03-progress.md)을 따른다. 실제 SDK 옵션은 등록하지 않았으며 GPG·플러그인 포함/제외·실제 빌드 성공을 확인한 것은 아니다. 다음 실제 SDK 연동은 자동 시작하지 않는다.

## 13. 후속 디버그 모드·공통 로그

사용자 후속 요청으로 실제 **디버그 모드** 옵션을 기존 등록 구조에 추가했다. 기본 OFF이며 Development Build와 조건부 공통 로그를 연결한다. 원본 프로필을 수정하지 않고 이번 실행 플래그만 적용한다. 이전 3단계 완료 시점의 빈 등록표 기록과 구분하며 현재 운영 기본 옵션은 이 항목이다. SDK 토글은 아직 추가하지 않았다. [구현·검증·미검증 기록](../../Verification/project-wide/build-tool-debug-mode-progress.md)을 따른다.
