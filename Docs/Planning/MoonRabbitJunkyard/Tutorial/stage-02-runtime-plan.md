# 레벨 튜토리얼 2단계 — 확장 가능한 진행 엔진

> 실행 방식: 이 세션에서 직접 수행하며 구현 시 executing-plans 절차를 적용한다. 하위 에이전트와 자동 커밋은 사용하지 않는다.

상태: 완료. 2026-10-07 구현·검증 완료. 이전 계획의 실제 게임 연결은 새 3단계로 이동했다. 기존 문서 경로는 연결 보존을 위해 유지한다.

목표: 공통 진행과 행동/완료 조건의 등록 구조를 구현하고, 기존 튜토리얼 데이터의 동작·검사 호환성을 유지하며 확장을 검증한다.

구조: 공통 진행부는 순서·권한·결과/연출 대기를 소유한다. 종류별 처리기·판정기를 명시적으로 등록하고 현재 단계에 필요한 것만 조회한다. 실제 퍼즐과 화면은 다음 단계의 연결부에서 공급한다.

기술: Unity6000.3.10f1, 기존 C#/MemoryPack·요소 ID·검사 도구. 새 패키지/asmdef/DI/MVVM 프레임워크는 추가하지 않는다.

## 범위와 기존 코드

- TutorialStepDefinition의 네 단계·세 결과 종류를 재사용하고 enum 값·MemoryPack 필드 순서를 유지한다.
- LevelTutorialValidator의 공통 문구/배치/공급 검사는 유지하고 종류별 규칙만 등록된 처리기에 위임한다. References의 종류별 참조 수집도 같은 규칙에 연결하여 팩 참조 폐쇄와 실행 지원이 어긋나지 않게 한다.
- 오브젝트마다 기능을 구현하지 않고 기존 요소 ID로 같은 행동/결과를 공유한다. 망치·교환·섞기는 아이템별 규칙으로 등록하고 중앙 엔진은 아이템 종류를 분기하지 않는다.
- 진행 엔진은 MonoBehaviour·GameObject·Canvas·Addressables·게임 세션을 직접 참조하지 않는다. 게임 연결용 입력/결과/연출 계약만 제공한다.
- 실제 게임 입력 제한·고정 공급 적용·EndStableTurn 수정·실제 행동 재생은 3단계다. 영구 기록·안내 UI는 4단계다. 모의 신호 검사를 실제 게임 검증으로 보고하지 않는다.

Tutorial 영역은 Assets/Scripts/Features/Tutorial 아래다. 파일이 커지면 같은 기능 폴더에서 책임별로 분리하되 타입마다 폴더를 만들거나 주변 소스를 일괄 이동하지 않는다.

계약의 필수 의미:

1. 등록 목록은 종류→처리기 직접 조회다. 초기 조립 후 변경하지 않는다. 처리기의 실행별 상태를 공유 목록에 저장하지 않는다.
2. 처리기는 해당 단계의 설정 검사·참조 수집·입력 허용·성공 판정을 소유한다. 공통 진행부에 좌표/아이템 종류 분기를 반복하지 않는다. 공통 배치 검사와 최초 행동의 초기 보드 검사는 보존한다.
3. 입력 의도는 다음/교환/제자리 발동/아이템과 필요한 좌표·아이템을 표현한다. 승인과 실제 실행 성공을 구별한다.
4. 결과에는 세션/단계/행동 식별값을 연결한다. 거절은 진행·권한을 변경하지 않고 과거·취소된 실행·중복 신호는 현재 단계를 완료시키지 못한다.
5. 결과 기록은 종류·실제 정의 ID·필요 좌표·발생 개체 구분을 전달한다. 2×2 피해 칸 수와 본체 제거 수를 혼동하지 않으며 같은 개체 재보고는 중복 집계하지 않는다.
6. 판정기는 해당 단계의 명시된 조건만 평가한다. 결과 종류로 조회하여 ID·좌표·수량을 적용한다. 결과 조건이 없으면 행동 성공과 연출 완료만 요구한다.
7. 상태는 설명 대기/행동 대기/연출 대기/완료/설정 오류/취소를 구별한다. UI는 읽기 전용 상태와 명령만 사용한다. 현재 단계·대기 이유·오류를 조회할 수 있다.
8. 결과/연출 신호 순서와 관계없이 관련 성공·조건 충족·연출 완료가 모두 확인돼야 진행한다. 팝업/일시정지는 진행을 보류하며 재개 시 상태를 유지한다.

## 작업 순서와 검사

A~C는 내부 묶음이다. 각 묶음의 실패 검사를 확보한 뒤 구현하고 통과시킨다. 별도 단계 번호/문서는 만들지 않는다.

### A. 등록 구조와 종류별 규칙

- [x] 현재 enum·validator·아이템 규칙·실제 퍼즐 결과 타입에서 계약의 값·수명을 확정한다. 실행 기록 자체 변경은 3단계로 남긴다.
- [x] 중복/미등록·현재 종류만 조회·등록 순서 독립의 실패 검사를 작성한다.
- [x] 단계·아이템·결과 등록을 구현하고 네 단계·세 아이템·세 결과를 명시적으로 등록한다. 전체 탐색·폴링·동적 리플렉션을 만들지 않는다.
- [x] 공통 기하/문구/공급과 종류별 대상/참조/초기 보드 검사를 분리한다. 파워 정의 검사, 망치 한 칸·교환 두 칸·섞기 무대상 규칙을 보존한다.

검사 결과: 같은 입력의 허용·참조·정적 오류가 기존 규칙과 일치하고 지정하지 않은 처리기 호출은 0이다.

### B. 공통 진행과 결과 판정

- [x] 설명 다음→교환 성공→생성 조건→파워 교환→발동 조건, 각 아이템의 진행/거절 검사를 작성한다. 역방향 교환은 실제 입력과 첫→둘째 안내를 확인해 정책을 명시한다.
- [x] 실행별 TutorialProgress·읽기 전용 상태를 구현한다. 입력 판정은 처리기에 위임하고 실제 퍼즐은 실행하지 않는다.
- [x] 현재 조건에만 관련 기록을 누적한다. ID/좌표/수량·2×2 본체 중복·재보충·서로 다른 개체를 검사한다.
- [x] 성공/결과가 있어도 연출 미완료면 유지한다. 연출 먼저 도착/중복, 지난 행동 결과, 취소 후 신호, 실패 행동을 검사한다.
- [x] 체험 권한은 해당 단계 성공 시 1회 소진한다. 거절/실패/취소는 소진하지 않고 다른 단계로 넘기지 않는다. 실제 재고 시스템은 추가하지 않는다.
- [x] 일시정지/재개·설명 무대상·튜토리얼 없음·세션 격리·취소/해제를 검사한다. 중복 신호로 두 번 진행하지 않는다.

검사 결과: 모의 실행 결과·연출 신호로 진행이 재현되고 원본 게임/레벨 변경 없이 성공·대기·거절·취소를 구별한다.

### C. 검사 연결·확장 검증·인계

- [x] validator 공개 진입점을 유지하며 종류별 검사/참조를 등록 규칙에 연결한다. Editor/runtime에 별도 분기 표를 두지 않고 지원 누락을 진단한다.
- [x] 시험 전용 처리기/판정기를 대체 등록한 별도 목록을 주입한다. 공통 TutorialProgress 수정 없이 호출되고 관련 없는 종류는 호출되지 않는지 검사한다. 운영 목록과 시험 목록은 격리한다.
- [x] 시험에서만 미등록 종류 값을 사용해 등록 시 지원되고 기본 목록에서 오류인지 확인한다. 운영 enum/팩은 변경하지 않는다. 이 검사를 저장/에디터까지 자동 지원한다는 증거로 해석하지 않는다.
- [x] 같은 제거 특성의 서로 다른 요소 ID에 동일 판정기를 재사용하고 결과를 구분한다.
- [x] 1단계 데이터/에디터/저장·팩1/2/3·튜토리얼 없는 입력·참조 폐쇄 회귀를 확인한다. 테스트 해제 후 게임 소스 컴파일과 원본/GUID 보존을 확인한다.
- [x] stage-02-progress.md에 실제 검사·제약·확장 방법을 기록하고 보고한다. 실제 계약으로 3단계 계획·목표·복사용 실행문을 작성하되 구현하지 않는다.

## 검증 실행

새 검사 엔트리: TutorialRuntimeVerification.Run. 기존 이름과 충돌하면 구현 전에 문서·실행문을 함께 갱신한다.

~~~powershell
& './Tools/Testing/ProjectTests.ps1' -Action Status
& './Tools/Testing/ProjectTests.ps1' -Action Run -Method 'TutorialRuntimeVerification.Run'
& './Tools/Testing/ProjectTests.ps1' -Action Compile
~~~

도구의 연결/해제 정책을 확인한다. 위 Compile은 테스트를 연결한 컴파일이므로 게임 소스만의 검증을 대체하지 않는다. 최종 게임 소스 검사는 연결 해제 확인 후 Unity를 -batchmode -quit -projectPath -logFile 인수로 별도 실행하여 종료 코드를 확인한다. 실제 수행 명령과 결과는 2단계 검증 기록에 보관한다. 남은 연결은 소유 상태 확인 후 Detach한다. 관련 1단계 회귀는 기존 엔트리명을 확인하여 수행한다. 사용자 Unity 때문에 검사가 막히면 임의 종료하지 않고 미검증을 보고한다.

## 검토 중점

구현 계약: TutorialProgress.TryApprove / ReportCompletion / ReportResults / ReportPresentationComplete / SetPaused / Fail / Cancel·Dispose. 생성 시 단계·조건을 복사하며 Snapshot은 불변 사본이다. Item은 RegisterItem으로 아이템 종류를 직접 등록한다. 등록 목록은 초기 조립 후 Freeze한다. 교환은 지정 두 칸의 양방향을 허용하며 설명에 실행 결과 조건을 붙이는 모순은 설정 오류로 진단한다. 전체 보드/카탈로그 검사는 3단계 연결부에서 수행하고, 보드 없는 엔진 준비는 대상 형식·ID 형식·종류 지원을 검사한다.

| 위험 | 담당 검사 |
|---|---|
| 누락된 등록이 임의 동작으로 진행 | A/C: 미등록·중복 오류 |
| 지난 결과가 다음 단계를 완료 | B: 실행 식별·지연·중복·취소 |
| 2×2 제거·재보충 수량 오판 | B: 본체 식별·좌표·ID·중복 |
| 권한/상태의 다른 세션 유출 | B: 실패/취소·두 세션 격리 |
| 실행/검사/팩의 참조 해석 차이 | A/C: 규칙 공유·References·팩 회귀 |

원본 레벨/팩/이미지/GUID·HEAD/WIP·1단계 완료분을 보존한다. 빌드·번들·커밋·푸시·하위 에이전트·사용자 Unity 종료·임의 씬 저장·출시 데이터 덮어쓰기는 하지 않는다. 과거 검사 출력은 보관 후 복원한다.

이 단계는 확장 엔진과 검사까지만 완료한다. 실제 화면 튜토리얼이 진행된다는 보고는 3~4단계 검증 후에 가능하다.
