# 레벨툴 책임 분리 리팩토링 통합 계획

> 실행자는 `superpowers:executing-plans`를 적용해 단계별로 진행한다. 하위 에이전트는 별도 승인 없이 사용하지 않는다. 이 문서는 계획이며 구현 완료를 의미하지 않는다.

**목표:** 기존 편집 동작과 데이터 호환성을 유지하면서 레벨툴의 입력·화면·편집 책임을 분리한다.

**구조:** 기존 `AuthoringToolWorkspace`, `AuthoringEditSession`, 문서 편집·저장·검증 기능을 재사용한다. `LevelToolScreen`은 화면 조립과 수명주기를 담당하고, 보드 입력과 기능별 패널이 명시적인 계약을 통해 편집 기능을 호출한다.

**기술:** Unity 6000.3.10f1, UI Toolkit, Newtonsoft JSON, 기존 MemoryPack 변환 및 외부 Tests 하네스.

**근거:** 2026-10-19 소스 구조 검토와 사용자의 리팩토링 계획 요청. 완료 기준은 [목표 문서](../../../Goals/MoonRabbitJunkyard/LevelToolRefactoring/2026-10-19-goals.md)에 분리한다.

## 현재 확인한 구조

- `LevelToolScreen*.cs`는 42개 파일, 약 5,383줄이지만 하나의 partial 클래스다. 파일 분할만으로 상태 접근과 의존성이 격리되지는 않는다.
- `AuthoringToolWorkspace`는 폴더·저장·복구를, `AuthoringEditSession`은 문서·선택·Undo/Redo를 소유한다. 이 상태를 다른 컨트롤러에 복제하지 않는다.
- 화면의 `Change` 경로에는 JSON 필드 및 스키마 버전 처리가 남아 있다. 다른 partial 파일의 쓰기 경로는 해당 단계에서 조사한다.
- Elements와 Tutorial에는 행동·조건 등록 구조가 있다. Drone에는 정책 등록과 대상 분기가 함께 존재한다. 이들은 이번 리팩토링의 수정 대상이 아니다.
- 제작 데이터 가져오기·변환·히스토리 정리는 이미 서비스와 화면이 분리되어 있다. 관련 회귀 검사로 보호하고, 이번에 새 범용 프레임워크로 재작성하지 않는다.

## 범위와 제약

- 총 4단계. 각 단계는 동작 가능한 상태로 끝내고 결과를 보고한 뒤 다음 단계 상세 계획·목표·복사 가능한 실행문을 작성한다. 다음 단계 구현을 자동으로 시작하지 않는다.
- 이번에는 통합 계획과 1단계만 상세화한다. 후속 파일명·계약은 직전 단계 결과를 반영해 확정한다.
- JSON 스키마, ID, 저장 위치, MemoryPack 형식, Addressables 키와 기존 사용자 데이터를 변경하지 않는다.
- Windows 마우스·키보드, Android 터치·롱터치·핀치, 창 크기·복구 동작을 유지한다.
- UI 재디자인, 게임 규칙 변경, 새 패키지·asmdef·DI 도입, 전면 MVVM 전환은 제외한다.
- MVVM의 상태와 표시 분리 원칙만 활용한다. 별도 ViewModel에 편집 문서와 선택 상태를 중복 보관하지 않는다.
- 제품 빌드, 커밋·푸시, HTML 매뉴얼 갱신, 사용자 이력 정리, 코드에 의한 프리팹 편집을 하지 않는다.

## 목표 의존 방향

```text
LevelToolScreen: 화면 조립·활성화·해제
  → 보드 입력 / 기능별 패널
    → 기존 문서 편집 기능
      → AuthoringEditSession: 변경·선택·Undo/Redo

프로젝트 열기·저장·복구 → AuthoringToolWorkspace → 저장소
편집 세션의 읽기 결과 → 패널 갱신
```

입력 제스처의 임시 상태만 입력 객체가 소유한다. 선택 셀은 세션이, 활성 탭·표시 상태는 화면 또는 해당 패널이 소유한다. 저장·검증 계층은 화면 객체를 참조하지 않는다.

## 1단계 — 보드 입력과 수명주기 분리

상태: 2026-10-19 구현·자동 회귀 검증 완료. 실기기 및 제품 실행 파일 수동 검사는 별도이며, 후속 단계는 미착수.

**결과:** 보드 포인터·휠 처리와 제스처 임시 상태를 하나의 명시적인 수명주기를 가진 객체로 분리한다.

- [x] 기존 입력·뷰포트 검사로 변경 전 기준을 확보한다.
- [x] 실제 호출부를 확인하고 이벤트 등록·해제와 포인터 취소를 분리한다.
- [x] 모달·작업 중 입력 차단, 레벨 전환 취소, 재활성화 중복 구독을 검사한다.
- [x] 화면 배치·줌 수치·문서 변경 의미가 같음을 확인한다.

상세: [1단계 계획](2026-10-19-stage01-plan.md).

## 2단계 — JSON 편집 경계 정리

**결과:** 보드·속성·튜토리얼 화면의 데이터 쓰기를 기존 Editing 기능으로 모은다.

- UI에서 직접 JSON을 수정하는 호출과 기존 `DocumentEditing`, `ElementSelectionEditing`, `FlowDocumentEditing`, `TutorialDraftEditing`의 중복을 먼저 목록화한다.
- 화면은 입력값을 전달하고, 문서 변경은 세션의 기존 트랜잭션을 통해 실행한다. 사용자 동작 하나당 기존과 같은 Undo 단위를 유지한다.
- 읽기까지 일괄 DTO로 복제하지 않는다. 반복되는 해석이나 스키마 판단에만 좁은 조회 함수를 둔다.
- 배치·삭제·붙여넣기·속성 수정·튜토리얼 조건 수정 후 JSON 의미, Undo/Redo, 저장 재로드 결과를 비교한다.

**검증:** 기존 JsonEditing/Workspace 및 Tutorial 편집 검사에서 관련 사례를 골라 변경 전후 비교. 실패한 편집이 부분 적용되지 않는지 포함한다.

## 3단계 — 기능별 패널과 화면 조립 분리

**결과:** 보드 표시·속성·튜토리얼 등 실제 변경 책임별 패널을 분리한다.

- 2단계의 편집 API를 사용해 패널을 분리한다. 단순 파일 수 감소를 목표로 하지 않는다.
- 화면 전체를 패널에 넘기는 방식, 서로의 private 상태를 대체하는 광범위 public 접근자를 금지한다.
- 필요한 읽기 상태와 편집 명령만 전달하고, 패널 간 변경은 화면 조정자가 연결한다.
- 공통 필드 UI는 실제 반복되는 동작만 재사용한다. 종류마다 전용 패널을 의무화하지 않는다.
- 창 크기 변경, 패널 이동·숨김, 탭 복귀, 모바일 드로어에서 상태와 레이아웃을 검사한다.

**검증:** 기존 Viewport/ControlLayout/Shortcut/MobileTutorialViewport 검사와 Windows 실제 화면 확인. Android 실기기가 없으면 미검증으로 기록한다.

## 4단계 — 통합 회귀와 확장 경계 마무리

**결과:** 새로운 작업자가 변경 위치와 상태 소유자를 찾을 수 있고 기존 편집·시험·변환 흐름이 보존된다.

- 편집 → 저장 → ZIP 내보내기·가져오기 → 검증 → MemoryPack 변환 → 시험을 격리된 테스트 데이터로 확인한다.
- 현재 원본·리소스 보호와 히스토리 정리 회귀를 실행한다. 실제 사용자 이력은 삭제하지 않는다.
- 이번 분리로 생긴 중복 래퍼·미사용 경로만 제거한다.
- 의존 방향, 상태 소유권, 기능 추가 위치를 개발용 Markdown에 정리한다.
- 전체 테스트 무조건 반복 대신 변경된 경계의 관련 검사를 묶어 실행하고 잔여 미검증을 보고한다.

## 공통 검토 초점

| 실패 조건 | 담당 단계·기대 결과 |
|---|---|
| 드래그 중 모달 또는 레벨 전환 | 1: 기존 입력을 취소하고 뒤늦은 편집 금지 |
| 화면 비활성화·재활성화 | 1: 콜백 중복·이전 root 참조 없음 |

| 현재 원본·변환 복구 상태 | 4: 데이터 보호·복구 규칙 유지 |

검증을 위해 새 프레임워크를 만들지 않는다. 기존 검사에 의미 있는 회귀 사례만 추가한다. 실패 시 해당 단계의 변경만 조정하며 기존 사용자 변경은 원복하지 않는다.
