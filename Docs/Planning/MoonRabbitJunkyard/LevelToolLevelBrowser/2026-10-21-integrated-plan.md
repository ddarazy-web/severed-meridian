# 레벨툴 대량 레벨 탐색 통합 계획

> 구현 담당: `superpowers:executing-plans`에 따라 단계별로 구현·검증한다. 커밋·푸시하지 않는다.

**상태:** 2026-10-21 1단계·2단계 완료 (실기기 검증 제외)
**목표:** 수천·수만 레벨에서 원하는 레벨을 쉽게 찾고, 다른 작업을 잃지 않고 편집한다.  
**구조:** 목록용 메타데이터와 편집 문서를 분리한다. 가상 목록과 검색은 탐색 상태만 바꾸고, 공통 레벨 열기 경로가 저장 여부 확인과 최근 편집 기록을 담당한다.  
**기술:** 기존 Unity UI Toolkit, C# 제작 세션, JSON 저장소를 재사용한다.

## 확정한 사용 방식

| 항목 | 동작 |
| --- | --- |
| 목록 | 페이지 번호 대신 가상 스크롤. 보이는 행과 여유 행만 생성·재사용 |
| 검색 | 숫자는 레벨 번호 정확히 검색, `1200~1299`는 번호 범위, 문자는 이름 부분 검색 |
| 정렬 | 레벨 번호 오름차순. 같은 번호는 ID로 순서를 고정하는 안 |
| 입력 | 짧은 입력 대기 후 검색. Enter는 검색만 확정하고 레벨을 열지 않음 |
| 행 선택 | 탐색 강조만 변경. 현재 편집 중인 레벨은 유지 |
| 편집 버튼 | 각 행의 **편집** 버튼으로 해당 레벨을 열기 |
| 현재 레벨 찾기 | 검색을 해제하고 현재 편집 레벨이 보이도록 스크롤. 레벨 전환 아님 |
| 표시 | 전체/검색 결과 개수, 검색 결과 없음, 검색 형식 오류를 명확히 표시 |
| 최근 편집 | 성공적으로 연 레벨 최대 20개. ID 기준 중복 제거, 다시 열면 맨 위 |
| 최근 목록 선택 | 별도 편집 버튼 없이 바로 열기 요청. 동일한 미저장 확인 적용 |
| 유지 | 최근 편집 목록은 프로젝트별로 저장하고 앱 재실행 후 복원 |
| 변경 버리기 | **현재 레벨의 변경만** 버림. 다른 레벨·공유 데이터와 그 편집 이력은 유지 |

같은 프로젝트에서는 검색·스크롤을 유지하고 프로젝트를 바꾸면 초기화하는 안을 적용한다. 현재 편집 표시와 탐색 중인 행 표시는 구별한다. 검색·목록 탐색만으로 문서를 저장하거나 편집 이력에 추가하지 않는다.

## 다른 레벨을 열 때

현재 레벨에 미저장 변경이 있으면 다음 확인을 표시한다.

- 제목: **레벨 125를 편집할까요?**
- 설명: **현재 편집 중인 레벨 120에 저장하지 않은 변경 사항이 있습니다.**
- 버튼: **저장하고 다른 레벨 열기** / **변경 버리고 다른 레벨 열기** / **계속 편집하기**

저장 성공 또는 현재 레벨 변경 취소 성공 후에만 새 레벨을 연다. 실패·취소 시 기존 편집 내용과 화면 상태를 유지하며 최근 목록도 갱신하지 않는다. 이미 편집 중인 레벨은 다시 열거나 변경을 버리지 않는다.

**저장 범위에 대한 구현 전제:** 기존 저장은 프로젝트 단위다. 이번 작업에서는 이를 재사용하며 팝업에 “저장 시 다른 레벨과 공유 데이터의 미저장 변경도 함께 저장됩니다.”라고 안내한다. 레벨별 파일 발행 방식은 추가하지 않는다. 반면 변경 버리기는 사용자가 확정한 현재 레벨 단위로 구현해야 한다.

## 착수 시 구조와 주의점

- `LevelToolScreen.cs`는 레벨 전체를 정렬하고 목록 키를 조합하며 행 버튼을 전량 생성한다. 행 클릭이 바로 `Session.SelectLevel`을 호출한다.
- `LevelToolScreen.Refresh.cs`는 최초 화면 구성에서 전체 문서 복사본을 준비하며 이후에도 문서 ID·버전을 조회한다. 목록 가상화만으로 전체 문서 로딩 비용까지 해결되지는 않는다.
- `AuthoringEditSession.Discard()`는 프로젝트 전체를 복원하고 Undo/Redo를 비운다. 레벨 열기 확인에 재사용할 수 없다.
- Undo/Redo는 문서 집합의 상태를 보관한다. 현재 레벨만 복원해도 과거 상태가 그 변경을 다시 살려낼 수 있으므로 이력 처리까지 함께 설계·검증한다.

## 두 단계 진행

| 단계 | 제공 결과 | 완료 판단 |
| --- | --- | --- |
| **1. 레벨 탐색·안전한 편집 전환** | 검색/가상 목록, 명시적 편집 버튼, 현재 레벨만 변경 버리기, 프로젝트별 최근 20개 | 데이터 보존 회귀 검사, 1천/1만 건 목록 검사, Editor UI 확인 |
| **2. 대량 문서 로딩·복사 비용 개선** | 1단계 측정에 근거해 목록 조회와 편집 문서 준비 분리, 불필요한 전체 순회·복사 축소 | 실제 대량 프로젝트 열기/전환 시간·메모리 측정, 저장·복구·Undo 동작 보존 |

1단계 내부 작업은 네 묶음으로 수행하되 매번 별도 단계를 만들지 않는다. 2단계 상세 계획은 1단계가 끝난 후 측정 결과를 반영하여 작성한다. 1단계 목록 검증을 전체 1만 레벨 프로젝트의 시작 성능 검증으로 보고하지 않는다.

## 저장·이력의 안전 경계

현재 레벨 변경 판정에는 아직 반영되지 않은 입력 필드도 포함한다. 다른 레벨이나 공유 데이터만 변경된 상태라면 그 변경을 유지한 채 레벨을 열 수 있다.

부분 취소는 현재 레벨 문서의 마지막 저장 기준을 복원한다. 다른 문서의 현재 값, dirty 상태, 유효한 Undo/Redo를 보존하고 취소한 변경이 Undo/Redo로 되살아나지 않게 한다. 여러 문서를 함께 변경한 원자적 작업은 임의로 분해하거나 전체 이력을 삭제하지 않는다. 새 레벨처럼 저장 기준이 없거나 공유 참조와 충돌하는 경우의 처리도 1단계 구현 첫 묶음에서 검증한다. 기존 계약으로 결정할 수 없는 충돌은 재현 예시를 제시하고 시간제한 없는 문답으로 결정한 뒤 구현한다.

공유 튜토리얼 초안 편집 중인 기존 전환 제한은 최근 목록에도 동일하게 적용한다. 현재 레벨 변경 버리기로 공유 초안을 지우지 않는다.

최근 목록은 게임 콘텐츠·ZIP에 넣지 않는 사용자별 도구 설정이다. 정규화한 작업 폴더 경로와 프로젝트 ID의 조합을 키로 사용하는 안을 우선한다. 같은 ID를 가진 작업 사본을 구분하고, 삭제된 레벨은 표시 시 제외하며 이름·번호 변경은 현재 데이터에서 읽는다. 경로 변경 후에는 별도 프로젝트로 취급하는 단순한 정책을 사용한다.

## 범위와 후속 문서

- 1단계 소스 구현과 Editor 검증을 완료했다. 제품 빌드·프리팹·씬·HTML 매뉴얼 변경은 하지 않았다.
- 구현 시 기존 수동 저장·dirty 표시와 실제 제작 데이터를 보존한다. 검색마다 저장하거나 게임 데이터 포맷을 바꾸지 않는다.
- 새 테스트 임시 사본은 소유 범위를 명확히 하여 자동 정리하고 실제 작업 데이터·검증 결과를 보존한다.
- 각 단계 종료 시 완료/미완료, 검증 수치, 제한을 보고한다. 다음 단계 계획·목표·복사용 실행문을 작성하되 다음 단계 구현은 자동 시작하지 않는다.
