# 2단계 추가 설계안 — 대량 문서의 본문 지연 로딩

상태: **2026-10-21 사용자 1번 선택으로 권장 구조 구현 승인 / 진행 중**. 기존 통합 목표를 축소하거나 완료 처리하는 문서가 아니다.

> 후속 사용자 지시가 우선한다: ‘모든 데이터를 다 읽지마. 파일 목록 정보로 리스팅’. 아래의 최초 전체 검증/본문 보관소 생성 전제는 더 이상 실행 기준이 아니다. 현재 실행 기준은 2단계 계획서의 ‘추가 지시’ 절이다. 필요한 본문만 읽는 것으로 변경하며 기존 전량 읽기 구현을 완료로 보고하지 않는다.

## 필요한 이유와 측정의 한계

정식 데이터 15레벨의 내용을 반복한 1천 레벨 검사에서 JSON 해석·문서 검증이 약 53초였다. 다음 스냅샷 복사 단계에서 WorkingSet 약 6.49GB를 기록하여 검사 전용 보호 장치가 종료했다. 이 결과는 단계별 검사 수치이며 실제 앱의 전체 시작 시간을 측정한 결과가 아니다. 1만 레벨 검증은 여전히 남아 있다.

현재 저장소의 Read는 모든 JSON을 객체로 만들고 ContentSnapshot이 이를 다시 복사한다. 세션 생성도 Snapshot.Documents를 통해 전체를 복사한다. 화면 PrepareDisplay도 다시 전체 문서 사본을 만든다. 조회용 사본으로부터 원본을 보호하는 목적은 유지하되, 수정하지 않은 본문까지 모두 편집 객체로 보관할 필요는 없다.

## 권장 경계

| 구역 | 유지할 정보 | 본문 처리 |
| --- | --- | --- |
| 목록 | 문서 ID·종류·번호·이름·내용 해시 | 편집 본문을 만들지 않는다 |
| 저장 기준 | 검증된 불변 문서 버전과 그 소유 본문 | 읽기 전용 보관소에서 필요할 때 읽는다 |
| 현재 편집 | 선택 레벨과 실제 참조 문서, 변경된 버전 | 조회/수정 계약에 맞게 필요한 문서만 사본 생성 |
| Undo/Redo | 당시의 문서 버전 관계와 선택 상태 | 같은 불변 버전은 공유하고 수정된 버전만 추가 |
| 검사/저장/변환 | 명시적으로 순회하는 문서 스트림 | 전체 JObject 배열로 동시에 펼치지 않는다 |

새 범용 프레임워크를 만드는 대신 기존 ContentSnapshot, AuthoringEditSession, 저장소 및 화면 사이의 문서 조회 경계를 변경한다. 현재 반환값을 수정할 수 있는 Get/Documents 같은 API는 내부 불변 본문을 그대로 노출하지 않는다. 대량 호출부부터 개별 조회/순차 열거로 옮기고 호환 API는 필요한 동안 유지한다.

## 단순히 원본 파일을 나중에 읽으면 안 되는 이유

사용자가 레벨을 편집하는 동안 외부에서 원본 파일이 바뀌어도, 이미 연 세션과 Undo의 내용이 몰래 달라지면 안 된다. 따라서 문서 핸들에 원본 경로만 저장하는 구현은 제외한다.

권장안은 작업공간이 소유하는 불변 본문 보관소다. 원본을 읽을 때 해시와 함께 안정된 바이트를 확보하고, 편집 객체는 필요할 때 만든다. 큰 데이터의 보관소는 사용자별 도구 영역의 디스크를 사용해 메모리 상한을 둔다. 게임 콘텐츠/ZIP에 도구 캐시를 추가하지 않는다. 저장 직전 원본 해시 비교는 계속 수행한다.

보관소 수명은 세션·Undo·복구와 연결한다. 활성 작업이나 복구 기록이 참조하는 본문을 정리하지 않는다. 캐시가 손상되거나 공간이 부족하면 현재 세션을 보존하고 오류를 알리며, 외부에서 바뀐 원본을 대신 읽어 조용히 이어가지 않는다. 정확한 파일 구성은 구현 전 테스트 계약으로 확정한다.

## 검증을 생략하지 않는 열기·저장

1. 새 프로젝트는 임시 로딩 작업공간에서 메타데이터와 본문을 순차 수집한다. 진행량과 취소를 제공하며 기존 편집 세션은 유지한다.
2. 각 문서의 문법/형식 검사와 전체 참조 검사를 수행한다. 필요한 공통 정의·참조 요약을 재사용하며 레벨 본문 전체를 동시에 보관하지 않는다.
3. 검증 성공 후에만 새 세션으로 교체한다. 취소·오류·외부 변경 시 기존 세션을 유지하고 이번 작업의 임시 사본만 정리한다.
4. 저장은 기존 세대별 문서 기록과 project.json의 마지막 원자적 교체를 유지한다. 외부 변경 확인과 기록 결과 검증을 생략하지 않는다.
5. 변경 감지 목적의 전체 JSON 재해석은 해시 비교로 대체 가능한지 검증한다. 실제 새 문서의 형식/참조 검증까지 제거하지 않는다.

지속 인덱스·검증 캐시를 추가하지 않아도 메모리 문제를 먼저 해결할 수 있다. 첫 방문의 전체 검증 시간은 남을 수 있다. 캐시를 추가한다면 내용 해시와 검사 규칙 버전을 키로 하여 외부 수정·규칙 변경 시 무효화해야 하며, 구현 전에 범위를 별도 확정한다.

## 복구와 호환성

- 게임 콘텐츠 JSON 및 ZIP 전달 형식은 유지한다. MemoryPack 변환도 같은 의미의 문서를 받는다.
- 1단계의 현재 레벨만 변경 버리기, 저장 이전 Undo 경계, 공유 문서 원자적 작업을 그대로 보존한다.
- 기존 복구 기록을 계속 읽어야 한다. 복구 읽기/쓰기도 전체 JObject 구성 대신 순차 처리하고 동일 본문 버전의 중복 메모리를 피한다.
- 기존 복구 v1은 상태마다 본문을 반복 기록하므로 파일 크기·처리 시간 문제가 남을 수 있다. 우선 형식 유지로 검증하고, 버전 변경이 필요하면 근거와 이행 방안을 제시한 뒤 별도 확정한다. 이 설계안만으로 복구 형식 변경까지 승인된 것으로 취급하지 않는다.

## 구현 묶음과 통과 조건

### A. 불변 본문 소유권과 조회 경계

외부 수정 격리, 개별 조회 사본, 세션 종료/실패 시 임시 본문 수명부터 검증한다. 선택하지 않은 본문이 외부 수정 때문에 달라지는 경우도 포함한다. public API의 반환값을 변경해도 저장 기준·다른 세션이 바뀌면 실패다.

### B. 목록·편집·이력 연결

메타데이터 인덱스와 선택 레벨을 분리하고, 반복 보드 조작에서 전체 문서 조회/정렬을 없앤다. 1단계의 모든 전환 경로와 부분 취소·Undo/Redo·공유 편집을 회귀 검사한다.

### C. 순차 검사·저장·복구·전달

검증 오류, 외부 변경, 중간 실패/취소가 원본과 현재 세션을 손상시키지 않는지 확인한다. ZIP와 MemoryPack 입력 호환성을 기존 검사로 확인한다.

### D. 동일 조건 전후 측정과 완료 감사

실제 1천/1만 레벨 문서를 사용한다. 준비·첫 표시·전환·저장·복구를 분리하며 첫 실행과 정상 3회, 메모리·측정 가능한 할당량을 기록한다. 보호 한도에서 중단된 기준값은 실패/상한 도달로 표시한다. 100개 진단 수치를 1만 개 성공으로 대체하지 않는다.

기존 2단계는 위 묶음까지 포함해 완료를 판단한다. 소규모 복사 최적화만 하고 전체 목표를 완료 처리하지 않는다. 제품 빌드·커밋·푸시·HTML 매뉴얼 갱신은 하지 않는다.

## 확정 기록

사용자가 1번을 선택했다. 위 권장 구조로 구현한다. 복구 형식 버전 변경과 지속 검사 캐시는 이 승인에 포함되지 않는다.
