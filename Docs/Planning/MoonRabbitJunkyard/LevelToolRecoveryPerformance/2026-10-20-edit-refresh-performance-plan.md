# 레벨툴 화면 갱신·문서 복사 성능 개선 계획

> 실행 담당: `superpowers:executing-plans`로 단계별 구현·검증한다. 하위 에이전트는 별도 승인 없이 사용하지 않는다.

**Goal:** 편집할 때 필요한 화면과 문서만 처리하여 응답 비용을 줄이고 수동 저장·Undo/Redo·입력 보호를 유지한다.

**Architecture:** 화면은 변경 범위에 따라 갱신하고, 표시용 파생 데이터는 의존 문서가 바뀔 때만 다시 만든다. 문서 편집은 변경 대상만 복사하되 게시된 내부 문서의 불변성과 외부 참조 격리를 유지한다. 기존 화면을 전면 교체하거나 새 MVVM 프레임워크를 도입하지 않는다.

**Tech Stack:** 기존 Unity UI Toolkit, C#, Newtonsoft JSON, AuthoringEditSession, 프로젝트 검사 harness.

**Spec:** [목표·완료 조건](../../../Goals/MoonRabbitJunkyard/LevelToolRecoveryPerformance/2026-10-20-edit-refresh-performance-goal.md), [기존 측정·회귀 결과](../../../Verification/MoonRabbitJunkyard/2026-10-20-level-tool-manual-save-stage03.md).

상태: 1~3단계 완료(2026-10-20). 이름 편집 정상 3회 중앙값 62~65ms, 100회 반복 중앙값 64.94ms로 동기 100ms 목표를 충족했다. 다른 조작의 잔여 지연까지 모두 해결했다는 의미는 아니다. 기존 수동 저장 전환 1~3단계와 구분하는 후속 작업이다.

[3단계 계획](2026-10-20-edit-refresh-stage03-plan.md)과 [목표](../../../Goals/MoonRabbitJunkyard/LevelToolRecoveryPerformance/2026-10-20-edit-refresh-stage03-goal.md)의 검증을 마쳤다. [최종 결과](../../../Verification/MoonRabbitJunkyard/2026-10-20-level-tool-edit-refresh-stage03.md)에 대표 조작·메모리·미검증과 후속 후보를 정리했다. 후속 구현은 자동 시작하지 않는다.

- 화면 갱신: 기존 1단계 최종 기록에서 편집 중앙값은 221~227ms, 명령·화면 구간은 57~58ms다.
- 문서 복사: 2단계에서 대상 지정 편집과 호출부 전환·회귀를 완료했다. 데이터 편집 중앙값은 약 14.5ms, 전체 편집은 62~65ms다. [2단계 결과](../../../Verification/MoonRabbitJunkyard/2026-10-20-level-tool-edit-refresh-stage02.md).
- 최종 판정: 3단계에서 대표 조작·100회 반복·새 세션 참조 해제·네 화면 크기를 확인했다. 반복 편집 최대 129ms, 튜토리얼 중앙값 약 1.05초·공유 적용 약 0.89초 및 명시적 저장 약 10초는 남는다.

## 공통 제약

- 커밋·푸시·제품 빌드·HTML 매뉴얼 갱신·코드로 씬/프리팹 편집 금지. 기존 변경과 사용자 파일 보존.
- 편집은 메모리에서 유지하고 명시적 저장만 허용한다. 자동 checkpoint/전체 이력 Export/종료 Flush를 되살리지 않는다.
- JSON 스키마, ZIP 전달, MemoryPack 형식, 게임 규칙은 변경하지 않는다.
- 단계별 보고 후 다음 단계 계획·목표를 최신 상태에 맞춰 작성한다. 다음 구현은 자동 착수하지 않는다.
- 질문이 필요하면 제한시간 없는 문답으로 제시한다.

## 근거와 범위

38문서 고정 입력의 정상 3회 측정에서 편집 중앙값은 750~763ms, 데이터 변경은 148~151ms, 나머지 명령·화면 갱신은 590~595ms였다. 마지막 수치는 순수 렌더 시간은 아니다. 먼저 화면 처리 범위를 줄이고 다음으로 문서 복사를 줄인다.

`LevelToolScreen.Refresh()`는 속성·공급·튜토리얼 패널을 지우고 다시 구성하며 문서 목록 사본과 보드 비교용 JSON 문자열을 반복 생성한다. `AuthoringEditSession.Apply()`는 한 문서 수정에도 전체 문서를 편집 초안으로 복사한다. 게시 후 변경 없는 문서를 공유하는 기존 이력 구조는 유지한다.

수동 저장 9.8~9.9초는 별도 병목이다. 이번 작업에서는 저장 회귀를 검사하지만 저장소 검증·직렬화·게시 자체의 최적화까지 확대하지 않는다. 화면을 떠날 때 남은 Refresh 비용은 1단계 범위에 포함한다.

## 전체 진행: 3단계

| 단계 | 사용자에게 보이는 결과 | 주요 작업 | 단계 판정 |
|---|---|---|---|
| 1. 필요한 화면만 갱신 | 선택·속성 변경 때 무관한 패널을 다시 만들지 않음 | 갱신 의존성, 표시 데이터 캐시, 문자열 비교 제거 | 갱신 누락 없이 불필요한 전체 재구성·표시용 전체 복사 감소 |
| 2. 변경 문서만 복사 | 레벨 한 곳을 고칠 때 다른 문서 수에 따른 비용 감소 | 대상 지정 편집, 문서 조회 범위 축소, dirty 비교 비용 개선 | 격리·원자성·Undo/Redo 유지, 단일 편집의 전체 문서 복사 제거 |
| 3. 성능·회귀 검증 | 이전 기능을 유지하면서 개선량 확인 | 동일 입력 반복 측정, 대표 조작·장기 편집·플랫폼 레이아웃 검사 | 성능 목표와 기능 통과 여부를 별도로 보고 |

1단계에서 2단계 전체 편집 API 개편을 앞당기지 않는다. 필요한 최소 변경 식별 정보만 세션에 추가할 수 있다. 2·3단계 상세 문서는 직전 단계 결과를 반영하여 작성한다.

## 갱신 의존성 기준

| 변경 | 갱신할 부분 | 보존할 부분 |
|---|---|---|
| 선택 칸·브러시·줌 | 선택 표시, 해당 도구 상태, 필요시 속성/보드 배치 | 문서 데이터, 무관한 목록·패널 |
| 레벨 이름·번호 | 제목, 레벨 목록, 해당 필드, 저장 상태 | 보드 셀과 소재 목록 |
| 셀·장애물·연결·공급 편집 | 보드 및 영향받는 속성/공급/검사 상태 | 무관한 레벨 목록·소재 정의 |
| 튜토리얼·공유 문서 적용 | 참조하는 미리보기·속성·보드·파생 정의 | 참조하지 않는 표시 데이터 |
| Undo/Redo | 실제 변경된 문서와 선택 상태에 의존하는 영역 | 무관한 패널 |
| 새 작업·불러오기·복구·재로드 | 세션 캐시 폐기 후 전체 갱신 | 이전 세션 캐시를 재사용하지 않음 |
| 저장 성공/실패·취소 | 상태·명령·오류 안내, 게시 결과의 실제 변경 영역 | 편집 중 입력·선택·스크롤 |

검사 결과는 데이터가 바뀌면 유효하지 않음을 표시하거나 기존 정책대로 다시 검사한다. 오래된 성공 표시를 그대로 유지하지 않는다. 숨긴 패널은 변경 상태를 기억하고 다시 열 때 최신 내용으로 만든다.

## 2단계 방향과 안전 경계

`AuthoringEditSession.cs`, `AuthoringEditSession.State.cs`, 편집 호출부와 공유 튜토리얼 적용 경로를 조사한다. 단일 레벨 편집부터 대상 문서만 복사하는 경로로 옮기고 다중 문서 변경은 하나의 원자적 편집으로 처리한다. 임의 문서 변경을 허용하는 기존 Apply는 호출부를 확인하여 필요한 곳에만 호환 경로로 남긴다.

외부에 내부 `JObject`를 반환해 복사 비용을 없애지 않는다. 표시에는 필요한 요약이나 제한된 사본을 사용한다. 콜백 예외는 부분 반영되지 않아야 하고 콜백이 보관한 초안을 나중에 바꿔도 현재 상태·과거 이력은 변하지 않아야 한다. dirty는 저장 당시 내용으로 Undo하거나 동일 내용으로 돌아왔을 때 해제되는 의미와 project 세대 경로 제외 규칙을 보존한다. 단순 세대 번호 불일치만으로 dirty를 판정하지 않는다.

## 3단계 측정 계약

고정 입력: `Logs/LevelToolRecoveryPerformance/stage01/fixed-ten-record.json` (38문서). SHA256: `0911A4AAAB24D1E39C0C65C843E7FD1E0499455242012EBD163E44B8209688B0`. 사라졌다면 같은 내용의 격리 fixture를 복구하고 해시를 확인하며 사용자 원본을 대체 입력으로 쓰지 않는다.

- 기존과 같은 이름 편집 10회·Undo/Redo·유휴·수동 저장·이탈의 정상 표본 3회. 준비·저장 후 검증은 분리한다.
- 대표 셀 편집, 공급/튜토리얼 변경, 공유 적용, 선택·줌도 별도 표본으로 검사한다. 반복 100회 편집은 작은 묶음으로 측정하여 메모리 추이를 확인한다.
- 최종 목표는 기존 **편집 동기 처리 중앙값 100ms 이하**. 최대값·Undo/Redo·최초/반복 비용도 숨기지 않고 별도 기록한다. 지연 갱신을 사용하면 입력부터 다음 표시 준비 완료까지도 측정하여 타이머 밖으로 비용을 옮기지 않는다.
- 전체 갱신·문서 복사 횟수, working set·관리 힙을 함께 기록한다. 지원되지 않는 누적 할당 카운터는 null이며 Editor update 간격을 렌더 FPS로 부르지 않는다.
- 표본 30초·working set 8GiB 보호 유지. 실패 표본을 보존하고 성공 표본과 섞지 않는다. 자동 프로젝트/복구 기록은 0회여야 한다.
- JSON/ZIP/MemoryPack/게임 시험·과거 복구본 사본 저장 회귀와 보호 파일 검사를 수행한다. 기존 검증을 의미 없이 반복하지 않고 변경 영향에 맞춰 범위를 정한다.

검사는 `Tools/Testing/ProjectTests.ps1 -Action Compile` 및 `-Action Run -Method <검사 진입점>`으로 순차 실행한다. 구체적인 진입점은 기존 검사와 새 검사의 실제 선언을 확인한다. 제품 빌드는 실행하지 않는다.

## 검토 중점

1. 같은 ID의 문서를 다시 불러오거나 Undo했는데 캐시가 남는 문제: 1단계 재로드·Undo/Redo 검사.
2. 숨김 패널의 미확정 입력과 물리 IME 처리: 1단계 입력 경계 검사 및 미검증 표시.
3. 복사 축소로 초안 참조가 현재/과거 상태를 바꾸는 문제: 2단계 참조 격리·예외 원자성 검사.
4. 저장 성공·실패·공유 적용 뒤 dirty가 잘못 바뀌는 문제: 1단계 표시 및 2단계 상태 의미 검사.
5. 지연 처리로 측정상만 빨라지거나 자원이 누적되는 문제: 3단계 표시 준비까지의 시간·반복 메모리 검사.
