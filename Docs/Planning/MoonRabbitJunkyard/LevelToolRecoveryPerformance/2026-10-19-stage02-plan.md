# 복구 성능 개선 2단계 — 이력 사본과 직렬화 비용

> 상태: 2단계 완료. 기능 회귀와 10회 표본 통과, 30회 보호 종료·60회 미실행. 전체 성능 목표는 미달이다. 실행 시 `superpowers:executing-plans` 적용. 1단계 결과를 기준으로 하며 별도 승인 없이 3단계를 시작하거나 하위 에이전트를 사용하지 않는다.

**목표:** 변경되지 않은 문서의 이력 사본과 v1 직렬화의 중간 JSON 트리를 줄이되 Undo/Redo와 외부 수정 격리를 유지한다.

**구조:** AuthoringEditSession 내부에서만 문서 소유권을 명확히 한다. 외부 ContentDocument.Data를 불변이라고 가정하지 않는다. 기존 Workspace/ToolDraftStore와 1단계의 일회용 PreparedDraft를 유지한다.

**기술:** C#, Newtonsoft JSON, 기존 Unity 검사 하네스. 패키지/asmdef/프레임워크 추가 없음.

**기준:** [통합 계획](2026-10-19-plan.md), [2단계 목표](../../../Goals/MoonRabbitJunkyard/LevelToolRecoveryPerformance/2026-10-19-stage02-goal.md), [1단계 실행 기록](../../../Verification/MoonRabbitJunkyard/2026-10-19-level-tool-recovery-performance-stage01.md).

## 1단계에서 확인한 남은 비용

- 동일한 26,414,289바이트 workspace 입력에서 Save는 18.61초→10.65초로 줄었다. 개선 후 ReadPrepared 9.51초, Apply 0.34ms를 관측했다.
- 저장·읽기·적용 이후 전체 상태 검증을 통과했으나 추가 이력 검증 중 30초 보호 종료했다. 저장과 읽기를 포함한 전체 작업의 성능 목표는 아직 충족하지 못했다.
- 소형 표본은 전후 모두 통과했지만 작은 시간 차이는 노이즈가 크며, 모든 경로가 빨라졌다고 주장하지 않는다.
- 구간 분리 측정에서 입력 검증 9.21초, 기존 기록 검증 9.65초, 임시 파일 쓰기 29ms, 바이트 대조 627ms였다. 전체 이력 재구성이 파일 쓰기보다 큰 비용이다.
- Save에는 입력과 기존 파일 검증, Read에는 전체 Session 재구성이 필요하다. 문서 사본/직렬화 비용을 줄이지 않고 검증을 더 제거하는 방향은 취하지 않는다.

## 제약

- 복구 v1과 작성 JSON/MemoryPack 형식, ID, 파일 위치를 유지한다. 새 복구 포맷·압축·차분 파일·이력 개수 제한은 범위 밖이다.
- 미완성 문서, saved/current, dirty, 선택, 전체 Undo/Redo, 공유 사본, 저장 실패와 이전 정상 기록 보호를 보존한다.
- 사용자 자료는 읽기만 한다. 고유 Logs 시험 경로만 사용하며 기존 실행 기록을 덮어쓰지 않는다.
- 제품 빌드·커밋·푸시·HTML·프리팹/씬 편집 금지. Unity 검사 순차 실행, 하네스 연결 중 Assets/Tests 수정 금지.
- 모든 변경은 이력 비용 개선 또는 그 검증에 한정한다. UI 재설계/게임 규칙/데이터 형식 변경을 섞지 않는다.

## 작업 A — 내부 소유권 고정과 이력 공유

대상: `Assets/Scripts/Features/LevelAuthoring/Editing/AuthoringEditSession.cs`, `AuthoringEditSession.State.cs`. 조회/저장 호출부는 실제 참조 경계를 확인하는 데 필요한 만큼만 조사한다.

- [x] Get/Documents/Apply/EditLevel/Fork/Publish/Discard/Capture 및 Snapshot의 문서 반환 방식을 조사한다. 모든 current/saved/undo/redo 쓰기 경로를 목록화한다.
- [x] 외부에서 보관한 편집 콜백 사본·Get 반환 문서·Documents 배열·입력 Snapshot·선택 배열을 나중에 수정해도 세션/과거 이력이 바뀌지 않는 회귀 검사를 먼저 만든다.
- [x] 내부에 게시한 문서는 다시 수정하지 않는 소유권을 보장한 뒤 Capture/Undo/Redo에서 변경되지 않은 문서를 공유한다. State의 선택 배열과 문서 목록 소유권을 별도로 보장한다.
- [x] Apply는 callback 예외/무변경/잘못된 선택 레벨 삭제 시 트랜잭션을 보존한다. 외부 callback 객체를 current에 직접 넣지 않는다.
- [x] 문서 추가·삭제·여러 문서 동시 편집·저장 후 Undo·Undo 뒤 새 편집·Fork/공유 사본 적용·Discard를 검사한다. 변경 동작 하나가 기존과 같은 Undo 단위를 만든다.

결과물은 Session 내부의 공유이며 ContentDocument 전역 API를 불변 객체로 바꾸는 작업이 아니다. 공유가 안전하지 않은 경계는 복사를 유지한다.

## 작업 B — v1 재구성과 직렬화 중간 비용

대상: 위 State 파일과 `AuthoringToolWorkspace.cs`. 필요한 경우 같은 Editing 폴더에 책임이 분명한 전용 코덱을 추가하되, 단순 래퍼/범용 캐시를 만들지 않는다.

- [x] Encode/Decode 및 Workspace↔Session 사이 문자열→JObject→문자열 왕복 비용을 분리 측정한다.
- [x] v1 필드·이력 순서·값을 유지하면서 스트리밍 JsonWriter 또는 기존 JToken 경계의 직접 전달을 선택한다. 작업 A와 측정 결과로 선택 근거를 남긴다.
- [x] Restore 중 같은 문서 내용의 공유가 필요하면 복원 한 건 내부로 범위를 제한한다. ID만 같다고 공유하지 않으며 kind/내용까지 같아야 한다. 해시 사용 시 충돌을 검증한다.
- [x] 복원 거절 조건을 줄이지 않는다. saved는 유효 문서, current/이력은 기존에 허용한 작성 중 오류 범위를 유지한다. 선택/ID/중복/버전/공유 초안 손상 사례로 비교한다.
- [x] 과거 v1 fixture와 신규 출력이 기존 읽기 의미를 유지하는지 확인한다. 의미 비교와 바이트 비교를 구분하고 예기치 않은 포맷 변경은 보고한다.

## 작업 C — 전후 비교·회귀·다음 단계 준비

- [x] 기존 고정 10회 입력 해시를 사용해 Export/Save/Read/Apply와 전체 상태·실제 Undo/Redo를 비교한다. 초기화/fixture 복사/검증 시간과 실제 경로 시간을 분리한다.
- [x] 실제 편집 10→30→60회 검사는 이전 표본이 보호 한도 안에서 완료한 경우만 확대한다. 30초 또는 8GiB 한도 도달 시 더 큰 표본을 실행하지 않는다.
- [x] 소형/손상/실패/공유 초안/입력/전체 전송 복구 검사 및 컴파일을 순차 실행한다. 정상 표본의 반복 측정은 3단계에서 통합한다.
- [x] 보호 파일 해시·meta GUID·변경 범위·diff 검사를 확인하고 측정 한계를 보고한다.
- [x] 구조 문서를 갱신하고 3단계 상세 계획·목표·복사 가능한 실행문을 작성한다. 자동 구현하지 않는다.

기존 검사 재사용: LevelToolRecoveryPreparedVerification.Run, LevelToolTransferRecoveryVerification.RunAll, LevelToolRecoveryCostVerification.RunSmall/RunFixedTen/RunFixedTenHistory, JsonEditingVerification/JsonWorkspaceVerification 관련 사례. 실행 전 fixture/출력 안전성과 실제 진입점 존재를 확인한다.

성능 제안 목표는 통합 계획을 유지한다. 2단계에서도 목표 미달이면 검증 제거/이력 축소/기준 완화로 합격시키지 말고 실측 결과와 남은 병목을 보고한다.
