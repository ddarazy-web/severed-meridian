## 목표와 범위

8단계의 초기 후보를 읽고 완성 매칭과 가능한 행동을 조회한다. 고정 배치를 보존하면서 시작 조건을 만족하는 구성을 제한된 탐색으로 찾고, 기존 **Match → 초기 보드 확인** 화면에서 결과와 근거를 확인한다.

성공 기준은 **완성 매칭이 없고 유효한 교환이 최소 하나 있음**이다. 제자리 파워 발동만 있는 상태는 가능한 행동이 있지만 시작 조건은 미충족이다. 이는 게임 도중 자동 재배치의 “교환 또는 파워 발동” 조건과 다르다.

이번 완료는 시작 조건의 정적 검사/구성 완료다. 실제 교환 실행·블록 제거·파워 생성/효과·낙하·공급·승패는 실행하지 않는다. 조건 통과를 클리어 가능성이나 난이도 판정으로 표현하지 않는다. 튜토리얼의 지정 교환 제한도 아직 데이터/실행 계약이 없으므로 이번 일반 시작 조건 검사에 포함하지 않는다.

## 현재 코드에서 확인한 사실

- `Simulation/LevelStateBuilder.Build`는 v4 구조를 검사하고 원본과 독립된 초기 후보를 만든다. 매칭·행동·시작 조건은 검사하지 않는다.
- `LevelRuntimeState`는 칸/본체/덮개/먼지/흐름·벽/연결/공급/미션 상태를 제공한다. 초기 지정과 실제 점유가 분리되어 있다.
- 명시된 `FixedNormal`과 파워 블록은 유지하고, 무작위 일반 및 비점유 활성 칸을 레벨 사용 색으로 채운다. 초기 고정은 이동 잠금이 아니다.
- `SimulationRandom`은 상태별 System.Random과 추출 횟수를 가진다. 조회를 반복한다고 난수가 소비되면 재현 계약을 깨뜨린다.
- `LevelInitialStateWindow`는 읽기 전용 후보를 표시하고 입력 변경 시 이전 결과를 지운다. 이 동선을 확장한다.
- 저장 정의는 v4이며 기존 구조 검사와 오류 데이터 저장 정책을 유지해야 한다. 8단계의 160개 검증 기록은 선행 증거다.

## 대안과 추천

| 대안 | 장점 | 비용·위험 | 판단 |
| --- | --- | --- | --- |
| 실제 제거/낙하까지 구현해 결과를 관찰 | 플레이에 가까움 | 아직 없는 효과·공급 규칙까지 의존함 | 후속 단계 |
| 무작위 보드 전체를 계속 재추첨 | 코드가 짧음 | 3색·큰 보드에서 기존 매칭을 피하기 어려워 시도 낭비가 큼 | 단독 전략으로 사용하지 않음 |
| 순수 조회 + 제약을 확인하며 제한된 후보 탐색 | 원본/난수 보호, 실패 이유 구분, 재현 가능 | 탐색 상한과 고정/변수 칸 구분 필요 | 추천 |

조회 로직은 향후 실제 교환 판정에서도 공유한다. 이번에는 필요한 매칭/행동 책임만 분리하고, 모든 장애물 효과를 처리하는 매니저나 범용 규칙 등록소는 만들지 않는다.

## 매칭 조회 계약

입력 상태를 변경하지 않고 패턴 종류·색·구성 좌표·직선 방향·연결된 파워 종류를 반환한다. 좌표/결과 순서는 고정하며 같은 패턴을 중복 반환하지 않는다.

| 대상 | 판정 |
| --- | --- |
| 일반 달토끼 | 같은 색만 연결. 색 없는 파워/장애물/회수 부품은 참여하지 않음 |
| 거미줄 내부 일반 블록 | 이동은 불가하지만 매칭에는 참여 |
| 곰팡이 내부 일반/파워 | 매칭 및 직접 조작에서 제외 |
| 먼지 | 매칭/교환을 막지 않으며 조회로 내구도가 변하지 않음 |
| 비활성/빈칸/고철 벽 | 매칭 연결을 끊음. 그 너머를 하나의 직선으로 잇지 않음 |
| 직선 3 | 일반 매칭 |
| 직선 4 | 가로 매칭→세로 로켓, 세로 매칭→가로 로켓 |
| 직선 5 이상 | 최대 연속 구간 하나를 자석 패턴으로 조회. 6개를 여러 5개로 중복 반환하지 않음 |
| ㄱ·ㄴ·T | 기존 3×3 기준의 5칸 모양, 모든 회전/반사 방향을 검사. 같은 색 연결군이면 무조건 폭탄으로 판정하지 않음 |
| 2×2 | 네 칸만으로 유효. 바깥 같은 색이 붙어도 네 칸 패턴을 인정. 내부 네 경계 중 하나라도 벽이면 불가 |

ㄱ·ㄴ·T의 실제 연결 경계에도 벽이 없어야 한다. 통로·전선·낙하 경로는 매칭 연결선을 대신하지 않는다.

겹친 패턴은 구성 좌표를 각각 보존한다. 표시/분류용 우선순위는 자석 > 폭탄 > 로켓 > 드론이다. 조회에서 모든 좌표를 합쳐 제거 범위라고 반환하지 않는다. 동률 무작위 선택·생성 위치·실제 제거는 후속 실행 단계 책임이다. **조회는 동률 해소를 위해 난수를 쓰지 않는다.** 시작 검사에는 유효 패턴이 하나라도 존재하는지만으로 충분하다.

## 교환과 제자리 발동 조회

### 공통 제약

- 상하좌우 인접한 활성 칸 두 곳이며 둘 다 이동 가능한 점유자가 있어야 한다. 빈칸·같은 칸·대각선·범위 밖·벽 너머 교환은 불가다.
- 일반/노출 파워/고철 뭉치/회수 부품은 이동 후보다. 고정 장애물과 덮개가 있는 블록은 교환할 수 없다.
- 일반 블록의 초기 고정 색 지정은 교환을 막지 않는다. 먼지·중력·통로·도착 바닥은 교환 잠금이 아니다.
- 임시 조회 뷰 또는 독립된 작업 사본에서 교환 결과를 읽는다. 입력을 바꾼 뒤 되돌리는 방식으로 공유 상태에 순간적인 변경을 노출하지 않는다.
- 일반 교환은 **교환으로 새로 완성된 패턴이 교환 도착 칸 중 하나를 포함**해야 유효하다. 다른 곳에 이미 있던 매칭이나 같은 색끼리 바꾸어 그대로 남은 매칭으로 허용하지 않는다.
- 결과는 허용 여부, 이유 코드/한국어 설명, 두 좌표, 새 매칭 또는 파워 발동/조합 종류를 담는다. 피해량·목표 기여·클리어 여부는 계산하지 않는다.

### 대상별 허용 표

| 교환 대상 | 조건 |
| --- | --- |
| 일반 ↔ 일반 | 새 매칭이 성립할 때 |
| 일반 ↔ 고철/회수 부품 | 이동한 일반 블록으로 새 매칭이 성립할 때 |
| 고철/회수 ↔ 고철/회수 | 매칭/파워 발동을 만들지 않으므로 불가 |
| 로켓/폭탄/드론 ↔ 일반·고철·회수 | 매칭 없이 파워 발동 가능 |
| 자석 ↔ 일반 | 교환한 일반 블록의 색 제거 발동 가능 |
| 자석 ↔ 고철·회수 | 취소 대상, 불가 |
| 로켓/폭탄/드론 ↔ 파워 | 해당 조합 가능. 자석이 포함되면 아래 예외 우선 |
| 자석 ↔ 로켓/폭탄/드론 | 대상 가능한 일반 블록이 보드에 하나 이상 있을 때 |
| 자석 ↔ 자석 | 일반 블록이 없어도 조합 가능 |

파워끼리의 열 가지 순서 없는 조합을 빠짐없이 다룬다. 개별 조합의 폭발 범위는 실행하지 않는다. 덮개/벽/인접 제약은 파워 교환에도 적용한다.

제자리 발동은 교환과 별도 행동으로 반환한다. 덮개 없는 로켓/폭탄/드론은 가능하고 자석은 대상 일반 블록이 있어야 가능하다. 자석의 일반 대상에는 거미줄 내부 일반 블록을 포함하고 곰팡이 내부는 제외한다. 이번 조회에서는 제거 색을 무작위 선택하지 않는다.

전체 행동 조회는 교환 쌍을 중복 집계하지 않고 제자리 발동은 좌표별로 구분한다. 양쪽 교환 좌표를 유지해 후속 입력 방향을 잃지 않게 한다. 읽기 전용 조회는 이동 수·미션·내구도·공급·난수에 영향을 주지 않는다.

## 시작 조건 검사와 생성 정책

### 결과 상태

| 결과 | 뜻 |
| --- | --- |
| 정의 오류/미지원 | 기존 구조/버전 문제. 탐색을 시작하지 않음 |
| 시작 조건 통과 | 완성 매칭 0개, 유효한 교환 최소 1개. 교환 증거 좌표를 제공 |
| 현재 후보 미충족 | 완성 매칭 있음 또는 유효 교환 없음. 후보 검사 결과이며 불가능 판정은 아님 |
| 고정 조건 위반 | 변경 불가 칸만으로 이미 완성된 매칭 등, 고정 조건에서 위반이 증명되는 경우 |
| 전체 고정 미충족 | 바꿀 일반 색 칸이 없고 현재 상태가 조건을 만족하지 않음. 한 번 검사하고 종료 |
| 탐색 한도 도달 | 정해진 작업량 안에 찾지 못함. 해결 불가능이라고 단정하지 않음 |

마지막 실패 후보와 진단을 표시할 수 있지만 성공 상태로 반환하지 않는다. “검사 실패”와 “정의 오류”도 구분한다.

### 재구성 범위와 절차 제안

1. 기존 빌더로 독립 후보와 정의 진단을 만든다. 8단계 원시 후보 API의 동작을 보존한다.
2. 명시된 고정 일반/파워, 장애물·회수 부품, 활성 칸·덮개·먼지·바닥·공급·연결을 고정한다.
3. 명시적 무작위 일반 및 초기 자동 채움 일반 칸만 변수로 삼는다. 초기 구성 중이므로 그 칸에 덮개가 있어도 정의가 무작위라면 색을 정할 수 있다. 플레이 중 섞기와 다른 정책이다.
4. 첫 후보가 시작 조건을 만족하면 그대로 반환한다. 변경할 수 없는 매칭과 전체 고정 실패는 진단 후 종료한다.
5. 변수 칸은 고정 순서로 방문하고 색 후보 순서를 균등하게 무작위 섞어 검사한다. 완성 매칭이 생기는 분기는 버리고 필요한 경우 변수 칸만 되돌아간다. 부분 할당의 미정 색을 실제 일반 색으로 판정하지 않는다.
6. 완성된 후보에 유효 교환이 없으면 다른 할당을 탐색한다. 성공한 후보만 독립 결과로 반환한다.
7. 최초 제안 상한은 **색 할당 시도 100,000회**다. 매 시도마다 세고 실제 수행 수/상한을 결과에 기록한다. 제작자 옵션은 추가하지 않는다. 구현 시 10×10의 실제 비용을 측정해 조정하면 근거와 최종 값을 목표 문서에 기록한다.

색 후보 제안은 선택된 종류 안에서 균등하게 섞는다. 매칭 배제 조건이 적용된 최종 보드를 “각 칸 독립 균등분포” 또는 “모든 유효 보드에 균등분포”라고 주장하지 않는다. 실제 플레이 중 무작위 공급의 균등 규칙은 바꾸지 않는다.

탐색은 횟수로 제한하고 성공/한도 판정을 벽시계 시간에 의존시키지 않는다. 화면이 멈추지 않게 필요하면 작은 작업 단위로 나누되, 프레임 분할에 따라 방문 순서·난수·결과가 바뀌면 안 된다. 실행 중 레벨/시드 변경·창 닫기는 결과를 폐기하고 오래된 결과가 새 입력에 적용되지 않게 한다. 별도 자동 플레이 실행기나 스레드 풀은 도입하지 않는다.

입력 정의 지문·시드·조회/탐색 알고리즘 버전·할당 시도 수를 기록한다. 탐색은 작업용 난수를 사용하고 성공 상태의 난수 진행을 함께 보존한다. 실패가 원본/이전 후보의 난수 상태를 바꾸면 안 된다. 같은 환경의 독립 프로세스에서도 같은 결과와 종료 이유가 재현되어야 한다.

| 기존 Editor/Levels/LevelInitialStateWindow.cs 및 USS | 후보/검사 결과와 좌표 강조, 입력 변경·진행 상태 처리 |
| Editor/Levels의 검증 코드 | 규칙 표, 실패, 재현, 실제 화면, 기존 기능 회귀 |

새 스크립트는 `Assets/Scripts` 아래 책임별로 둔다. 파일명은 역할 제안이며 작은 값 타입 때문에 빈 계층·폴더를 늘리지 않는다. 실행부에 Editor API를 넣지 않고 아트/새 패키지/asmdef/게임명 폴더를 추가하지 않는다.

기존 화면에 **원시 후보 / 시작 조건 구성** 두 목적을 명확히 구분하는 간단한 선택과 기존 시드/구성 버튼을 연결한다. 원시 후보는 유지하고 검사 결과를 함께 표시한다. 별도 대형 도구 창이나 고급 설정을 늘리지 않는다.

- 조건 검사 결과, 매칭 수·유효 교환 수·제자리 발동 수, 실패 이유, 탐색 횟수 표시.
- 매칭/행동 목록을 선택하면 관련 칸 강조. 새 조작을 실행하는 것이 아닌 조회임을 명시.
- 중첩 패턴은 별개 목록으로 표시하며 합집합을 실제 제거 범위로 보여주지 않음.
- 성공 문구는 **시작 조건 통과 · 실제 플레이 미지원**. 기존 “시작 조건 미검사”를 무조건 남겨 성공과 충돌시키지 않음.
- 실패/입력 변경 시 이전 통과 표시를 지움. 1000×780/680×480에서 결과·진단·마지막 칸 접근 확인.

## 검증 계획

| 범위 | 필요한 검사 |
| --- | --- |
| 패턴 | 직선 3/4/5/6+, ㄱ·ㄴ·T의 모든 방향, 독립 2×2/추가 이웃/중첩, 비슷하지만 성립하지 않는 모양 |
| 연결 | 비활성·빈칸·각 벽 방향, 2×2 내부 네 벽 각각, 통로 너머 잘못된 연결 거절 |
| 층 | 거미줄 일반의 참여/교환 금지, 곰팡이 일반 제외, 덮인 파워 금지, 먼지 영향 없음 |
| 행동 | 일반/고철/회수/파워 표 전체, 열 가지 파워 조합, 자석 대상 없음·거미줄만 있음·곰팡이만 있음 |
| 교환 원인 | 별도 위치의 기존 매칭으로 허용하지 않음, 같은 색 교환 거절, 한쪽/양쪽 신규 매칭, 2×2만 완성되는 교환 |
| 시작 조건 | 매칭 0+교환 있음 통과, 제자리 파워만 있으면 미충족, 고정 위반·전체 고정 실패·상한 구분 |
| 생성 | 3~5색/전체·부분 고정/전체 무작위/비정형, 고정 요소 보존, 불가능 예제에서 유한 종료 |
| 재현 | 반복 조회가 상태/난수 불변, 같은 입력·시드·알고리즘의 반복/독립 프로세스 결과 일치 |
| 독립 오라클 | 손으로 정한 좌표/허용 결과를 기준으로 검사. 구현의 같은 함수 두 번 호출만으로 정답을 주장하지 않음 |
| 화면/회귀 | 실제 결과/강조/실패/입력 변경·창 종료/좁은 창, 8단계 원시 후보·독립성·재현 및 영향 범위 기존 편집 검사 |

상한 검사에는 의도적으로 작은 내부 테스트 한도를 주입할 수 있지만 사용자 설정으로 노출하지 않는다. 임시 데이터는 검증 소유 폴더에서 만들고 기존 사용자 에셋·JSON/dirty·GUID/meta를 보존한다. 성능은 측정 결과로 기록하며 미실행 플랫폼 검증을 완료로 표시하지 않는다.

## 구현 순서 제안

1. 위 규칙 표와 현재 상태 표현을 대조하고 조회 입력/결과 및 원본 보존 기준을 확정한다.
2. 매칭 조회와 손으로 지정한 패턴 예제를 검증한다.
3. 가상 교환/제자리 발동 조회와 대상별 예외 표를 검증한다.
4. 시작 조건 검사와 제한 탐색을 연결해 고정 보존·실패 분류·시드 재현을 확인한다.
5. 기존 확인 화면에 연결하고 실제 Unity UI·별도 재시작·필요한 회귀를 검증한다.
6. 완료 조건별 증거·최종 탐색 상한·사용법·남은 한계를 목표 문서에 기록한다.

이 문서는 구현 제안이며 Goal 실행 요청 후 작업 의존성과 파일 책임을 구체화한다. 문서 작성 자체로 코드 구현이나 에이전트 위임을 시작하지 않는다.

후속 단계는 실제 한 수의 교환/매칭 처리다. 조회 결과를 공유하면서 패턴 중첩 우선순위·동률 난수·파워 생성 위치·피해 처리를 실행하고, 이후 낙하/공급·미션 진행을 연결한다.
