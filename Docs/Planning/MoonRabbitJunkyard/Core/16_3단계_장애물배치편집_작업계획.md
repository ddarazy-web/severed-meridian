## 1. 목표와 조사 결과

제작자가 기존 10×10 보드에서 장애물·덮개·먼지·초기 파워 블록을 구분하여 배치하고, 내구도 등의 속성과 2×2 점유 영역을 편집할 수 있게 한다. 배치·충돌 검사·Undo/Redo·저장 보존까지가 완료 범위다. 매칭이나 장애물 파괴가 실행되는 게임을 만드는 단계는 아니다.

현재 구현에서 확인한 사실은 다음과 같다.

- `LevelDefinition`의 저장 형식 버전은 1이며, 레벨 설정·보드·초기 일반 블록 목록을 소유한다.
- `InitialBlockKind`의 기존 저장값은 `RandomNormal = 0`, `FixedNormal = 1`이다.
- `LevelBoardEditing`은 일반 블록만 조회하고 수정한다. 여러 층과 2×2 점유를 아직 판정하지 않는다.
- `LevelBoardView`는 100칸 표시, 포인터 캡처, 방문 칸 미리보기와 확정을 제공한다.
- `LevelEditorWindow`는 UI Toolkit 창, 단일 칸 속성, 오류 이동, 외부 Inspector 변경 동기화를 제공한다.
- `LevelDefinitionValidator`는 데이터를 변경하지 않고 오류 코드·필드 경로·좌표를 반환한다.
- 2단계 기록에는 UI·재시작·1단계 회귀 검증 총 130개 통과가 남아 있다. 이후 메뉴를 `Match/레벨 에디터`로 변경했으며 메뉴 변경 후 실제 실행은 재검증하지 않았다. 3단계 검증에 새 메뉴 실행을 포함한다.

현재 부족한 부분은 그림 리소스가 아니라 **층별 배치 모델과 점유 판정**이다. 먼저 이 경계를 정해야 일반 블록 칠하기가 장애물을 덮어쓰거나 2×2 본체의 일부만 삭제하는 문제를 막을 수 있다.

## 2. 포함 범위와 후속 경계

| 이번 단계 | 후속 단계 |
| --- | --- |
| 나무상자·고철 뭉치·금고·색깔 자물쇠 | 장애물 피해·제거·낙하·교환 실행 |
| 거미줄·우주 곰팡이 덮개 | 곰팡이 확산과 미션 수량 갱신 |
| 바닥 먼지와 다른 층의 독립 편집 | 중력·경로·벽·통로·도착 바닥: 4단계 |
| 대형 폐가전·발전기의 2×2 배치·이동·삭제 | 발전기 연결 대상·전선·충전 실행: 연결 편집은 4단계 |
| 초기 청소로켓·달폭탄·수거드론·무지개 자석 | 파워 생성·발동·조합·드론 목표 관리 |
| 단일 요소 속성, 충돌 검사, 형식 전환 | 다중 선택·공통 인스펙터·설정 복사: 후속 편집 완성 단계 |
| 저장·재시작·Undo/Redo·기존 편집 회귀 | 생성구·공급 목록·회수 부품·미션: 5단계 |

- 초기 파워 배치는 거미줄·곰팡이가 파워 블록도 덮는다는 확정 규칙을 편집할 수 있도록 이번 단계에 포함하는 제안이다. 발동 로직은 포함하지 않는다.
- 발전기는 본체와 필요 충전량만 편집한다. 화면에 `연결 편집은 4단계에서 지원`이라고 표시하고, 미연결 발전기를 완성된 플레이 데이터로 판정하지 않는다. 아직 없는 연결 필드나 빈 연결 도구는 만들지 않는다.
- 장애물 등장 레벨, 해금 순서, 튜토리얼은 정하지 않는다.
- 정식 이미지·애니메이션·씬·프리팹·새 패키지는 필요 없다. 기호·문자·윤곽·숫자로 확인한다.

## 3. 방식 비교와 추천

| 방식 | 장점 | 비용과 위험 |
| --- | --- | --- |
| 기존 한 칸/블록 구조에 모든 속성을 추가 | 처음 수정할 파일이 적음 | 덮개·바닥·2×2 본체의 수명과 점유를 혼동하기 쉬움 |
| 요소마다 별도 ScriptableObject 또는 씬 오브젝트 생성 | 요소를 개별 선택하기 쉬움 | 한 레벨의 저장·Undo·참조 관리가 복잡해짐 |
| 한 레벨 에셋 안에 층별 배치 기록 저장 | 기존 저장 흐름 유지, 다른 층을 독립 편집 | 층간 호환성과 점유 검사가 필요함 |

**세 번째 방식을 추천한다.** 초기 블록, 공간 점유 장애물/장치, 덮개, 먼지를 분리한다. 목록이 저장 원본이며 좌표 조회와 점유 영역은 계산 결과다. 범용 장애물 플러그인 시스템이나 규칙 매니저는 만들지 않는다.

## 4. 편집 가능한 종류와 값

| 편집 층 | 종류 | 점유 | 제작자가 입력할 값 |
| --- | --- | --- | --- |
| 블록 | 고정/무작위 일반 블록 | 1칸 | 기존 색/무작위 설정 |
| 블록 | 청소로켓 | 1칸 | 가로 또는 세로 제거 방향 |
| 블록 | 달폭탄·수거드론·무지개 자석 | 1칸 | 종류만 |
| 장애물/장치 | 나무상자 | 1칸 | 내구도 1~6 |
| 장애물/장치 | 고철 뭉치 | 1칸 | 내구도 1~5 |
| 장애물/장치 | 잠긴 고물 금고 | 1칸 | 내구도 1~5 |
| 장애물/장치 | 색깔 자물쇠 | 1칸 | 내구도 1~3, 레벨 사용 색 중 하나 |
| 장애물/장치 | 대형 폐가전 | 2×2 | 공유 내구도 1~9 |
| 장애물/장치 | 고장 난 발전기 | 2×2 | 필요 충전량 3~5 |
| 덮개 | 거미줄 | 1칸 | 내구도 1~3 |
| 덮개 | 우주 곰팡이 | 1칸 | 내구도 1 고정 |
| 먼지 | 바닥 먼지 | 1칸 | 내구도 1~3 |

- 파워에는 달토끼 색을 부여하지 않는다. 로켓 방향은 그림 방향이 아니라 제거할 행/열 기준으로 표기한다.
- 고철이 이 편집 층에 속한다고 런타임에서 고정 장애물로 취급하는 것은 아니다. 고철은 이동 가능한 장애물이라는 기존 규칙을 유지한다.
- 기본값 제안: 새 장애물·거미줄·먼지는 내구도 1, 발전기는 필요 충전량 3, 로켓은 가로, 자물쇠는 현재 사용 색의 첫 항목. 유효한 색이 없으면 자물쇠 신규 배치를 막는다.
- 본체 내구도와 발전기 필요 충전량을 구분한다. 현재 피해량·현재 충전량·확산 이력 같은 플레이 상태는 저장하지 않는다.

## 5. 배치와 층간 충돌 계약

### 공통

- 신규 배치는 활성 칸에만 허용한다. 비활성화는 어느 층의 기록도 지우지 않고 오류로 표시한다.
- 블록과 공간 점유 장애물/장치는 같은 칸을 공유할 수 없다. 서로 다른 점유 장애물도 겹칠 수 없다.
- 같은 종류의 정상적인 1칸 요소를 다시 칠하면 해당 속성만 갱신한다. 일반 블록끼리 교체는 기존처럼 허용한다. 다른 장애물 종류나 일반/파워 간 교체는 명시적으로 해당 층을 지운 후 배치하는 방식을 제안한다.
- 실패한 배치는 다른 요소를 밀거나 삭제하지 않으며 이유를 표시한다. 일부 적용되는 드래그는 적용/제외 칸 수와 제외 이유를 보여준다.
- 한 칸의 중복 기록을 임의의 첫 항목으로 해석하지 않는다. 충돌 층은 보드에서 수정하지 않고 기존 Inspector 원본 목록으로 정리하도록 안내한다. 다른 정상 층·칸 편집은 가능하게 한다.

### 덮개

- 일반 블록 또는 파워 블록 위에만 거미줄/곰팡이를 배치한다. 무작위 일반 블록 표식도 일반 블록으로 인정한다.
- 같은 칸에는 덮개 하나만 허용한다. 거미줄과 곰팡이는 공존하지 않는다. 고철·상자·금고·자물쇠·2×2 장치 위에는 씌우지 않는다.
- 덮개 추가·속성 변경·삭제는 내부 블록 종류·색·로켓 방향을 바꾸지 않는다.
- 내부 블록만 지우면 덮개 기록은 남고 `내부 블록 없음` 오류가 된다. 편집 도중 불완전한 상태의 저장은 허용한다. 일반/파워 블록을 다시 넣으면 해결된다.
- 편집기에서는 덮개 표식과 내부 블록 정보를 구분하여 확인할 수 있다. 곰팡이 속 블록을 플레이어에게 숨기는 게임 화면 규칙은 별개다.

### 먼지

- 먼지는 다른 층과 독립적인 바닥 기록이다. 빈 활성 칸, 일반·파워, 덮개, 공간 점유 장애물과 중첩을 허용한다. 발전기 아래 먼지도 편집에서 허용하는 제안으로 둔다.
- 먼지 삭제는 위쪽 내용물에 영향을 주지 않는다. 위쪽 요소 삭제·이동도 먼지를 옮기거나 삭제하지 않는다.
- 2×2 아래 먼지는 칸마다 독립적으로 최대 네 기록이다. 본체의 공유 내구도와 섞지 않는다.

### 2×2

- 왼쪽 위 기준 좌표 하나와 종류·공유 속성으로 저장한다. 네 칸에 본체를 네 번 저장하지 않는다.
- 배치 도구에서 네 칸 미리보기를 표시하며 클릭 한 번으로 설치한다. 드래그 연속 칠하기 대상에서 제외한다.
- 네 칸 모두 활성이고 보드 안이며 점유 충돌이 없어야 한다. 하나라도 실패하면 설치 전체를 취소한다.
- 어느 점유 칸을 선택해도 같은 본체를 선택하고 네 칸을 강조한다. 어느 점유 칸에서 삭제해도 해당 본체 전체를 삭제한다. 먼지는 남는다.
- 이동은 선택한 본체의 `이동` 도구로 목적 기준 칸을 클릭하는 두 단계 조작을 제안한다. 기존 자기 점유는 제외하여 검사하고 유효할 때 기준 좌표만 변경한다. 이동 중 원본은 유지하고 실패·Esc·포커스 상실 시 취소한다.
- 자기 자리 이동은 변경 없는 작업이다. 이동 후 저장·Undo/Redo에서 하나의 본체와 공유 속성이 유지되어야 한다.
- 발전기 전선 삭제·경로 재지정은 연결이 생기는 4단계에서 함께 구현한다.

## 6. 화면과 편집 경계

- 진입 메뉴는 **Match → 레벨 에디터**를 유지한다. 별도 창이나 Tools 하위 메뉴를 만들지 않는다.
- 왼쪽에 편집 층과 종류를 구분하고, 오른쪽에는 선택한 층의 단일 요소 속성만 보여준다. 한 칸에 여러 층이 있어도 선택 대상이 모호하지 않게 층 이름을 표시한다.
- 보드에서는 블록/장애물 기호, 내구도 숫자, 덮개 윤곽, 먼지 가장자리 표시를 함께 읽을 수 있게 한다. 로켓은 가로/세로 화살표를 사용한다. 2×2는 하나의 외곽선과 본체 이름·공유 값을 보여준다.
- 삭제는 현재 편집 층에만 적용한다. `칸 전체 비우기`는 이번 단계에 추가하지 않는다.
- 1칸 도구의 클릭·드래그는 2단계 입력 계약을 재사용한다. 정상 종료 때 한 번 적용하며 한 드래그는 Undo 한 번이다. 유효하지 않은 칸은 제외하고 정상 칸만 반영한다.
- 저장·검사·도구/층 변경·Undo/Redo·외부 변경·에셋 변경·창 닫기 때 미완료 미리보기를 취소한다. 중복 적용과 다른 에셋으로의 적용을 막는다.
- 속성은 Unity 직렬화와 Undo를 사용한다. 동일 값 적용과 실패 작업은 dirty/Undo를 만들지 않는다. 숫자 입력은 기존 지연 입력 방식을 유지한다.
- 사용 색을 바꾸어 자물쇠 색이 미사용이 되어도 자동 변환하지 않는다. 오류를 표시하고 제작자가 수정하게 한다.
- 좁은 창, 외부 Inspector, 재시작, 지원하지 않는 버전·손상된 보드 처리도 기존 계약을 유지한다.

## 7. 모델·책임과 저장 호환성 제안

### 모델 구성

- `InitialBlockDefinition`은 일반/파워 블록만 담당한다. 기존 종류 값 0·1을 유지하고 파워 종류를 뒤에 추가하며 로켓 방향을 별도 값으로 둔다. 기존 `fixedColor` 저장값을 불필요하게 삭제하거나 재해석하지 않는다.
- 점유 장애물/장치는 종류·기준 좌표·초기 내구도, 자물쇠 색, 발전기 필요 충전량을 가진 배치 기록으로 묶되 종류별 의미 있는 속성만 노출한다.
- 덮개와 먼지는 각각 독립 기록으로 둔다. 단순 열거형과 값 구조는 관련 파일에 함께 두어도 된다.
- `LevelDefinition`은 이 목록들의 저장 루트다. 저장된 점유 배열·화면 선택 상태·런타임 객체를 추가하지 않는다.
- 점유 범위와 층간 호환성은 순수한 조회/판정 코드에서 계산한다. 편집 미리보기·확정·검사기가 이 기준을 공유하고, UI 코드 안에 규칙을 복제하지 않는다.
- 100칸 보드에 필요한 정도의 순회/임시 조회만 사용한다. 전역 매니저·등록 레지스트리·DI·범용 상속 체계·새 asmdef는 도입하지 않는다.
- 발전기 연결용 식별자와 연결 모델은 실제 연결을 구현할 4단계에서 정한다. 이번에는 무의미한 연결 필드를 미리 저장하지 않는다.

### 저장 형식

- 새 배치 종류와 목록을 추가하므로 새 에셋은 버전 2를 사용한다. 버전 1을 자동으로 최신으로 간주하거나 `OnEnable`/`OnValidate`에서 변환하지 않는다.
- 기존 버전 1은 읽기·검사·보기 경로를 유지하며 새 편집은 명시적인 `3단계 형식으로 전환` 이후 허용하는 안이다. 버전 호환 상태와 전환 필요를 구조 오류와 구분하여 설명한다.
- 전환은 선택한 레벨 하나에만 적용한다. 레벨 번호·이동 횟수·색·칸·초기 배치·알 수 없는 원본 값·GUID를 그대로 보존하고 새 목록을 비어 있는 상태로 추가한다. 버전 1에 예상 밖 신규 데이터가 존재하면 덮어쓰지 않고 전환을 중단하여 사유를 표시한다.
- 전환 한 번은 Undo 한 번이며, 자동 디스크 저장은 하지 않는다. 명시적으로 저장 후 별도 Editor 재시작에서 보존을 검사한다.
- 미지원 버전은 자동 다운그레이드하지 않는다. 일반적인 마이그레이션 프레임워크나 프로젝트 전체 일괄 변환은 만들지 않는다.
- 기존 검증의 버전 기대값을 바꿀 때에는 실제 버전 1 직렬화 형태를 불러오는 호환성 검사를 남긴다. 모든 검증 데이터를 새 생성 함수로만 만들고 호환성 통과라고 보고하지 않는다.

## 8. 오류 검사와 위험 대응

- 종류·내구도·충전량·로켓 방향·자물쇠 색의 유효성을 검사한다. 범위를 벗어난 기존 값을 자동 clamp하지 않는다.
- 범위 밖·비활성·누락 칸, 같은 층 중복, 서로 다른 점유층 충돌, 2×2 네 칸의 범위/활성/중복 점유, 덮개 내부 누락과 금지 중첩을 검사한다.
- 좌표·목록 인덱스·필드 경로를 유지한다. 2×2 오류는 본체와 문제 칸을 구분할 수 있게 표시한다. 가능한 영역을 강조하되 범위 밖 좌표를 가까운 칸으로 보정하지 않는다.
- Inspector로 만든 잘못된 기록도 저장·재시작 시 그대로 남겨 수정할 수 있게 한다. 정상 칸 편집 때문에 오류 기록이 없어져서는 안 된다.
- 편집 결과와 검사 결과가 어긋나는 위험은 동일 점유 판정 재사용으로 줄인다. 단, 신규 배치를 거절하는 것과 기존 오류를 보존하는 것은 구분한다.
- 목록 삭제로 인덱스가 바뀌면 선택을 다시 확인하거나 해제한다. 다른 본체의 속성이 수정되는 일을 막는다.
- 검사는 `현재 구현 범위의 구조 검사`다. 발전기 연결, 공급, 미션, 시작 매칭 검사는 아직 제공하지 않음을 표시한다. 오류가 없어도 플레이 가능 또는 난이도 판정으로 표현하지 않는다.

## 9. 승인 후 구현 순서 제안

아래는 승인 전 작업 흐름 제안이다. Goal 실행 후 현재 파일과 의존성을 다시 확인하여 목표 문서에 확정 작업·완료 증거를 기록한다. 이번 규모에서는 공유 파일이 많으므로 순차 구현을 기본으로 한다.

1. **모델·호환성**: 현재 버전 1 데이터와 오류 사례를 확보하고 새 배치 모델·명시적 전환·검사를 구현한다. 전환 전후 기존 필드와 GUID 보존, Undo/Redo를 확인한다.
2. **단일 칸 층 편집**: 일반/파워·1칸 장애물·덮개·먼지의 배치와 속성·삭제·충돌 표시를 연결한다. 다른 층과 오류 데이터 보존을 검증한다.
3. **2×2 편집**: 본체 단일 기록·미리보기·클릭 배치·선택·이동·삭제를 구현한다. 경계와 부분 충돌에서 원자적으로 취소되는지 확인한다.
4. **편집 통합**: 외부 Inspector, Undo/Redo, 미완료 조작 취소, 저장, 오류 이동, 새 Match 메뉴와 좁은 창을 확인한다.
5. **재시작·회귀·결과 기록**: 별도 Editor 재시작과 기존 1·2단계 회귀를 검증하고 임시 에셋을 정리한다. 실제 결과·실패 수정·미실행 항목을 목표 문서에 기록한다.

## 10. 검증 시나리오

| 구분 | 관찰할 결과 |
| --- | --- |
| 각 종류와 경계값 | 내구도 최소/최대·충전 3/5·로켓 두 방향·자물쇠 색 저장, 잘못된 값은 오류 |
| 층 독립성 | 먼지+일반+거미줄, 먼지+파워+곰팡이 각각 일부 삭제·수정 후 나머지 보존 |
| 충돌 | 점유 중복·덮개 중복·장애물 위 덮개 신규 배치 거절, 기존 오류 기록은 보존 |
| 2×2 | 네 점유 칸 각각 선택/삭제, 9행9열 배치 성공, 10행/10열 기준 배치 실패, 자기 영역과 일부 겹치는 이동 가능 |

| Undo/Redo | 단일 속성·드래그·2×2 이동/삭제·형식 전환 각각 한 작업으로 복구, 무변경 기록 없음 |
| 오류와 외부 변경 | 미사용 자물쇠 색·누락 내부 블록·미지원 값·중복/범위 밖 기록 보존, 오류 이동, 외부 편집 후 갱신 |

기존 Editor 검증 실행 방식을 재사용한다. 새 테스트 프레임워크를 만들거나 의미 없는 검사 수를 목표로 삼지 않는다. Unity 실행 여부·로그·실패 수·화면 확인·제약을 구분하여 남기며 실행하지 않은 것을 통과로 기재하지 않는다.

## 11. 완료 의미

3단계 완료 후에는 장애물과 초기 파워를 포함한 보드를 편집·검사·저장할 수 있다. 발전기 연결과 중력 등은 4단계에서 이어간다. 상세 완료 조건과 실행문은 [3단계 개발 목표](../../../Goals/MoonRabbitJunkyard/Core/17_3단계_개발목표.md)를 따른다.
