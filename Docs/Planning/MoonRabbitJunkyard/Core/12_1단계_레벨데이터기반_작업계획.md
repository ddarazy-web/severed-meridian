## 1. 확인된 프로젝트 상태와 전제

- `ProjectSettings/ProjectVersion.txt`: Unity `6000.3.10f1`.
- 현재 `Assets` 조사에서 확인한 C# 코드는 기본 TutorialInfo 코드이며, 별도의 퍼즐 실행부나 레벨 에디터는 없다. `Assets/Scripts`도 아직 없다.
- Unity Test Framework `1.6.0`은 설치되어 있으나 프로젝트 자체의 테스트 어셈블리는 확인되지 않았다.
- 1단계에는 외부 패키지나 그림 리소스가 필요하지 않다. Unity 기본 에셋 저장과 Inspector를 이용한다.
- 이번 문서는 1단계의 추천 설계다. 세부 파일명과 API는 구현 검토 과정에서 조정할 수 있으며 프로젝트 전체 명명·어셈블리 정책을 변경하지 않는다.

## 2. 범위와 단계 완료의 의미

### 이번 단계에 포함

1. 레벨 하나를 나타내는 독립 Unity 데이터 에셋.
2. 파일명과 별도인 레벨 번호, 데이터 형식 버전, 이동 횟수, 사용 색상.
3. 기본 10×10 보드, 좌표, 활성·비활성 칸.
4. 초기 일반 블록의 고정 색 배치와 무작위 배치 구분.
5. 데이터 생성·저장·다시 열기와 기본 Inspector 확인.
6. 데이터 자체의 형식·참조 오류 검사 및 구조화된 검사 결과.
7. 저장 후 재로딩과 원본 보존 검증.

### 후속 단계에 구현

- 배치 도구·보드 그리기·선택·드래그 등 전용 편집 화면: 2단계 이후.
- 장애물별 속성 및 2×2 배치 조작: 3단계.
- 중력 경로·벽·통로·전선·발전기 연결: 4단계.
- 생성구 공급 목록·개수 유지·미션 입력: 5단계.
- 전체 편집 기능의 실행 취소·복제·연결 수정과 통합 검수: 6~7단계. 각 기능의 데이터 보존은 해당 기능을 만들 때부터 확인한다.
- 실제 매칭·낙하·효과·드론 목표 관리·유효한 첫 교환 검사·테스트 플레이: 공통 게임 규칙 구현 단계.
- 봇·분석·재생: 자동 플레이 개발 단계.

1단계 완료는 ‘게임이 가능한 레벨’이 아니라 ‘다음 편집 단계에서 손실 없이 다룰 수 있는 레벨 데이터 기반’을 뜻한다. 기본 검사를 통과했다고 플레이 가능으로 표시하지 않는다.

## 3. 구현 방식 비교와 추천

| 방식 | 장점 | 이번 단계에서의 한계 |
| --- | --- | --- |
| 씬의 GameObject 배치를 원본으로 저장 | 장면에서 바로 볼 수 있음 | 편집 데이터와 실행 오브젝트가 섞이고 고속 테스트용 상태 분리가 어려워짐 |
| 외부 JSON 파일을 원본으로 사용 | 외부 도구에서 가공하기 쉬움 | Unity 에셋·Inspector 편집 및 저장 처리를 별도로 연결해야 함 |
| 레벨별 ScriptableObject 에셋 | 기존 합의인 독립 Unity 에셋과 맞고 기본 Inspector로 검증 가능 | 실행 중 에셋을 직접 수정하지 않도록 경계를 지켜야 함 |

**추천: 레벨별 ScriptableObject를 저장 원본으로 사용한다.** 내부 데이터는 기능별 직렬화 가능한 값·기록으로 구성한다. 별도 저장 프레임워크·JSON 이중 저장·칸마다 개별 에셋 생성은 이번 단계에 도입하지 않는다.

## 4. 모델링 원칙

### 서로 다른 세 가지 상태를 구분한다

| 구분 | 소유 내용 | 이번 단계 처리 |
| --- | --- | --- |
| 레벨 정의 | 제작자가 설정한 초기 구성 | 구현 대상 |
| 플레이 상태 | 현재 블록 위치·남은 내구도·공급 소진·난수 상태 등 | 별도 소유 경계만 명시하고 구현은 후속 단계 |
| 편집 화면 상태 | 선택 칸·현재 도구·미리보기·화면 위치 | 레벨 정의에 넣지 않으며 2단계 이후 구현 |

- `remainingDurability`, 실행 중 목표 예약, 봇 판단 결과 같은 값은 레벨 에셋에 저장하지 않는다.
- 새 레벨 정의를 초기화하는 동작과 저장된 에셋을 읽는 동작을 구분한다. 읽거나 검사할 때 내용을 자동 정규화·삭제하지 않는다.
- 레벨 번호는 진행 순서이며 에셋의 고유 식별자를 대신하지 않는다. Unity 에셋의 식별 체계를 이용하고, 번호를 바꿔도 같은 에셋을 다른 대상으로 취급하지 않는다.
- 형식 버전은 저장 구조의 변경을 식별한다. 아직 필요하지 않은 범용 마이그레이션 엔진은 만들지 않는다.

### 칸과 점유 요소를 분리한다

- 보드는 크기와 칸의 활성 여부를 가진다. 초기 블록 배치는 별도 목록으로 관리한다.
- ‘비활성 칸’, ‘활성 빈칸’, ‘무작위 일반 블록’, ‘고정 색 일반 블록’을 서로 다르게 표현한다.
- 칸을 비활성화해도 그 좌표의 배치 기록은 유지한다. 오류로 보고하되 다시 활성화하면 원래 내용을 확인할 수 있어야 한다.
- 초기 무작위 표식은 에셋 생성·저장 때 실제 색으로 바꾸지 않는다. 무작위 결정은 후속 실행부의 책임이다.
- 하나의 범용 칸 클래스에 모든 장애물의 내구도·충전·통로·봇 필드를 몰아넣지 않는다. 기능이 구현되는 단계에서 해당 설정 기록을 추가한다.
- 후속 2×2 요소는 네 칸의 독립 장애물 복사본이 아니라 하나의 배치 기록과 점유 영역으로 표현한다. 이번 단계에 장애물·연결 코드를 미리 구현하지는 않는다.
- 저장 목록을 원본으로 삼고 좌표별 조회 인덱스·점유 정보는 필요할 때 계산한다. 같은 배치 정보를 두 곳에 영구 저장하지 않는다.

### 좌표와 크기

- 데이터 좌표는 왼쪽 위를 `(행 0, 열 0)`으로 두며 행은 아래로, 열은 오른쪽으로 증가하는 방식을 제안한다.
- 사용자에게 보이는 좌표는 `(행 1, 열 1)`부터 표시한다. 표시 변환과 데이터 좌표를 한 기준으로 관리한다.
- 기본 지원 범위는 기존 기획의 10×10이다. 보드 정의에 크기를 보관하되 임의 크기 편집·확장·축소 기능은 이번 단계에 추가하지 않는다.
- 칸 목록은 행 우선 순서로 저장하고 칸 수가 `행 수 × 열 수`와 맞는지 검사한다. 검사 과정에서 잘라내거나 빈 내용을 자동 덧붙이지 않는다.

## 5. 제안 파일 구성과 책임

```text
Assets/Scripts/
├─ Board/
│  ├─ BoardCoordinate.cs
│  ├─ BoardDefinition.cs
│  └─ CellDefinition.cs
├─ Levels/
│  ├─ LevelDefinition.cs
│  ├─ InitialBlockDefinition.cs
│  ├─ LevelDefinitionValidator.cs
│  └─ LevelValidationIssue.cs
└─ Editor/
   └─ Levels/
      ├─ LevelAssetOperations.cs
      └─ LevelDefinitionInspector.cs
```

| 형식·파일 | 책임 |
| --- | --- |
| `BoardCoordinate` | 행·열 좌표값, 비교와 동일 위치 판정 |
| `BoardDefinition` | 보드의 행·열 수와 칸 정의 소유 |
| `CellDefinition` | 칸의 활성·비활성 상태 |
| `LevelDefinition` | ScriptableObject 저장 루트. 레벨 번호·형식 버전·이동 횟수·사용 색·보드·초기 배치 소유 |
| `InitialBlockDefinition` | 배치 좌표와 고정 색 또는 무작위 일반 블록의 초기 설정 |
| `LevelDefinitionValidator` | 저장된 정의를 변경하지 않고 이번에 구현한 범위의 문제 검사 |
| `LevelValidationIssue` | 문제 코드·설명·대상 필드·해당 좌표 등의 검사 결과 |
| `LevelAssetOperations` | Editor 전용 에셋 생성·저장·읽기, 레벨 번호 중복 확인 |
| `LevelDefinitionInspector` | 전용 보드 화면 이전의 최소 속성 편집과 검사 결과 표시. Unity 기본 직렬화 편집 우선 |

- 위 파일명은 역할을 설명하는 초안이다. 작은 열거형·값 형식을 이유 없이 파일·폴더로 더 쪼개지 않는다.
- `Rules`, `Targeting`, `Simulation`, `Bots`, `Analysis`는 이후 해당 기능이 생길 때 `Assets/Scripts` 아래에 추가한다. 빈 기반 클래스·매니저·등록소를 지금 만들지 않는다.
- 저장 데이터는 `Assets/Data/Levels`를 기본 위치로 제안하며 스크립트 폴더에 넣지 않는다. 이 경로는 프로젝트 전체 에셋 로딩 정책을 바꾸는 의미가 아니다.
- 이 단계에서는 신규 asmdef·DI 프레임워크·런타임 UI를 추가하지 않는다. Editor API는 `Editor/Levels` 내부에서만 사용한다.
- 네임스페이스는 선택한 기능 소유권과 맞추고, 구체 명칭은 구현 시 기존 타입 충돌을 확인해 정한다. 폴더와 무관한 전역 `Managers`, `Models`, `Helpers` 분류는 만들지 않는다.

## 6. 기본 데이터 계약

| 데이터 | 1단계 계약 |
| --- | --- |
| 레벨 번호 | 양의 번호, 파일명과 독립. 다른 레벨과 중복되면 검사 결과에 표시 |
| 형식 버전 | 최초 저장 형식 식별값. 이후 변경 때 기존 에셋 처리 방식을 함께 결정 |
| 이동 횟수 | 양의 정수. 실제 감소·게임 종료는 이번 단계에서 실행하지 않음 |
| 사용 색 | 다섯 달토끼 종류 중 3~5종, 중복 없음. 실제 아트 색값과 게임 종류 식별을 분리 |
| 보드 | 기본 10×10, 활성 여부 목록과 크기가 일치해야 함 |
| 초기 배치 | 좌표당 하나의 일반 블록 배치. 고정 색 또는 무작위 유형 |
| 고정 색 | 해당 레벨 사용 색에 포함되어야 함 |
| 무작위 유형 | 실제 색 미확정 상태로 저장. 고정 색과 동시에 유효한 설정으로 해석하지 않음 |

- Inspector의 임시 입력 오류는 저장 자체를 막지 않고 진단한다. 자동으로 번호를 바꾸거나 색·배치 기록을 지우지 않는다.
- 레벨 번호 중복처럼 에셋 집합이 필요한 검사는 Editor 측에서 수행한다. 순수 데이터 검사기는 `AssetDatabase`를 참조하지 않는다.
- 다른 에셋·씬·GameObject에 의존해야만 초기 정의를 읽을 수 있는 구조는 피한다.

## 7. 작업 순서와 확인할 결과

아래는 1단계 내부의 순차 작업안이며 구현에 앞선 상세 Task DAG나 에이전트 배정은 아니다.

| 순서 | 작업 | 산출물·확인 사항 |
| --- | --- | --- |
| 1 | 데이터 경계와 직렬화 형식 구체화 | 좌표·색 종류·고정/무작위 표현·배치 소유권을 명확히 하고 저장 예시 검토 |
| 2 | Board와 Levels 모델 작성 | Editor API 없이 정의 데이터가 컴파일되고 기본 10×10을 표현 |
| 3 | 에셋 생성·읽기·저장 연결 | 기본 Inspector에서 수정한 내용이 별도 레벨 에셋으로 저장 |
| 4 | 읽기 전용 검사기와 결과 표시 | 위치가 있는 오류와 레벨 전체 오류를 구분하고 잘못된 데이터를 보존 |
| 5 | 저장·재로딩·원본 보존 검증 | 정상 데이터 및 의도적인 오류 데이터의 왕복 결과 확인 |
| 6 | 2단계 연결점 정리 | 배치 도구가 읽고 수정할 데이터와 검사 결과의 경계를 문서화 |

첫 단계에서는 데이터 모델 변경이 여러 파일에 영향을 주므로 순차 진행을 기본으로 한다. 실제 코드 작성이나 작업 위임은 이번 문서 작성 범위에 포함하지 않는다.

## 8. 검증과 완료 조건

| 검사 | 기대 결과 |
| --- | --- |
| Unity 컴파일 | 새 스크립트 오류가 없으며 Editor 전용 API가 데이터 영역에 섞이지 않음 |
| 기본 생성 | 독립 레벨 에셋을 만들고 100칸의 기본 보드 정의를 확인 가능 |
| 정상 저장 왕복 | 번호·이동 수·사용 색·활성 칸·고정/무작위 배치가 저장 후 재로딩에도 동일 |
| Editor 재시작 또는 도메인 재로딩 | 데이터가 초기화되거나 무작위 색으로 바뀌지 않음 |
| 비활성 칸 보존 | 비활성화한 좌표의 배치를 보존하고 오류 표시, 재활성화 후 확인 가능 |
| 배치 오류 | 좌표 범위 초과·중복 점유·미사용 색을 정확한 대상과 함께 보고 |
| 정의 오류 | 보드 크기와 칸 수 불일치, 색 중복·개수 오류, 번호·이동 수 오류 보고 |
| 번호 중복 | 같은 번호의 두 레벨을 검사하면 문제를 표시하고 번호를 자동 변경하지 않음 |
| 검사 부작용 | 검사 전후 에셋 데이터가 동일하며 검사만으로 수정 상태를 만들지 않음 |
| 독립 편집 | 두 레벨 중 하나를 수정해도 다른 에셋 내용은 변하지 않음 |
| 기본 Inspector 변경 취소 | 지원하는 프로퍼티 변경이 Unity 기본 Undo/Redo와 저장 상태에 정상 반영 |

- 컴파일만 성공한 상태를 완료로 보지 않는다. 실제 Unity에서 저장·재로딩 검증까지 해야 1단계 완료다.
- 확인용 임시 에셋은 검증 자료이며 정식 레벨 데이터로 배포하지 않는다. 검사에 필요한 최소 예제만 만들고 검토용 운반 레벨의 본격 제작은 진행하지 않는다.
- 설치된 테스트 패키지를 활용할 수 있는지 구현 시 확인한다. 별도의 테스트 어셈블리·범용 테스트 기반 추가를 이 계획만으로 확정하지 않는다. 실행하지 못한 검증은 미완료로 기록한다.
- 검증 후 의도하지 않은 씬·프로젝트 설정·패키지·기존 문서 변경이 없는지 확인한다.

## 9. 위험과 대응

- **저장 정의와 실행 상태 혼합:** 플레이 중 상태 필드를 만들지 않고 이후 실행부가 원본에서 독립 상태를 구성하게 한다.
- **무작위와 빈칸의 혼동:** 별도 초기 배치 유형으로 저장하고 초기 에셋에서는 난수를 실행하지 않는다.
- **모든 장애물의 성급한 일반화:** 이번에 필요한 일반 블록 모델만 구현하고 후속 기능별 설정은 해당 단계에서 추가한다.
- **후속 모델 추가로 저장 형식 변화:** 형식 버전을 기록하고 저장 필드 이름·타입 변경 시 기존 에셋 처리 방식을 확인한다.
- **잘못된 설정의 자동 손실:** 저장과 유효성 판정을 분리하고, 오류 데이터도 보존한다.
- **형식 검사와 게임 가능성의 혼동:** 검사 범위를 표시하고 미션 완료 가능성·유효한 수·시작 매칭은 아직 검사하지 않는다고 명시한다.

## 10. 완료 후 다음 단계

위 완료 조건을 충족하면 2단계에서 이 에셋을 그대로 사용하는 보드 편집 창을 만든다. 임시 화면 전용 데이터나 두 번째 저장 형식을 추가하지 않는다.
