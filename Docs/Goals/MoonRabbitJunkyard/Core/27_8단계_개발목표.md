## Goal 목표

현재 Unity 프로젝트에서 레벨 정의와 분리된 실행 상태를 구성하고, 명시적 시드로 초기 배치 후보를 재현하며, Match 메뉴의 읽기 전용 확인 화면에서 결과와 진단을 확인할 수 있게 한다. 원본 데이터·GUID·v4 저장 형식과 기존 편집 기능을 보존하고 실제 Unity 조작·독립 프로세스 재현·필요한 회귀를 검증한다.

이번 목표는 **시작 조건 검사 전의 초기 후보 구성**이다. 매칭 없음/유효한 교환이라는 확정 시작 규칙을 완화하지 않으며, 아직 그 조건을 검증하지 않는다는 사실을 화면과 문서에 명시한다.

## 실행 지침

1. 프로젝트 지침, `ponytail`, Unity 프로젝트 규칙과 관련 UI Toolkit 지침을 따른다. 상세 계획과 실제 소스/정의를 대조한 뒤 작업한다.
2. 이 문서를 참조한 Goal 실행 요청은 상세 계획의 추천 범위 구현·검증을 포함한다. 문서 작성만으로 Goal이나 구현을 시작하지 않는다.
3. 기존 `Board`/`Levels` 정의와 구조 검사를 재사용한다. `LevelDefinition` 저장 필드·버전·GUID와 기존 에디터의 오류 데이터 저장 정책을 변경하지 않는다.
4. 스크립트는 `Assets/Scripts` 아래 `Simulation`, `Editor/Levels` 등 책임별로 둔다. 별도 게임명 폴더, 새 패키지/asmdef/DI, 범용 프레임워크를 추가하지 않는다.
5. 실행 상태의 가변 데이터는 원본·다른 실행 상태와 공유하지 않는다. 특히 합류/전선/공급 중첩 목록을 확인한다. 읽기 전용 인터페이스만으로 깊은 복사를 대신하지 않는다.
6. 초기 고정을 이동 잠금으로 바꾸지 않는다. 파워 종류/방향, 2×2 본체, 덮개 아래 블록, 먼지/흐름/연결/공급/미션 데이터를 보존한다.
7. 시드·난수는 상태별로 소유하고 전역 Unity 난수를 건드리지 않는다. 재현 보장 범위와 실제 입력 내용을 기록한다.
8. 초기 후보 구성에서 낙하·공급 소비·매칭 제거·파워 효과·미션 완료·이동 수 감소를 실행하지 않는다. 후보의 직접 채우기를 실제 플레이의 보충 규칙으로 재사용하지 않는다.
9. 메뉴는 Match 아래에 둔다. 화면은 레벨/시드/재구성/결과에 집중하며 플레이·봇·난이도 기능이나 설정을 미리 만들지 않는다.
10. 검증에는 소유한 임시 데이터만 사용한다. 사용자 원본의 JSON·dirty·파일 해시·meta/GUID를 보존하고 임시 에셋·대기 상태를 정리한다.
11. 실제 수행한 검증만 완료로 기록한다. 기존 735개 결과를 새 구현의 검증으로 자동 승계하지 않는다. 변경 영향이 없는 검사를 이유 없이 반복하지 않는다.
12. 착수 시 아래 기록에 작업 의존성·수정 책임·검증 기준을 구체화한다. 공유 상태/Unity 검증은 순차 실행하며 검증 프로세스 중 소스 변경을 피한다.

설정 컬렉션은 읽기 전용 래퍼로 노출한다. 현재 상태의 변경은 실행 코드 내부로 제한했다. 초기 고정을 이동 잠금으로 취급하는 필드를 만들지 않았다.

v4 이외 버전은 구성 미지원으로 진단하며 변환하지 않는다. 기존 에디터의 버전별 읽기·저장 동작은 그대로다. 구성 실패는 상태 없이 기존 구조 진단을 반환하고, 화면은 이전 성공 후보를 지운다.

### 시드와 재현 범위

- 구현 식별: System.Random/initial-state-v1. 시드는 int, 무작위 칸 방문 순서는 행→열 오름차순이다.
- 검증 환경: Windows, Unity 6000.3.10f1, 런타임 4.0.30319.42000.
- 같은 입력 정의·시드·이 구현 환경의 반복/독립 프로세스 재현을 확인했다. 다른 Unity 버전·플랫폼 사이의 동일성이나 강제 종료 복구/리플레이 저장은 이번에 구현·검증하지 않았다.
- 시드 12345, 기본 다섯 색의 첫 10칸 기준값(0부터 센 종류)은 0,0,3,2,3,4,0,3,1,2다. 전체 고정은 난수를 소비하지 않는다.
- SHA-256 입력 지문으로 메모리 정의의 내용을 식별한다. 같은 번호/시드라도 정의가 바뀌면 같은 입력이라고 표시하지 않는다.
- 새 시드 생성과 재구성을 구분하고 새 시드는 직전 값과 다르게 만든다. 다른 시드가 반드시 다른 보드를 만든다는 보장은 없다.
- 조회와 화면 갱신은 상태 난수를 소비하지 않는다. Unity 전역 난수는 구성/새 시드 버튼의 호출 직전·직후 비교로 보존을 확인했다.

### 실제 사용법

1. Unity에서 **Match → 초기 보드 확인**을 연다.
2. 레벨 에셋과 정수 시드를 지정하고 **같은 시드로 구성**을 누른다. 원본의 미저장 내용도 사용하며 원본을 저장하지 않는다.
3. **새 시드로 구성**은 표시된 시드와 초기 후보를 함께 바꾼다.
4. 보드 칸을 눌러 본체 ID/내구도/충전, 덮개/먼지/중력, 경로/연결, 공급 목록을 읽는다. 색 종류는 토1~토5로도 구분하며 별표는 먼지다.
5. 원본·레벨·시드가 바뀌면 이전 후보가 사라진다. 다시 구성해 새 내용을 확인한다.
6. 오류가 있으면 필드/좌표 진단을 확인하고 기존 레벨 에디터에서 수정한다. 이 창에는 배치 편집·저장·플레이 기능이 없다.
7. 좁은 창에서는 보드와 속성을 스크롤한다. 양방향 스크롤로 10행 10열까지 접근하는 경로를 검사했다.

- 다섯 임시 에셋(Random/Fixed/Mixed/Maintain/Copy)을 저장하고 별도 프로세스에서 원본 전체 JSON/GUID 및 의미 있는 전체 실행 상태를 비교했다.

### 발견과 수정

- 새 시드 버튼 내부의 값 변경 알림이 구성 이후 처리되어 방금 만든 후보를 지웠다. 내부 시드와 입력 표시를 알림 없이 함께 갱신한 뒤 한 번 구성하도록 수정했고 다음 프레임에도 후보가 유지되는 검사가 통과했다. 최초 실패는 initial-ui.log/initial-ui-results.txt에 보존했다.
- 전역 난수를 서로 다른 Editor 프레임에서 비교한 초기 검사는 다른 Editor 작업의 난수 소비까지 포함했다. 호출 직전·직후 검사로 수정했다. 진단 실행은 frame-random-diagnostic.log/frame-random-results.txt에 보존했으며 최종 통과에 합산하지 않았다.
- 시각 검수 후 보드의 실제 너비를 명시하고 양방향 스크롤/끝칸 접근 검사를 추가했다. 미션·덮개·중력·공급 속성은 한국어로 표시한다.

### 완료 조건별 감사

- 입력/구조/버전 경계: 실제 빌더와 null·구버전/미래·좌표·내구도·공급 수량·중복 ID 실패 검사가 근거다.
- 전체 데이터와 독립성: 대응표의 각 층/목록 검사 및 원본·두 상태의 직접 변경 실험, 전체 상태 재시작 비교가 근거다.
- 시드/부작용: 고정 기준값·추출 횟수·전역 난수·조회 불변·독립 프로세스 비교가 근거다.
- 화면/기존 동작: 실제 패널/크기별 화면과 기존 공통 편집 회귀가 근거다. 기존 제품 코드를 바꾸지 않아 다른 배치/흐름/공급 검증군 전체는 반복하지 않았다.
- 보존/정리: baseline.json과 final-audit.json을 대조했다. 기존 제품 파일은 변경되지 않았으며 임시 에셋·대기 state·검증 프로세스는 남아 있지 않다.
- 최종 새 소스/meta 해시는 final-source-hashes.json에 보존했다. 완료 문서 외 무관한 파일은 변경하지 않았다.

초기 후보의 직접 채우기는 실제 낙하·공급이 아니다. 완성 매칭과 유효 교환은 아직 판정하지 않고 고정 배치를 보정하지도 않는다. 화면에 **시작 조건 미검사·플레이 미지원**을 계속 표시한다. 실제 게임 실행부·봇·난이도 분석은 이번 범위에 추가하지 않았다.
