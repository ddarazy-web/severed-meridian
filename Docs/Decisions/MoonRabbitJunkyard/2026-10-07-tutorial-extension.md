# 레벨 튜토리얼 — 등록식 확장과 단계 경계

날짜: 2026-10-07. 상태: 2단계 소스 적용·검증 완료. 실제 게임 연결과 안내는 후속 단계.

## 결정

공통 진행 엔진과 행동별 처리기·완료 조건별 판정기를 분리한다. 기능 소유의 명시적 조립 지점에서 단계/아이템/결과 종류를 등록하고 현재 단계에 필요한 것만 직접 조회한다. 진행·권한·결과 집계는 실행별로 소유한다. 중복/미등록은 설정 오류다.

설명·교환·파워 교환·아이템과 생성·발동·제거를 최초 구현으로 사용한다. 오브젝트별 코드보다 요소 ID·좌표·수량과 공통 특성을 사용한다. 실제 퍼즐 효과는 기존 BoardActionExecutor에 위임한다. 설정 검사와 참조 수집은 같은 종류별 규칙을 사용한다.

진행과 표현은 읽기 전용 상태/명령 경계로 분리한다. 전체 MVVM 프레임워크는 추가하지 않는다. 전역 서비스·동적 리플렉션·임의 문자열 플러그인 엔진으로 확대하지 않는다.

완료된 1단계는 보존한다. 새 2단계는 등록 구조·공통 엔진·검사 공유와 확장 검증, 새 3단계는 실제 게임 연결·공급/종료·재생 검사, 새 4단계는 안내·기록·최종 적용이다. 팩3 저장 ADR의 당시 ‘2단계 실행 적용’은 재계획 후 새 3단계에 해당한다. 과거 완료 기록은 당시 번호를 유지한다.

enum 값·MemoryPack 필드 계약은 유지한다. 새 종류는 값 추가·등록·지원 검사와 필요한 제작 UI 변경을 동반하며 새 저장 항목은 별도 호환성 설계가 필요하다. 처리기만 등록하면 모든 데이터 형식이 자동 확장된다는 의미가 아니다.

## 이유와 대안

중앙 분기를 계속 추가하면 새 기능이 진행/검사/표현 곳곳에 영향을 준다. 좁은 등록 구조는 실행과 검사 규칙을 함께 관리하고 현재 종류만 선택한다. 계약과 등록 누락 검사가 필요하므로 실제 행동/조건만 일반화한다.

게임 연결까지 한 단계로 묶는 대신 엔진을 먼저 검증하면 구조 문제와 세션/연출 문제를 구별할 수 있다. 엔진의 모의 검사만으로 실제 게임이 검증되는 것은 아니므로 3단계에서 실제 기록·연출·종료를 확인한다.

범용 그래프 편집기와 모든 기능을 문자열로 선택하는 플러그인 방식은 현재 기획보다 관리·저장 호환성 비용이 크므로 채택하지 않는다.

## 검증과 적용

2단계에서 시험 전용 처리기/판정기를 별도 목록에 추가·대체하고 중앙 엔진 수정 없이 진행되는지 검사한다. 미사용 처리기 호출 0, 중복/미등록 오류, 실행별 상태 격리, 검사/참조 수집 공유와 기존 팩 회귀를 완료 조건으로 삼는다.
