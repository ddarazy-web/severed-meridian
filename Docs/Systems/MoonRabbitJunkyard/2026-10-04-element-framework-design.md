# 퍼즐 요소 정의와 공통 행동 구조 — 리팩토링 설계안

- 상태: 설계·계획 제안. EF-13 영구 ID·기존6종 매핑과 EF-14 불변 메모리 ID/표시명·카탈로그 기본 조회 구현·검증 완료. EF-15/16 내구도형5종 Size·MaxDurability와 EF-17 별도 발전기 Size/배치 충전 프로필 연결 검증 완료. 다른 소비자·행동/저장 전환은 미착수, 기존 동작 유지.
- 범위: 블록·파워 블록·장애물·덮개·바닥·장치의 종류 확장과 공통 규칙 재사용.

## 1. 문제와 목표

현재 `BoardActionExecutor`의 교환·연쇄 진행, `DamageReaction`의 반응 조회, `PowerEffectResolution`의 공통 적용과 규칙·연출 분리는 유지할 가치가 있다. 문제는 크기·내구도·피해 조건·미션·그림 정보가 종류 enum과 여러 파일의 조건문에 연결되어 있다는 점이다.

목표는 같은 행동을 가진 장애물 100개를 추가할 때 처리 코드 100개를 만들지 않는 것이다. 기존 행동으로 설명되는 종류는 정의 데이터로 추가한다. 새로운 행동만 규칙 코드·등록·검증을 추가하고 교환·매칭·낙하·연쇄 엔진은 복제하지 않는다.

## 2. 정의·상태·행동·표현의 분리

| 구분 | 책임 |
| --- | --- |
| 정의 ID | 영구적인 콘텐츠 종류 식별. 표시 이름·배열 순서·Unity GUID와 독립 |
| 요소 정의 | 배치 층, 점유 영역, 초기·최대 내구도, 피해 정책, 행동 키, 미션 태그, 표현 키 |
| 인스턴스 상태 | 보드 위치, 현재 내구도·색·충전·연결과 행동별 필요한 상태 |
| 공통 행동 | 내구도형, 충전·연결형, 번식형, 파워 발동형 등 실제 처리 규칙 |
| 표현 정의 | 상태별 이미지, 프레임, 피벗, 크기, 정렬, 효과와 아틀라스 주소 |

정의 ID 예시는 `obstacle.crate.wood`다. 한번 배포된 ID를 다른 종류에 재사용하지 않는다. 기존 배치의 `Id`는 발전기 연결 등에 쓰이는 본체 인스턴스 ID이므로 정의 ID로 재해석하지 않는다.

전체 종류마다 enum을 추가하지 않는다. 배치 층·기본 분류·피해 원인 같은 작은 의미 집합에는 enum을 유지할 수 있지만 수백 개의 콘텐츠 목록으로 사용하지 않는다.

## 3. 공통 규칙과 고유 행동

피해 정책은 허용 피해 원인, 색 조건, 피해량, 집계 단위를 표현한다. 집계 단위는 현재의 본체별 턴당 1회와 타격별 점유 칸 피해를 보존한다. 점유 영역은 상대 좌표 목록으로 정의해 크기를 종류명에서 추론하지 않는다.

덮개는 내용물을 보존하고, 바닥은 블록 소비에 반응하는 현재 의미를 유지한다. 모든 요소를 같은 피해 처리로 평탄화하지 않는다. 발전기·번식·파워 발동은 실제 고유 행동이므로 코드가 필요하지만 종류별 복제 대신 행동 키로 등록한다.

반응 조회는 상태를 변경하지 않는다. 변경은 공통 적용 경로만 수행하고 피해·미션·연쇄 기록을 같은 턴 문맥에 남긴다. 정책과 행동이 같은 타격을 두 번 적용하지 않게 책임을 구분하고 실행 순서를 고정한다.

모든 기능을 임의로 겹쳐 쓰는 범용 스크립트 언어는 만들지 않는다. 검증된 정책·행동 조합만 허용하고 잘못된 충전·파괴·번식 조합은 제작 오류로 표시한다. 행동 등록은 명시적 등록표를 사용하며 리플렉션·문자열 함수 실행은 사용하지 않는다.

## 4. 파일 경계와 계약

새 공통 기능은 `Assets/Scripts/Features/Elements/`에 둔다. 기존 매칭·낙하·파워 엔진은 해당 기능 폴더에 유지하고 정의를 조회하도록 연결한다.

```text
Elements/
  Data/          제작 정의, ID, 배포 DTO, 피해·표현 정책
  Runtime/       카탈로그, 행동 등록, 조회·적용, 표현 조회
  Editor/        정의 편집·검사, 구형 연결·변환, 검증
```

제작 원본은 요소별 ScriptableObject 정의와 표현 정의로 편집한다. 배포는 가벼운 정의 DTO와 Addressables 표현 키를 사용한다. 제작 원본 객체를 런타임 상태마다 복제하지 않는다.

계획상 공유할 타입과 책임은 다음과 같다.

- `ElementId`: 영구 정의 ID 값.
- `ElementDefinition`, `PackedElementDefinition`: 제작 원본과 배포 정의.
- `ElementCatalog.Get(ElementId)`: 읽기 전용 정의 조회. 누락은 ID를 포함한 오류로 처리.
- `LegacyElementMap`: 기존 enum을 같은 의미의 정의 ID로 연결하는 과도기 경계.
- `ElementPlacementDefinition`: 정의 ID, 본체 ID, 좌표, 레벨별 초기 상태.
- `ElementBehaviorRegistry`: 종류 ID 대신 행동 키로 실행 코드 조회.
- `ElementVisualResolver`: 에디터·게임에서 상태에 맞는 동일 표현 조회.

카탈로그는 초기화 시 ID 인덱스를 만든다. 프레임마다 전체 종류를 탐색하거나 ScriptableObject를 검색하지 않는다. 내부 핸들은 사용할 수 있지만 저장에는 영구 ID를 사용한다.

## 5. 저장·변환 호환성

1. 기존 레벨·시드·행동 결과의 기준 사례를 먼저 확보한다.
2. 기존 enum과 같은 동작의 정의를 연결한다. enum 숫자와 원본 `.meta` GUID를 유지한다.
3. 새 배치를 추가하고 스키마 버전으로 구형/신형의 유일한 원본 목록을 구분한다. 신형 목록이 비었다고 구형 목록을 되살리지 않는다.
4. 변환은 미리보기·원본 백업·메모리 비교 후 선택한 원본에만 적용한다. 대량 자동 덮어쓰기는 하지 않는다.
5. 소비자를 순서대로 전환하고 동등성이 확인된 중복 실행 분기만 제거한다. 필요한 구형 원본 읽기는 호환 경계에 남긴다.

현재 `LevelPackCodec`는 구형 바이너리의 자동 마이그레이션 대신 버전 불일치를 거절한다. 원본 에셋을 변환해 새 포맷으로 재생성하는 방식을 기본으로 유지한다. 이전 바이너리를 새 DTO로 바로 읽는다고 가정하지 않는다. 실제 배포된 구형 바이너리 지원이 필요해지면 버전 전용 판독기와 검증을 별도로 추가한다.

정의 카탈로그와 레벨 팩의 호환 버전을 기록한다. 누락 ID·미지원 행동·버전 불일치는 레벨 번호와 ID를 포함해 거절한다. 기본 상자로 몰래 대체하지 않는다. 50레벨 MemoryPack 구간과 레벨 원본의 배포 제외 방식은 유지한다.

## 6. 제작·표현·리소스

에디터 선택 목록은 카탈로그에서 생성하고 분류·검색·태그 필터를 제공한다. 공통 필드는 공통 편집기로 표시하고 실제 고유 행동만 별도 편집부를 제공한다.

게임·에디터·플레이 테스트는 동일 표현 정의를 사용한다. 현재 `LevelBoardArtwork`, `RuntimeBoardArtwork`, `PuzzleArtworkPaths`의 중복 연결을 조회기로 모은다. 내구도·색·충전·방향·애니메이션 프레임도 정의 데이터로 선택한다.

Addressables 아틀라스는 종류·용도별로 분리한다. 전체 이미지를 한 아틀라스에 넣지 않는다. 초기 배치, 공급 가능 요소, 미션 표시, 파워 생성·조합·고유 행동의 생성 가능 관계를 따라 필요한 요소와 효과의 로드 집합을 계산한다. 순환 생성 관계는 방문 집합으로 종료한다.

가벼운 카탈로그 메타데이터와 무거운 이미지·프리팹 로딩을 구분한다. 공유 아틀라스의 동반 이미지 로딩은 발생할 수 있으므로 미사용 이미지가 단 하나도 로드되지 않는다고 보장하지 않는다. 불필요한 종류의 아틀라스·프리팹 로딩이 없는지를 검사한다.

풀은 공통 표시 오브젝트와 효과를 재사용한다. 정의 500개 때문에 풀 500개를 미리 만들지 않는다. 복귀 시 프레임·색·정렬·효과·콜백·취소 상태를 초기화하고 씬 전환 시 소유한 핸들을 해제한다.

## 7. 미션·자동 플레이·튜토리얼

미션은 집계 행동과 대상 태그/정의 선택을 분리한다. 새 장애물을 같은 제거 미션에 연결하기 위해 `MissionKind`를 계속 늘리지 않는다. 기존 미션의 대상·완료 수와 2×2 본체 집계를 보존한다.

자동 플레이에는 화면에 공개된 상태와 행동 특성만 복사한다. 정의 원본·내부 ID·배열 인덱스·난수 시드·숨은 내용물·미공개 공급 순서·드론 예약을 넘기지 않는다. 새 종류도 공개 정보로 같은 규칙을 조회하며 별도의 피해 알고리즘을 복제하지 않는다.

튜토리얼은 정의 ID·행동 결과·공개 상태를 대상으로 작성한다. 튜토리얼 기획은 유지하고 정의·규칙·에디터 연결을 검증한 뒤 구현을 시작한다. 튜토리얼에 구형 종류별 분기를 늘리는 작업을 먼저 하지 않는다.

## 8. MVVM·MVP 적용 검토

사용자는 MVVM도 효율적인 곳에서 고려하도록 요청했으며 전면 도입을 요구하지 않았다. 추천은 기능별 모듈과 정의·행동 구조를 유지하고, 화면 상태 전달에 MVVM 또는 MVP를 선택하는 방식이다. 요소 종류 확장과 UI 상태 분리는 서로 다른 책임이다.

| 영역 | 추천 | 적용 이유 |
| --- | --- | --- |
| 요소 카탈로그·튜토리얼 단계 등 복잡한 에디터 화면 | MVVM 우선 검토 | 검색·선택·검사·버튼 활성 상태를 UI 코드와 분리해 검사 가능 |
| 에디터의 실제 원본 에셋 필드 편집 | SerializedObject/SerializedProperty 유지 | Undo·직렬화·변경 감지의 기존 경로 보존 |
| 기존 uGUI HUD·팝업 | MVP와 읽기 전용 표시 상태 | 기존 프리팹을 유지하면서 세션 전체에 대한 화면 의존 축소 |
| 보드 규칙·피해·낙하·연쇄 | 현재 규칙/실행 경계 유지 | 화면 모델이 게임 상태를 소유하지 않도록 함 |
| 보드 스프라이트·프레임별 이동 | 기존 결과 기록과 Playback 유지 | 프레임마다 전체 ViewModel과 바인딩을 갱신하지 않음 |

에디터 ViewModel은 선택 ID·검색어·필터·검사 결과·사용 가능 명령을 관리한다. 실제 정의와 레벨 에셋 필드를 복사해 또 하나의 저장 원본으로 만들지 않는다. 편집 명령은 기존 편집 응용 계층을 통해 SerializedObject·Undo 처리를 수행한다. 모델의 변경은 화면에 필요한 변경 통지로 전달하고 선택/필터 갱신 때문에 원본을 저장하지 않는다.

기존 `PuzzleHudView.Refresh(PuzzleGameSession)`는 세션 전체를 읽는다. 표현 통합 단계에서 Presenter가 화면용 읽기 전용 상태를 구성하고 View가 이를 그리도록 연결을 줄인다. 미션 표시에는 실제 최종 시뮬레이션 값이 아니라 기존 연출의 표시 진행값을 사용해 수집 연출보다 숫자가 먼저 바뀌지 않게 한다.

MVVM 시범은 5단계의 카탈로그 목록·검색·선택·검사 영역으로 한정한다. UI 없이 선택·필터·검사 상태를 검증하고, 기존 Undo/Redo·선택 복원·창 닫기·구독 해제·가상화 목록 재사용을 확인한다. 직접 연결보다 상태의 중복과 갱신 누락이 줄었는지 평가한 뒤 같은 패턴을 확장한다. 단순 필드마다 ViewModel·Command·인터페이스를 추가하거나 수백 요소 각각에 ViewModel을 만들지 않는다.

MVVM을 위해 런타임 UI Toolkit으로 전환하거나 바인딩/반응형 패키지를 새로 설치하지 않는다. Unity 6 UI Toolkit은 일반 C# 객체 바인딩을 제공하지만 에디터 직렬화 데이터는 SerializedObject 바인딩이 Undo/Redo 등에 적합하다는 공식 권고를 따른다. 공식 자료: [UI Toolkit 데이터 바인딩](https://docs.unity3d.com/6000.0/Documentation/Manual/UIE-runtime-binding.html), [Unity의 MVC·MVP 안내](https://learn.unity.com/tutorial/build-a-modular-codebase-with-mvc-and-mvp-programming-patterns).

## 9. 드론 목표 선택 정책의 선택적 등록

사용자 제안은 미션과 요소 특성에 해당하는 선택 로직을 미리 연결하고, 매번 모든 검색 로직을 호출하지 않는 방식이다. 이 구조를 추천안에 포함한다. 현재 `DroneTargetManager`의 후보 캐시·예약·착탄 재검증은 보존하고 종류별 후보·우선순위 분기를 정책으로 옮긴다. 기존 미션별 기여 계산도 재사용한다.

### 9.1 정책 정의와 활성 연결의 구분

전체 정책 등록표는 정책 키를 실행 구현에 연결하는 작은 인덱스다. 새 콘텐츠마다 정책 클래스를 만들지 않는다. 색 수집·내구도 제거·덮개 제거·충전/연결 등 서로 다른 목표 해결 방식에 공통 정책을 제공한다.

레벨 구성 시 남은 미션의 목표 선택 정책 키와 요소 정의의 목표 프로필을 읽어 활성 연결 목록을 만든다. 등록표를 매번 순회하며 모든 정책에 `CanHandle`을 묻지 않고 키로 필요한 정책만 직접 연결한다. 같은 정책의 여러 미션은 매개변수·대상 집합으로 구별하고 가능한 검색은 묶어 재사용한다.

요소 목표 프로필은 후보 분류·선택에 필요한 공개 특성과 정책 매개변수를 제공한다. 피해를 받는지·얼마나 피해를 받는지·충전되는지는 공통 반응 규칙이 결정한다. 목표 정책에 별도의 피해 알고리즘을 복제하지 않는다.

현재 보드에 대상이 없어도 공급이나 행동으로 등장할 수 있으면 미션 연결을 유지한다. 후보가 없다는 이유로 영구 해제하지 않는다. 실제 미션 완료·레벨 종료 때 연결을 제거하고, 요소 생성·제거·변환·덮개/내구도/충전 변경 때 후보 인덱스와 캐시를 갱신한다. 레벨 전체 연결과 실제 효과 작업 사본의 후보 상태를 구분해 다른 상태의 캐시를 재사용하지 않는다.

### 9.2 후보 조회와 최종 선택

```text
활성 미션 → 정책 키 직접 조회 → 미션별 활성 연결
공개 요소 상태 → 목표 프로필·층·색·태그별 후보 인덱스
드론 요청 → 필요한 연결의 후보 조회 → 중복 후보 병합
          → 공통 타격 예상·미션 기여 계산 → 예약 반영
          → 우선순위 비교 → 최종 후보 선택·예약
착탄 직전 → 유효성 재확인 → 필요할 때 재선정 → 공통 타격 적용
```

정책은 읽기 전용 상태에서 후보와 선택 근거를 반환한다. 검색 중 상태·예약·난수를 변경하지 않는다. 예약과 해제는 공통 목표 관리자만 수행하고 실제 피해·충전·제거·미션 갱신은 공통 실행기에 맡긴다.

가능하면 층·색·태그·본체의 후보 인덱스를 공유해 정책마다 보드 전체를 다시 검색하지 않는다. 9×9에서 단일 공통 순회가 더 단순하거나 빠르면 그 결과를 여러 정책이 공유할 수 있다. 목표는 무조건 복잡한 인덱스를 만드는 것이 아니라 전체 콘텐츠·전체 정책을 반복 검색하지 않는 것이다.

범위가 있는 드론은 미션 대상이 있는 칸만 후보로 제한하지 않는다. 로켓형·폭탄형 도착 효과가 목표를 포함할 수 있는 주변 조준 중심도 후보로 계산한 뒤 공통 범위 규칙으로 예상 기여를 검증한다. 여러 정책이 같은 좌표를 제안하면 하나의 후보로 병합하고 같은 칸·본체의 기여를 중복 합산하지 않는다.

우선순위는 공통 비교 계약으로 표현하고 정책은 그 입력과 선택 근거를 제공한다. 서로 다른 정책이 비교할 수 없는 임의 점수를 각각 내지 않는다. 이번 리팩토링의 기본 프로필은 기존의 남은 미션 우선·노출 색 직접 기여 우선·예약 제외·일반 블록 대체·동률 난수 선택을 보존한다. 내구도 낮은 대상 우선 등의 새 밸런스는 별도 프로필과 기획 결정으로 추가하며 구조 변경에 섞지 않는다.

일반 블록 대체 정책은 예약과 기여 검사를 거친 유효 미션 후보가 없을 때만 실행한다. 남은 미션에 정책 연결이 없으면 설정 오류로 표시하며 이를 일반 블록 대체로 숨기지 않는다.

### 9.3 다중 드론과 캐시

여러 드론이 한 목표를 이미 해결할 것으로 예상되면 그 예약 기여를 반영해 다른 후보를 선택한다. 예약 소유자·해제·2×2 칸 타격·턴별 제한은 기존 공통 문맥을 사용한다. 정책마다 예약 목록을 따로 만들지 않는다.

후보 캐시는 보드 변경과 도착 효과 범위·조회 범위를 기준으로 재사용한다. 예약·미션 잔량·턴 피해 기록이 달라지면 이전 최종 순위를 그대로 쓰지 않고 현재 문맥으로 필터링·기여를 다시 계산한다. 착탄 전 목표가 없어지거나 성질이 바뀌면 자기 예약을 해제한 뒤 활성 미션 정책부터 다시 조회한다.

정책 실행 횟수·후보 수·캐시 재사용·선택/제외 근거·예약·재선정을 진단 기록으로 확인할 수 있게 한다. 플레이 화면에는 목표 표시를 추가하지 않는다. 실제 드론 연출과 자동 플레이의 공개 관찰 경계도 유지한다.

### 9.4 모든 드론의 상승·호버·돌진 통일

2026-10-04 추가 요청. 드론 수와 조합 종류에 따른 비행 방식 구분을 제거한다. 모든 드론은 발생 위치에서 천천히 상승하고, 조금씩 다른 시간 동안 호버한 뒤 목표로 빠르게 돌진한다. 기존 원형 선회와 목표 주변 회전은 사용하지 않는다. 프로펠러 4컷 회전은 유지하며 목표 예고는 표시하지 않는다.

초기 조정안은 기존 상승 0.55초·0.65칸을 유지하고 기본 호버를 드론별 0.45~0.75초로 분산하는 것이다. 수치는 구현 시 화면 확인으로 조정할 제안값이다. 연출 편차는 드론 식별자/발생 순서에서 산출하고 규칙 난수를 소비하지 않는다. 선행 공격 또는 목표 확정을 기다려야 하면 돌진 전 호버를 연장할 수 있다. 많은 드론도 순차 실행 대기열로 만들지 않고 상승·호버를 함께 진행한다.

돌진 중 목표가 제거되거나 유효하지 않게 되면 그 시점의 비행 위치에서 짧게 감속해 정지하고 호버하며 재선정한다. 새 비행은 발생 위치로 되돌리지 않고 현재 호버 위치에서 시작한다. 무효 목표의 예약을 해제하고 활성 미션 정책으로 검색하며, 유효 후보가 확정되면 공통 관리자에서 예약한 뒤 다시 빠르게 돌진한다. 새 목표 확정 뒤에도 선행 효과 정합성이나 짧은 정지 연출이 필요하면 호버를 연장한다. 호버는 제자리의 작은 부유만 허용하며 원형 이동으로 대체하지 않는다.

표현 코드가 최신 게임 상태를 임의로 조회해 목표나 피해 결과를 바꾸지 않는다. 현재 효과 타임라인의 소유자가 목표 무효화·예약 해제·재선정과 피해 적용 순서를 결정하고, 표현에는 중단 시점과 새 돌진 구간을 전달한다. 미리 계산한 최종 보드 상태를 현재 표시 상태로 간주하지 않는다. 후보가 없으면 기존 일반 블록 대체 경로를 검사하고, 대체 후보도 없고 진행 중 효과로 생길 후보도 없다면 타격 없이 비행을 종료해 무한 호버를 막는다. 취소·씬 전환·풀 반환 시 대기와 예약·위치·프레임 상태를 정리한다.

이 연출 변경은 명시적으로 요청된 동작 변경이며 기존 원형 비행과의 표현 일치 대상에서 제외한다. 목표 우선순위·피해·미션 집계 변경은 포함하지 않는다. 과거 선회 검증 문서는 당시 구현의 이력으로 유지하며 이 절을 신규 구현 기준으로 사용한다.

## 10. 범위와 한계

새 고유 행동의 설계·검증 비용은 사라지지 않는다. 목표는 같은 기능의 재구현과 연결 누락을 줄이는 것이다. ECS, DI 전면 교체, 새 asmdef, 외부 패키지, 전체 코드 이동, 아트 교체는 범위 밖이다.

플레이어 빌드와 Addressables 콘텐츠 빌드는 하지 않는다. 이 설계와 단계 계획을 검토한 뒤 구현에 착수한다. 문서 저장은 구현 승인이나 검증 완료를 뜻하지 않는다.
