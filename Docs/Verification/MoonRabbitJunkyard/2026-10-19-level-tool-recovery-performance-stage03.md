## 측정 판정

- 동일 Unity 프로세스에서 고정 입력 3회 반복. 첫 표본과 뒤의 워밍업 표본을 구분한다.
- 표본 사이에만 GC를 수행한다. 실행 중 최대 working set은 100ms 간격으로 측정한다. OS 전체/Unity 프로세스 메모리와 관리 힙을 혼동하지 않는다.
- Export는 복구한 같은 작업공간에서 별도 측정하며, Save/Read/Apply 합계와 구분한다. 최초 파싱과 검증을 포함한 총 시간도 기록한다.
- 표본당 30초/Unity working set 8GiB 보호 한도를 유지한다.
- Ruling: 30회·60회는 재실행하지 않는다. 2단계 30회가 보호 종료되었으므로 정상 완료한 10회 표본까지만 반복한다. 큰 표본 목표는 미검증으로 남긴다.
- 실제 화면은 Unity Play Mode의 격리된 화면 인스턴스로 측정한다. 제품 실행 파일·Android 실기기 성능 검증을 대체하지 않는다.

## 수명주기 검토 범위

- 자동 저장은 UI에서 캡처한 문자열/View를 넘기며, 같은 화면의 draftStore는 최초 초기화 후 교체하지 않는다. store의 gate/sequence를 늦은 이전 저장 검사로 확인했다.
- 읽기는 recoveryReadRevision과 isActiveAndEnabled를 확인하고, OnDisable은 revision을 올린다. 재활성화 시 기존 Session이 있으면 파일로 다시 덮지 않는다. wantsToQuit는 등록 전 해제하는 경계를 소스에서 확인했다.
- 프로젝트 가져오기/전환 취소, 종료 취소·저장 실패, Pause/새 화면 복구는 실제 UI 17사례로 검사했다. 모든 OS 스케줄 순서를 강제한 경합 검사나 이벤트 구독 개수 계측을 수행했다는 의미는 아니다.
- 공유 튜토리얼 사본은 독립 이력 저장·복원 및 부모 적용까지 모델/저장 경계에서 확인했다. 공유 사본 편집 화면의 모든 위젯에 대한 종단간 검사는 아니다.

## 남은 성능 작업의 선택지

| 기준 | 관측 결과 | 판정 |
|---|---|---|
| 38문서/10회 복구 경로 5초 이하 | 3회 중앙값 11.125초, 최대 11.341초 | 미달 |
| 60회 복구 경로 15초 이하 | 2단계 30회 Read 중 보호 종료 후 60회 미실행 | 미검증 |

1. 다음 성능 작업을 승인한다면 메인 스레드의 전체 v1 직렬화와 종료 동기 Flush를 우선 분리 설계한다. 가변 Session/UI를 그대로 작업 스레드에 보내지 않고 일관된 스냅샷 소유권을 먼저 정해야 한다.
2. 전체 30MB급 v1 이력을 매번 기록·파싱하는 비용은 남아 있다. 이를 줄이는 증분/분리 저장은 이전 기록 호환·원자적 저장·previous 복원 정책까지 영향을 주므로 별도 승인할 구조 변경이다.
3. Undo 수 축소, 사용자 이력 삭제, 보호 한도 상향으로 목표를 맞추지 않는다. 30회 보호 종료와 60회 미실행은 그대로 남긴다.
