# 화면 갱신 최적화 1단계 — 작업·검증 기록

상태: 1단계 구현·회귀·측정 완료(2026-10-20). 전체 100ms 성능 목표는 미달이며 2·3단계는 미착수다. 아래 중간 실패는 최종 검사와 구분한다.

계획: [화면 갱신·문서 복사 성능 개선](../../Planning/MoonRabbitJunkyard/LevelToolRecoveryPerformance/2026-10-20-edit-refresh-performance-plan.md).

## 시작 상태와 판단

- `work` 브랜치에서 기존 계획 문서 변경을 보존한다. 커밋·푸시·제품 빌드·HTML 변경을 하지 않는다.
- 기존 고정 입력 SHA256이 계획과 일치함을 확인했다.
- `Refresh`는 속성/공급/튜토리얼 패널을 매번 비우고 시험 보드를 폐기한다. 정의 변환, 전체 문서 조회, 보드 비교용 문자열 생성도 반복된다.
- 호출부는 일반 Edit, 선택/브러시, 흐름/연결 도구, 튜토리얼 UI 내부 상태, 세션 전환, 저장/이탈, 시험 기록 변경으로 나뉜다. 선택적 갱신은 튜토리얼의 UI 전용 상태와 시험 기록의 외부 변경도 처리해야 한다.
- 사용자 지시에 따라 현재 작업 트리를 유지하고 하위 에이전트·별도 worktree를 사용하지 않는다. 실행 계획 스킬의 커밋/리뷰어 지시보다 사용자 제약을 우선한다.

## 중간 점검 당시 남은 작업

세부 갱신 의존성과 캐시 수명 검토, 검사 결과/시험 기록 갱신, 이탈 후 불필요한 갱신 제거, 입력/저장/공유/재로드 회귀, 화면 크기별 검사, 2단계 문서와 최종 보고가 남아 있다. 추가 수정 시 필요한 최종 측정을 수행한다.

후속 검토에서 확인한 경로:

- `UpdatePackStatus()`는 팩 상태를 한 번 확인한 뒤 매 Refresh에 전체 스냅샷을 구성한다. 상태의 최신성을 유지하면서 동일 문서 상태의 반복 비교를 피해야 한다.
- `ValidationIsCurrent()`도 검사 이후 전체 문서 사본을 반복 생성한다. 기존 검사 결과의 최신/낡음 판정을 보존해야 한다.
- 시험 기록 삭제/실패 후 Refresh는 문서 변경이 없으므로 명시적 속성 갱신 연결이 필요하다.
- `PrepareDisplay()` 예외가 기존 Refresh 오류 안내 경계를 벗어나지 않게 검토해야 한다.
- 문서 버전 API의 읽기 격리, Undo/Redo·동일 ID 재로드, 선택/브러시 변경에서 정의 재사용 검사를 확장해야 한다.
