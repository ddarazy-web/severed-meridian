## 파일 읽기와 메모리 검증

- 목록·검색 동안 모든 본문을 FileShare.None으로 잠갔다. 열기·표시·검색 모두 성공하여 본문 읽기 0건을 확인했다. 테스트의 잠금 준비 비용은 측정 구간 밖이다.
- 편집 때 선택한 첫/마지막 레벨 및 공유 문서만 잠금을 풀었다. 다른 998/9,998개 레벨은 저장 완료까지 잠근 상태였다.
- 실제 디렉터리 읽기 캐시는 두 규모, 네 표본 모두 21개였다: 선택한 레벨 2개 + catalog 1개 + element 18개. 정확한 ID는 measurements의 reads 행에 있다. 목록 수에 비례하여 레벨 본문을 읽지 않았다.
- 변경 레벨 저장도 다른 레벨 본문을 읽지 않고 통과했다. 전체 프로젝트의 참조 유효성을 검사했다는 의미는 아니며, 별도 전체 검사 상태는 유지된다.
- Editor 프로세스 전체 working set 최대는 1천 약 2,417.5MiB, 1만 약 2,536.2MiB. Unity·패키지·검사 fixture 준비 등을 포함하므로 레벨툴 단독 메모리나 파일별 소비량으로 해석하지 않는다.
- 관리 메모리 전후값은 원시 결과에 있으며 GC 영향을 받는다. Mono 할당량 API가 증가하지 않는 환경임을 probe로 확인하여 allocatedBytes는 null이다. 0바이트 할당으로 보고하지 않는다.
- 6GiB 검사 메모리 한계에 도달하지 않았다. 종료 후 소유 data 폴더 삭제 확인, 결과 파일 보존.

## 판단과 남은 검증

이 환경에서 목록 열기와 준비는 1만 파일에서도 첫 회 합계 약 491ms였다. 이후 변경 검토의 참고 예산은 같은 환경·fixture에서 목록 열기+준비 1초 이내, 첫 편집+준비 0.5초 이내, 단일 변경 저장 2초 이내로 둔다. 플랫폼 전체의 보장 수치나 부하 변동이 없는 절대 기준으로 사용하지 않는다. 가장 중요한 회귀 조건은 목록 본문 읽기 0건과 선택·참조만 읽기다.

이전 전량 읽기 기록과 원본 revision은 같지만 fixture 직렬화 크기와 측정 경로가 다르므로 배수 향상률을 계산하지 않는다. 현재 비교는 전량 준비에서 목록 전용 준비로 바뀐 경계와 위의 실측값을 근거로 한다. 동일 파일 바이트·동일 경로의 전후 비교 완료로 주장하지 않는다.

실제 렌더 프레임·육안 화면, 대량 복구, 공유 미리보기/게임 시험, MemoryPack 입력 호환 및 최종 리뷰는 별도 완료 조건으로 남는다. 이 보고서는 2단계 전체 완료 보고가 아니다.
