# 수동 저장 전환 3단계 검증 기록

상태: 3단계 측정·회귀 검증 완료. 편집 100ms 목표는 미달이며 아래에 남은 병목과 미검증 항목을 명시한다.

## 실행 판단

- 기존 1·2단계와 미커밋 변경을 보존한다. 제품 빌드·커밋·푸시·HTML 갱신·씬/프리팹 저장·하위 에이전트 사용 없음.
- 기존 자동 복구 화면 측정 진입점은 수동 저장 회귀만 수행한다. 이를 반복 성능 결과로 사용하지 않고 별도 측정 검사를 추가한다.
- 입력은 기존 `Logs/LevelToolRecoveryPerformance/stage01/fixed-ten-record.json`의 현재 38문서 스냅샷이다. 과거 이력 복원·샘플 준비는 측정 중 편집 비용과 구분한다. 각 표본은 같은 현재 문서에서 새 메모리 편집 세션을 구성한다.
- 3회 표본에서 10회 편집, Undo, Redo, 유휴, 명시적 저장, clean 상태 이탈 및 비활성화를 순서대로 측정한다. 첫 표본과 워밍업 표본을 구분한다.
- Editor update 간격은 렌더 프레임 지연으로 주장하지 않는다. 동기 명령 시간, 다음 Editor update까지의 간격, 명시적 저장 전체 대기를 분리한다.
- 과거 650ms 자동 Export 및 11초 Flush와 비교할 대상은 해당 경로의 제거 여부다. 현재 JSON 저장 시간이 과거 전체 이력 복구 저장과 동일한 작업이라는 비교는 하지 않는다.
- 표본 30초/Unity working set 8GiB 한도를 유지한다. 보호 종료는 실패 표본이며 자동으로 반복하지 않는다.

### 판정 및 다음 개선 우선순위

1. **100ms 편집 목표 미달.** 측정된 편집 시간 중 명령·화면 갱신 쪽이 데이터 변경보다 크다. 먼저 전체 Refresh 대신 변경된 패널/보드만 갱신하고, 보드 비교용 전체 비레벨 JSON 문자열 생성과 반복 문서 사본을 줄이는 설계를 검토한다.
2. **데이터 편집 자체도 약 150ms.** AuthoringEditSession.Apply가 전체 문서 초안을 복사하는 경로를 확인했다. 변경 문서 중심으로 복사 범위를 줄이되 외부 참조 격리·Undo/Redo·dirty 의미를 보존하는 후속 설계가 필요하다.
3. **수동 저장은 약 9.8~9.9초.** 저장소 검증·직렬화·파일 게시·화면 갱신을 세부 측정한 뒤 최적화해야 한다. 이번 수치만으로 디스크 쓰기가 원인이라고 단정하지 않는다.
4. **clean 이탈의 복구 Flush는 제거됐으나 약 0.33~0.42초가 남는다.** 종료 경로 finally의 Refresh가 남아 있다. 실제 이탈 이후 필요 없는 갱신을 줄일 수 있는지 확인한다. 이번 단계에서 동작을 변경하지 않았다.

위 항목은 다음 작업 제안이며 런타임 최적화 구현이나 새 저장 방식 도입을 자동 시작하지 않았다.
